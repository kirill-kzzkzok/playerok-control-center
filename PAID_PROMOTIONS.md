# Платное продвижение: план реализации

Исходный HEAD: 4bfe411. Только разработка и локальные проверки; реальных расходов/изменений лотов нет.

1. PREMIUM-публикация и поднятие: актуальный серверный тариф → подтверждение владельца → атомарный резерв бюджета и запись Outbox → свежие проверки → намерение перед HTTP → серверная транзакция → независимое чтение.
2. Существующие promotion_policy/targets/schedule/expenses сохраняются. Новые разрешения исполнения хранятся в settings и привязаны к account ID, версии политики и точному тарифу. Старые dry-run-политики не активируют расходы.
3. Ручная PREMIUM-публикация требует writes и подтверждения суммы; автоматическое поднятие также automation, явного разрешения для товара и текущей политики. Лимиты одной операции/суток/месяца/числа операций применяются атомарно; неопределённые расходы учитываются полностью.
4. Outbox/lease/permit/CAS остаются единственным путём мутации. Таймаут/рестарт после намерения = UNCERTAIN, без слепого повтора. Успех требует нового ID платежа и независимого совпадающего statusPayment. Неразрешённая неопределённость блокирует новые расходы.
5. Telegram: товар → другие действия → PREMIUM/поднятие; продвижение → тариф товара / бюджет / расписание / отдельное включение / остановка. Сохраняются проверки без оплаты и старые callback.
6. Целевые Dispatcher/transport/concurrency/fault тесты, полный pytest, Ruff/pip/selfcheck. Документация/commit/push. Live-платежи только отдельным сценарием.

Источники контракта: используемые playerokapi.account и QUERIES; https://playerokapi.readthedocs.io/ru/latest/account.html ; сведения о продвижении https://t.me/s/playerok_merchants?before=64 . Цены берутся только из API, не из публикаций.


## Реализованный путь

Новые виды существующего Outbox: premium_publish и premium_bump. Запись задачи, резерв promotion_expenses и owner receipt создаются одной SQLite-транзакцией; схемы и миграции не менялись. Снимок содержит account ID, товар, tariff ID/type/period/amount, исходный payment ID, owner, версию политики. Намерение в settings записывается до внешнего запроса. Оплаты сериализованы durable pending-intent; расходы с неизвестным исходом учитываются в лимитах и блокируют другие новые расходы. Бюджет повторно проверяется в фактические сутки/месяц отправки.

В SafeAccount сохранены permit, thread guard, точный QUERIES и allowlist; добавлен increaseItemPriorityStatus и разбор MyItem для обеих мутаций: upstream Item терял statusPayment. Только LOCAL, без card/paymentMethodId. Успех: новый transaction ID из ACK, независимый get_item с тем же transaction ID и CONFIRMED/OUT/LOCAL/ITEM_PREMIUM_PRIORITY, точная сумма, владелец/товар/PREMIUM и допустимый статус. Повторно использовать прежнюю квитанцию нельзя.

При потере ACK или ошибке readback — UNCERTAIN. Если candidate ID из ACK сохранён, положительная сверка доступна через существующую историю операций с подтверждением владельца. Если ID потерян — отсутствие квитанции не разрешает повтор. STOP_UNCERTAIN после начатого запроса не освобождает неопределённый бюджет. Если durable intent вообще не начинался и lease уже прекращён, явная остановка владельца может освободить резерв; прежний worker не проходит guard.

Товарный тариф и общее разрешение расписания подтверждаются отдельно и привязаны к версии настроек. Изменение политики/цены не включает новый тариф автоматически. Существующий PromotionWorker выполняет discovery/evaluate, после отдельного допуска ставит платную операцию в очередь. Gifts, возвраты, склад и их допуски не менялись.

## Остаточные ограничения до live-приёмки

- Настоящие платные мутации и ответы аккаунта не проверялись; локальные тесты не доказывают live-публикацию/поднятие. Нужно отдельное разрешение на один конкретный товар, тариф и максимальную сумму.
- Используемый серверный input содержит tariff ID, но не поле maxAmount. Клиент повторно проверяет сумму и состояние непосредственно перед запросом и ограничивает возраст тарифа, однако не может атомарно зафиксировать серверную цену при одновременном внешнем изменении. Если сервер списал другую сумму, подтверждение не проходит, состояние становится UNCERTAIN и новые расходы блокируются. Абсолютная серверная гарантия потолка расхода этим контрактом не доказана.
- Если Playerok не возвращает однозначный statusPayment, либо его статус/сумма не подтверждены, результат остаётся UNCERTAIN. Нельзя считать один priority=PREMIUM доказательством нового списания.
- При полном отсутствии ID потерянного ACK автоматическая корреляция нового платежа с этой попыткой не доказывается; ручная поддержка/разбор не заменяются повторной покупкой.
- Реальная банковская оплата, пополнение и вывод не реализованы; автоматическое повышение обычных товаров в PREMIUM без отдельного подтверждения не добавлено. Авторасписание обновляет подтверждённый PREMIUM-тариф.
