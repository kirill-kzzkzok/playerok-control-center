# AGENTS.md — обязательные правила разработки

Эти правила закреплены после серии регрессий, когда каждое точечное исправление
порождало новые дефекты того же класса. Они обязательны для всех агентов и людей,
работающих с этим репозиторием.

## A. Contract first
Перед изменением кода зафиксируй в PROGRESS.md: пользовательский сценарий,
инварианты и ожидаемое состояние при каждом отказе. Сначала границы транзакций
и переходы состояний — потом код.

## B. Red before green
Для каждой подтверждённой гипотезы дефекта сначала напиши воспроизводящий тест
(RED), затем минимальное исправление, затем GREEN. Тест, который не падал до
исправления, не доказывает исправление.

## C. Small coherent diffs
Не смешивай независимые изменения в одном большом патче. Каждый этап — отдельный
список изменённых файлов и фактические результаты тестов (exit code, а не
«должно работать»).

## D. Adversarial review
Независимый ревьюер обязан искать сценарий, ЛОМАЮЩИЙ реализацию, а не
подтверждающий её. Формулировка «всё выглядит хорошо» — не результат ревью.
Для платёжных изменений обязательны темы: duplicate execution, unknown outcome,
budget authority, изоляция лотов, восстановление после рестарта.

## E. Real user paths
Тесты Telegram-бота проверяют настоящие Dispatcher/FSM-переходы (ui.click /
ui.message), а не только прямые вызовы Python-сервисов. Тест, который вручную
готовит «идеальную» БД в обход интерфейса, не доказывает пользовательский путь.

## F. No greenwashing
Нельзя заявлять, что сценарий покрыт, если тест проверяет лишь наличие записи в
БД, а не фактическое решение worker/guard/планировщика. Отсутствие найденной
ошибки — не доказательство отсутствия ошибок.

## G. Money is special
Любая правка платных операций (approve/arm/queue/execute/reconcile) требует
проверки на: двойное списание, неизвестный результат (никогда не повторяется
вслепую), бюджетные лимиты, изоляцию между лотами, восстановление после
рестарта. UNCERTAIN-статус — терминальный для автоматики.

## H. Simplicity budget
Усложнение архитектуры требует письменного обоснования в PROGRESS.md:
почему нельзя проще, какой класс ошибок устраняется, какой новый появляется,
сколько новых состояний/зависимостей, какие ветви можно удалить. Если код
растёт, а число опасных состояний не сокращается — пересмотри решение.

## Ключевые инварианты репозитория
- PREPARE (чтения) строго отделён от COMMIT (одна атомарная транзакция).
- Никаких ручных snapshot/rollback-цепочек для локальных записей: атомарность
  даёт SQLite, а не восстановление состояния вручную.
- Внешние мутации — только через Outbox worker с guard/preflight.
- `intent.started_at` пишется атомарно ДО внешней мутации и служит единственным
  доказательством «отправка не начиналась».
- Рабочие .env, SQLite, Telegram-сессии в тестах не используются.
