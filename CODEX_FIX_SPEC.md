- Важна безопасность: reply, read и другие операции нельзя отправлять дважды из-за изменения статуса, повторного callback, рестарта, редактирования панели или ручного обновления результата.

- Реализуй наблюдение за жизненным циклом исходной Telegram-панели: status PENDING → PROCESSING → SUCCEEDED/PERMANENT_FAILED/UNCERTAIN; редактируй только конкретный известный message_id и только когда он всё ещё соответствует операции. Не позволяй worker перезаписывать уже навигированный на другую страницу экран.

F4. UNKNOWN Telegram send и `operation_receipts.notice_status=UNCERTAIN`.
- Отчёт верно показывает, что `notice_status=UNCERTAIN` не восстанавливается автоматически; это вызывает невидимые результаты. Но его предложение автоматически перевести UNCERTAIN→PENDING и послать новую квитанцию ОПАСНО: Telegram мог уже принять первую. НЕ делай безусловных ретраев.
- Разработай безопасную схему: предпочтительно idempotent edit уже известного ID, статус в открываемом по кнопке result:show, owner-initiated explicit recovery и отдельная диагностика «уведомление могло быть доставлено». Новое сообщение отправлять только когда достоверно известно, что первая отправка отклонена, либо после явного действия владельца с осознанием возможного дубля.
- Состояния PROCESSING/SENT/UNCERTAIN при рестарте должны быть видимы и достоверны; единственная потеря Telegram ACK не должна приводить к повторной отправке buyer reply или Gift.

F7. Обновление/удаление входящих сообщений.
- `inbox.payload` сейчас фиксируется первым ingest; `chat_messages.payload` обновляется. Проверь, как синхронизация передаёт deleted_at/is_read и какие ранее отправленные уведомления требуют безопасного обновления.
- Реализуй согласованное хранение и отображение изменённого/удалённого сообщения при сохранении history и event-key идемпотентности; никогда не создавай новое входящее уведомление просто из-за правки старого сообщения.
- Если Telegram уведомление уже отправлено, при возможности редактируй известный ID, а при неизвестном результате сохраняй неопределённость; не пытайся слепо повторять отправку.

F8. Backoff по уведомлениям.
- `defer_update` обновляет все notification_actions по owner/event вместо точных операций. Сделай retry metadata согласованными и изолированными: ошибка редактирования одного уведомления не должна портить счётчики и расписание несвязанных операций. Если backoff относится к уведомлению как целому — перенеси/выдели соответствующую сущность и добавь отдельные тесты нескольких операций на одном событии.
- Тестируй Telegram `message is not modified`, `message to edit not found`, `message can't be edited`, 429, network unknown и ситуацию, когда первое редактирование реально прошло, но ACK потерялся.

F9. Уведомление о заказе и статус.
- Перепроверь отмеченное аудитором как PROBABLE поведение. Если текущий код уже корректно отсекает устаревшее событие заказа — зафиксируй REJECTED/NO_CHANGE. Не делай фиктивный фикс только ради покрытия списка.

ЭТАП 3. P1 — СОХРАННОСТЬ ДЕНЕГ/СЕКРЕТОВ И ДОСТАВКА (F10–F14, F18)

Это самая опасная часть. Здесь запрещены решения «поменять все PERMANENT_FAILED на AVAILABLE» или «все 4xx считать определённым отказом». Цель — сохранить и safety (не отправлять/не списывать дважды), и liveness (не блокировать навсегда доказуемо безопасные операции).

F10 + F13. Preflight read, external dispatch и карантин.
- Построй полную state machine от резервирования товара до результата: локальные проверки → чтения Playerok (`get_deal`, `get_chat`, `fresh_delivery_item` и т.д.) → готовность к первому внешнему mutation POST → попытка POST → доказанный server receipt / отказ / unknown → Store.finish / chain outcome.
- Классифицируй отказ по фазе, а не только `APIError.uncertain=not read`. Если сбой произошёл ДО отправки внешней мутации, безопасное повторение именно preflight-чтений возможно; нельзя без необходимости терминировать заказ и навсегда карантинить секрет.
- Если mutating request мог быть отправлен, но receipt неизвестен — сохраняй UNCERTAIN/QUARANTINED, останавливай автоматические повторы, требуй read-only сверку результата. Никогда автоматически не возвращай этот секрет в AVAILABLE.
- Если внешняя отправка точно не произошла (локальный guard, запрет до сетевого вызова, однозначно документированное отклонение без side effect), предусмотри согласованный переход: безопасный bounded retry, сохранение резерва или освобождение по явно доказанной политике. Согласуй order, reservation, inventory, chain, outbox и audit_log в одной транзакции/CAS. Не отдавай секрет другому покупателю, пока исход предыдущей попытки не известен.
- Учитывай сетевые read-only preflight `503`, `429`, timeout, недоступный Playerok, смену аккаунта, cancellation/STOP, рестарт между preflight и POST, crash после POST до ACK, поздний результат и истечение lease.
- Если для гарантий фазы внешнего запроса необходим durable marker, вводи его через обратносуместимую миграцию с точной семантикой; marker не должен сам по себе объявлять внешний SUCCESS.
- `RETRYABLE_FAILED` можно использовать только когда доказано отсутствие внешней отправки и соблюдены лимиты/backoff/сохранность резерва. Убедись, что recover()/claim() не создают бесконечный цикл и не нарушают STOP.
- Для цепочки выдачи проверь разные шаги: сохранение секрета, отправка, благодарность, отметка fulfilled, частичный успех. Запрещено превращать неопределённый предыдущий шаг в безопасный повтор.

F11. Проблемные заказы.
- `Orders.reserve()` обязан учитывать локальные problem-аннотации, серверный `has_problem`, актуальность PAID, ownership, chat и logical product binding. Сейчас по аудиту problem-аннотация может пропускаться до reserve и быть замечена только в executor.
- Добавь проверку в момент reservation с теми же консервативными инвариантами, что использует executor. При изменении статуса между reserve и POST отказ должен быть безопасным, без потери уникальной единицы и без отправки покупателю.

F12. Разные режимы автовыдачи.
- Не вызывай глобальный `empty_stock` и не выключай автодоставку fixed_text/telegram_gift/manual из-за отсутствия inventory, когда данная политика не требует уникального склада. Определи тип выдачи из единого авторитетного места (logical product/политика) и соблюдай взаимную изоляцию режимов.
- Негативные тесты: нет unique_stock → блок только stock-policy; fixed_text/gift остаются неизменными; ручной reserve неподходящей политики отклоняется без side effects.

F14. HTTP 4xx, 429 и неизвестные результаты.
- Проверяй реальную семантику Playerok/GraphQL, а не обобщай HTTP status. Запрос мог достигнуть сервера до получения ошибки; 429, 409, 401/403, HTTP 500, timeout и GraphQL errors имеют различную степень определённости. Сам код `release_launch` предполагает некоторые releasable errors, но это НЕ универсальное доказательство для выдачи, оплаты и других операций.
- Создай типизированную матрицу исходов по operation kind + фазе запроса + доказательству server-side effect: NOT_DISPATCHED, CONFIRMED_REJECTED, CONFIRMED_SUCCESS, UNKNOWN. Не заявляй `CONFIRMED_REJECTED` без реальных оснований.
- Протестируй HTTP 200 с GraphQL errors, partial data, empty receipt, HTTP 429 с Retry-After, network timeout до соединения, timeout после потенциальной отправки, 401/403, 5xx, изменение connection state после завершённого ответа.
- Для операций с деньгами/подарками оставь более строгие гарантии текущего кода; не делай «оптимизаций», увеличивающих шанс двойного списания.

F18. Race с инвалидированной сессией.
- Если соединение меняет состояние во время безопасного чтения, не следует терминировать уже зарезервированную выдачу с необратимым карантином только по этому факту. Но уже начатые мутации нельзя объявлять невыполненными без доказательства.
- Проанализируй защиту от смены аккаунта и владельца между preflight, dispatch и получением результата; сохраняй fencing и запрет чужих операций.
