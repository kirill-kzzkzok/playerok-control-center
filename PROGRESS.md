Не запускать Universal: его фоновые задачи могут менять магазин и выводить деньги.
Переиспользовать MIT-модели, GraphQL-запросы и парсеры PlayerokAPI; заменить опасный транспорт.

первый /start в личном чате атомарно закрепляет единственного владельца в SQLite.
По умолчанию в .env.example эта возможность выключена. Тест конкурентных claims проходит.
Нельзя выдавать незавершённые live-критерии за выполненные.

## PHASE 4 — сохраняемая сверка и история диалогов (2026-10-30)

Синхронизация больше не требует завершить всю историю за один цикл. Для заказов,
списка диалогов и сообщений каждого чата сохраняется cursor checkpoint. Один проход
ограничен четырьмя страницами на поток; в цикле обслуживаются 12 самых давно
проверенных диалогов. При продолжении истории отдельно запрашивается первая страница,
чтобы видеть новые записи. После конца прохода начинается очередная полная сверка:
порядок/стабильность opaque cursors не предполагается. Это bounded reconciliation,
а не обещание мгновенного получения всех событий или WebSocket.

Сначала сохраняются записи страницы, затем cursor. Сбой между ними приводит к
безопасному повтору через устойчивые inbox keys. Сетевой сбой сохраняет checkpoint;
некорректный/зацикленный cursor сбрасывает проход. Ошибка одного API-потока/чата
не прерывает остальные. Недоступный чат сохраняет error_code и участвует в очереди
проверок, не занимая её навсегда. BACKFILL означает незавершённую начальную загрузку;
OK появляется после полных первых проходов. Ручная кнопка сверки больше не объявляет
всю историю загруженной после одного цикла. Параллельные once сериализованы lock.

Миграция v3 добавляет sync_chats и индексы. Перед применением к локальной рабочей
БД сделана SQLite backup: data/backups/before-sync-v3-*.sqlite3. Реальная read-only
проверка: 24 диалога, 4 checkpoint, BACKFILL с 23 необработанными до конца чатами,
217 заказов и 1 администратор сохранены, errors={}, mutations=0.
Свидетельство: data/live_sync_readonly.json. Уведомления/ответы покупателям в live
проверке не запускались, рабочие лоты не изменялись.

Telegram: история чата имеет страницы старее/новее, автора/дату, признак удаления
и количество изображений. Cursor и nonce хранятся в durable FSM; старые callbacks
отклоняются. Просмотр истории не создаёт входящие события/уведомления и не меняет
прочитанность. Явная кнопка «Прочитано» требует подтверждения и проходит через outbox;
успех требует ответа с тем же chat ID и unread counter=0. Неопределённый результат
не повторяется автоматически. Эта mutation проверена на mock API, live не выполнялась.

Уведомления: первоначальный baseline и initialized фиксируются одной транзакцией;
выборка ограничена 200 ещё не обработанными для владельцев событиями. Собственные и
неподдерживаемые события отмечаются SKIPPED, поэтому не блокируют следующие пакеты.
Изменившиеся сообщения обновляются в локальном кеше без второго входящего события.

обновление Telegram-уведомления после ответа, безопасный интерфейс ручной сверки

## PHASE 4 — быстрые ответы и сохранение уведомлений (2026-10-30)

Добавлены локальные шаблоны ответов: до 20 на владельца, название до 48 и текст до
3500 UTF-16 единиц. Создание проходит через сохраняемый FSM; изменение и удаление
проверяют владельца/revision, удаление имеет отдельное подтверждение. В настройках
есть управление шаблонами. «Ответить» позволяет ввести свой текст сразу либо выбрать
шаблон; выбор показывает весь текст, а отправка требует отдельного подтверждения.
Устаревшие кнопки не работают; шаблон сам по себе не создаёт outbox и не отправляется.

Исправлено разрушение важных уведомлений: кнопки исходного Telegram-уведомления
теперь открывают дополнительное сообщение, сохраняя оригинал. Связь операции с ним
фиксируется в notification_actions одной транзакцией с enqueue. Проверяются владелец,
исходное event_key, chat ID и сохранённый Telegram message ID; произвольное уведомление
или чужой чат привязать нельзя. Payload реального API не содержит служебной связи.

Notifications обновляет исходное сообщение по сохранённому ID: состояние очереди,
результат API, remote message ID, либо явный UNCERTAIN. Исходный вопрос и кнопки
сохраняются; приватный текст отправленного ответа повторно в уведомление не копируется.

## PHASE 4 — ручное разрешение UNCERTAIN (2026-10-30)

Диагностика получила постраничную историю операций и отдельный список UNCERTAIN.
Карточка показывает только безопасные метаданные/статусы upload journal, без текстов

владельцем. Решение остаётся ручным, не называется автоматическим успехом API.
Для mark_read проверяется актуальный unread counter=0. Перед записью решения чтения
повторяются; операция/владелец/snapshot сверяются ещё раз.

Другой исход — STOP_UNCERTAIN: локальный повтор останавливается, внешний результат
остаётся UNKNOWN. API mutations и новые outbox не создаются. Резерв остаётся
QUARANTINED, фото сохраняются как свидетельства даже после локального закрытия.
Для создания/редактирования/публикации и других mutation успешность в этом UI не
угадывается: доступна только остановка без повтора. Успешное создание не подделывается
без привязки remote ID. Кнопки повторной отправки неизвестных операций нет.

Решение требует комментария без секретов и отдельного подтверждения. FSM переживает
restart. operation_resolutions, изменение outbox, перевод подтверждённого резерва в
DELIVERED и audit записываются одной транзакцией. Одновременное решение через другое
подключение отвергается. Исходные error_code/result сохраняются; ответ покупателю и
завершение сделки в Playerok при этом не вызываются.

finish/recover атомарно создают безопасное durable событие operation_uncertain;
уведомление владельцу не ждёт первоначального sync и не попадает в baseline истории.
Notifications работает также при отсутствии сессии Playerok; уже закрытое до отправки
событие не создаёт устаревшую тревогу. Сообщения содержат только ID/тип операции.
Ручной успех в исходном уведомлении помечен как решение владельца после сверки,
а остановка — как неизвестный внешний результат, без ложного «не отправлено».

## PHASE 4 — WebSocket и сохраняемые сигналы сверки (2026-10-30)

неполная сделка не мешает другому чату. Обычный периодический обход истории продолжает
работать независимо от WebSocket. catchup означает ограниченный цикл, а не доказательство
полноты истории: BACKFILL остаётся видимым до окончания первой загрузки.

важный случай: нативные ping могут продлевать внутренний receive timeout. Внешний

в подтверждённом чате продажи по прежним sender/text/time правилам. Разрешение одного
шага само по себе не возобновляет остановленную цепочку — автоповтора нет. Запрошенный
