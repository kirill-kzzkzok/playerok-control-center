## B. Запрос пользователя и подготовка

Пользователь разрешил создать тестовый лот Telegram→Stars, цена1000р, белая TEST
картинка; дополнительных вопросов не задавать. Картинка подготовлена локально:
 data/live_proposal/telegram_stars_test.jpg. Local proposalJSON отдельно от рабочего
SQLite, без outbox и без разрешающих flags. Candidate50Stars выбран только для
локальной структуры и не подтверждает возможность фактической передачи.

Серверный create не выполнен: реальный товар/наличие/поставщик Stars не установлены,
правила категории требуют фактическую передачу Stars, прежний технический/non-sale
листинг уже отклонён. Новый технический лот не создаётся под видом реального.
Stars supplier integration не входит в текущий stock MVP. Stock-code message не
проверяет передачу Stars и не может закрыть критерий реальной выдачи.

## C. Минимальный разрешаемый live-проход при выполнении предпосылок

1. Установить реальный допустимый товар, выделенную единицу и способ передачи.
   Для складского MVP — уникальный реально поставляемый товар; для Stars необходим
   отдельный подтверждённый источник и способ перевода, без новой скрытой интеграции.
2. Один create с фото только в DRAFT. Меняется только новый объект; существующие лоты
   не редактируются. Проверить returned DRAFT/owner/category/text/price/photo IDs,
   затем get_item. Неизвестный результат оставить UNCERTAIN, не повторять create.
3. Отдельно согласованные edit name/description/price/photo на exact new ID; проверить
   returned fields и fresh read. Цена1000р — цена предложения, не разрешение списать1000р.
4. Отдельно согласованная publication только после live quote явного DEFAULT0, без
   PREMIUM/payment fallback. Exact ID/status/readback, не считать moderation активной
   публикацией. При отсутствии бесплатного quote остановиться.
5. Только согласованная controlled покупка/получатель и фактически доступный товар.
   Не покупать самому и не писать посторонним покупателям. Одна scoped политика на
   новый lot, future cutoff до test order, одна единица запаса; historical orders excluded.
   Не менять глобальные runtime flags без отдельного согласования.
6. Получить PAID по серверным фактам, зарезервировать1, выполнить1 выдачу и проверить
   message receipt/real delivery. UNKNOWN ->quarantine/manual reconciliation, no resend.
7. Подтверждение продавца только после фактической передачи и согласованного owner
   attestation. SENT не является buyer CONFIRMED; не подделывать приёмку покупателя.
8. Согласованное удаление непроданного test lot либо корректное завершение проданного.
   Exact owner/ID before action; response.deletedAt/read-state evidence, no auto-delete
   finally. Сохранить receipt и сравнить рабочие лоты/конфигурацию без их изменения.

## Риски, расходы и оставшиеся разрешения

Listing может быть отклонён модерацией; category agreements могут требовать отдельной
операции принятия. Free placement должно быть явно подтверждено API, не предположено.
Controlled покупка, комиссии продажи/вывода и поставщик могут иметь реальные расходы;
они не разрешены последним запросом. Publication/edit/delete/fulfillment/payment и
изменение глобальных flags не выводятся из разрешения создать draft. После конкретного
разрешения выполнять только согласованный этап, без повтора ранее rejected сценария.

## Локальное доказательство имеющегося stock MVP

Tests/test_mvp_sale_cycle.py связывает actual local services/workers с mock remote:
create/photo→publish→future PAID→atomic stock reserve→restart→delivery→owner confirmed
SENT/readback. Дублирование, lostACK и bad create receipt не дают повторной выдачи или
ложного успеха. Это mock evidence, live-create/Stars/payment критерии остаются открытыми.

## Остановка

Пока не установлен фактически допустимый товар/способ передачи, серверные записи не
выполняются. Без новых решений пользователя не развивать поставщиков Stars/Steam/
подарков, не переключать .env, не начинать P2 или новый масштабный аудит.
