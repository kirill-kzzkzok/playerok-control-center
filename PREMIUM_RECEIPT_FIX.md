Новая квитанция не привязана к другой операции, подтверждённому intent или
ручному финансовому разрешению на момент проверки.

**Первопричина:** после возвращения mutation код брал её status_payment.id,
сохранял его как candidate, выполнял ровно один немедленный get_item и требовал
совпадения с новым ID. Фактически mutation вернула в parsed result старый ID,
а независимая новая квитанция появилась позже единственной проверки. Receipt
guard правильно отвергал старое списание; execute затем скрывал причину общим
PREMIUM_PAYMENT_RESULT_UNKNOWN. Candidate не потерян — сохранён неверный для
этой покупки, прежний ID. Проверка никогда не дожидалась обновления.

Доказательства: сохранённый candidate==before_payment_id; создание новой
транзакции позже локальной записи UNKNOWN; первое авторизованное get_item
непосредственно связывало новый ID с TXE; независимая история подтверждает
именно этот ID и денежные поля. Воспроизводящий worker-тест возвращает старую
квитанцию из mutation, а затем новую из get_item — исходный код оставляет UNKNOWN.

Исходный сырой GraphQL mutation JSON приложение не сохраняло. Поэтому невозможно
восстановить все его исторические поля; факт старого parsed ID доказан intent.
Нельзя утверждать, что любой прежний UNKNOWN имеет ту же причину или что
Playerok всегда возвращает старую квитанцию.

## Реальный контракт API и SDK

Mutation increaseItemPriorityStatus и Item(MyItem) используют fragment
StatusPaymentTransaction: id, operation, direction, providerId, status,
statusDescription, statusExpirationDate, value, props.paymentURL.
Квитанция нового get_item фактически содержала:

```text

direction: OUT
```

В item-фрагменте нет createdAt/user самой транзакции. В истории transactions
есть createdAt, completedAt, user.id и те же денежные поля; точная запись имеет
createdAt=completedAt=2026-11-06T14:42:41.589Z и нужного владельца.
Транзакция не содержит itemId/quoteId в фактически проверенном ответе;
props.dealId=null. Нельзя связать её с лотом только по сумме и времени.
Связь даёт именно statusPayment.id в авторизованном ответе get_item для этого
лота либо точный candidate из ответа исходной mutation. SDK корректно сохраняет
эти поля: SafeAccount._placement→my_item→transaction→plain. Отдельный HTTP
MockTransport-тест проходит настоящие методы и parser; изменений SDK не нужно.

### Подтверждение после единственного POST

1. Mutation остаётся единственной. Сохраняется её точный candidate ID и факт
   возврата ответа до последующих чтений/валидации.
2. Выполняются максимум3 безопасных get_item с паузами0.5/1.5 секунды между
   проверками. Это ограниченный backoff для чтений, не повтор оплаты.
3. Валидный новый mutation candidate не заменяется более поздним ID. При старом
   или отсутствующем candidate после полученного ответа допускается только
   новый exact ID, непосредственно связанный текущим get_item с нужным лотом
   и владельцем. Этот anchor сохраняется ДО запроса истории.
4. Для обнаруженного readback ID требуется независимая история с точным ID,
   аккаунтом, ITEM_PREMIUM_PRIORITY, OUT, CONFIRMED, LOCAL/PENDING_INCOME, суммой
   и created_at в первых30 секундах от исходного intent. Поиск ограничен
   UTC-диапазоном и максимум4 страницами; само время проверяется повторно,
   серверный фильтр не является доказательством.
5. Для причинного mutation candidate используется прежняя историческая граница
   10 минут. Если лот уже показывает более позднюю квитанцию, точная исходная
   ищется по ID; её не заменяет совпавшая сумма. Сохранённый item anchor также
   переживает замену последней квитанции.
6. Квитанция атомарно закрепляется за intent при действующем lease. Полностью
   проверенный receipt сохраняется durable; последующий сбой чтения/рестарт
   не отменяет уже доказанный успех. Worker завершает Outbox+expense прежним
   транзакционным путём. При потере lease сохраняется UNKNOWN, а не новый POST.

### Восстановление и ограничения

Новые intent помечены для фоновой read-only сверки. Существующий PromotionWorker
сверяет одну due-операцию за цикл с ограниченным backoff через существующий
Reconciliation. Это работает и при отключённой политике покупок: учесть уже
сделанный расход не означает разрешить новые. STOP/бюджеты не включаются вновь.
Legacy intent без маркера и явно закрытые/финансово разрешённые владельцем
операции автоматически не переписываются.

Утрата ответа POST без точного сохранённого candidate/факта возврата не превращается
в success по текущему состоянию лота. Потерянный ответ остаётся UNKNOWN; нет
слепого повтора, автоматического освобождения резерва или возврата денег.

Во время COMMIT Reconciliation повторно проверяет expense/item/amount/account,
владельца и уникальность квитанции по Outbox result, intent.receipt_id и ручным
финансовым reviews. Конкурентные PREPARE не могут оба учесть один debit.
Проверенный платёж не требует нового согласия на тариф; изменённые денежные
условия по-прежнему требуют прежнего механизма разрешения.

### Диагностика без секретов

В существующем intent сохраняются stage, safe reason, candidate_present и
boolean checks: item/owner/id/new_id/amount/direction/operation/status/provider,
а при истории — history_id/account/amount/time и остальные денежные проверки.
Этапы: MUTATION_RESPONSE, CANDIDATE_EXTRACTION, READBACK, RECEIPT_VALIDATION,
PERSISTENCE. Не сохраняются произвольные exception text, raw API JSON, cookies,
сессионные данные, private props или персональные данные покупателей.
Внешний UNKNOWN-контракт сохранён, конкретная стадия больше не теряется.

## Операция62018: состояние и план только после отдельного согласия

В процессе расследования рабочая SQLite открывалась mode=ro + query_only;
total_changes=0. Операция/расход остаются UNCERTAIN, intent не изменён.
Платных POST0, сообщений/подарков/правок лотов0. Работающий магазин не перезапускался.

Первое авторизованное get_item зафиксировало связь нужного ID с TXE. Позже
get_item уже показывал `1f1d9f35-8a62-65c0-0ff8-1ab3f6971b08` — новое внешнее
изменение, не действие ассистента. Обычная сверка legacy intent со старым
candidate правильно отказалась подставлять эту более позднюю квитанцию.

Для подготовки проверен read-only facade: в памяти к исходному intent добавлен
anchor из ПЕРВОГО сохранённого ответа API (`data/premium-receipt-live-facts.json`),
затем выполнен настоящий новый get_transactions. Все8 history checks для
нужного ID прошли, total_changes=0; результат подготовки сохранён в
data/premium-receipt-prepared.json. Это подготовка, а не изменение живого intent
и не объявление рабочей операции SUCCEEDED.

**Предлагаемая запись после отдельного подтверждения владельца:**

1. Повторно прочитать viewer, точную транзакцию, исходный Outbox/expense/intent,
   сверить их с сохранённым диагностическим свидетельством связи с TXE.
   Проверить отсутствие чужого claim, late result и нового решения владельца.
2. Сохранить в существующий intent именно этот серверный anchor:
   candidate_id=`1f1d9f05-1f9a-6650-e7e2-4ac28d87eb6b`, source=ITEM_READBACK,
   target=исходный TXE. Сохранить прежний candidate и происхождение свидетельства
   в аудите; не включать automatic_receipt_check для этой legacy операции.
3. Вызвать существующий Reconciliation.resolve(CONFIRM_READ_STATE) с актуальной
   signature и причиной владельца. Его COMMIT атомарно закрепит receipt_id,
   pending=false, SUCCEEDED для расхода9 ₽ и операции, добавит resolution и аудит.
   started_at, attempts, исходный payload/тариф и история сохраняются.
4. Не выполнять POST, не запускать worker/магазин, не включать автопродвижение,
   не менять лимиты. Если свежее доказательство не проходит — оставить UNKNOWN.

Простое «продолжи» не трактуется как отдельное согласие на эту запись. До него
план не применяется. Сохранённый исходный anchor важен: API истории не даёт
независимого itemId для произвольной транзакции после смены statusPayment.
