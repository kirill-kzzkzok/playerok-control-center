# Глубокая проверка runtime Playerok Control Center

Дата: 05.11.2026. Проверяемый код: `aaa7045` (финальная полная регрессия запущена на этом HEAD). Начало работы: локальный `defef82`, который уже содержал изменения после GitHub `94e723b`. Рабочая SQLite, .env, разрешения и Telegram-сессия не изменялись. Существующие исправления сохранены.

## Граница результата

Это аудит критических производственных цепочек с воспроизведением найденных дефектов. Он не доказывает отсутствие всех возможных ошибок и не заменяет наблюдение работающего магазина. Платежей, отправок Gifts, сообщений покупателям, публикаций и изменений живых товаров не выполнялось.

Сеть текущей установки: Telegram — прямой транспорт приложения через системный Happ; Playerok — существующее Direct-правило Happ. FreeSocks не включался. Новые кнопки, экраны, разрешения и пользовательские настройки не добавлялись. После замены версии нужен обычный перезапуск процесса; старый запущенный Python автоматически новый код не загружает.

## Подтверждённые дефекты и исправления

### RT-01 — P1: падение кнопок при копировании RLock

- Код: `app/telegram/navigation.py:362`.
- Причина: `model_copy(deep=True)` входящей aiogram-клавиатуры копировал приватную привязку Bot → session/middleware → runtime с RLock. После сетевой ошибки обработчик переиспользовал входящий reply_markup.
- Последствие: исключение на нормальном callback товаров/операций, а не ошибка платежа.
- Исправление: клонируются сериализуемые поля клавиатуры через model_dump/model_validate; runtime Bot не копируется.
- RED: 3 failed, 1 passed; полный воспроизведённый traceback в локальном `data/deep-markup-red.txt`. В исходном журнале был текст исключения, полный исходный стек отсутствовал — его не выдумываем.
- GREEN: `tests/test_runtime_markup_copy.py`, реальные Dispatcher-переходы товаров, продвижения, заказов, меню; соседние message-scoped/back тесты — 24 passed.
- Остаток: не проверены реальные Telegram-клиенты всех владельцев; внешние сетевые ошибки остаются возможными.

### RT-02 — P1: периодическая проверка профиля останавливала независимые чтения

- Код: `app/services/playerok_connection.py:67`, `app/playerok/adapter.py:464,578`, `app/__main__.py:146`.
- Причина: периодический viewer переводил общий статус в UNKNOWN и закрывал записи. Playerok.call использовал тот же статус для запрета всех чтений, включая получение оплаченных заказов.
- Исправление: процесс сохраняет только уже доказанную read-identity для того же текущего account.id и bound_account_id. Временные network/timeout/5xx/429 сохраняют чтения, но не открывают мутации. Новый процесс начинает без read-proof. Явный отказ авторизации/другая личность очищают proof; повторная проверка обязательна перед записями.
- RED: 1 failed. GREEN: `tests/test_runtime_read_identity.py`, реальный SafeAccount/ThreadCalls, медленный viewer и независимый get_deals, восстановление, AUTH_REJECTED; профиль 32 passed.
- Остаток: причина конкретных физических обрывов Happ/провайдера не установлена по одному NETWORK_ERROR.

### RT-03 — P1: временный профильный запрет превращался в вечный BLOCKED

- Код: `app/workers/outbox.py:87,1030`, `app/services/delivery_chains.py:283`, `app/workers/enrollment.py:102`.
- Воспроизведение: настроить склад/текст через Dispatcher → оплатить → зарезервировать → во время get_chat начать профильную проверку. Либо закрыть runtime в первом допуске цикла, затем попробовать второй оплаченный заказ.
- Причина: ValidationError закрытого runtime / WRITES_DISABLED из реального SafeAccount.permit классифицировались как постоянная ошибка. Цикл продолжал забирать следующие сделки после закрытия runtime.
- Исправление: временный проверенный профильный запрет использует существующий CONNECTION_NOT_VERIFIED retry. Для отказа permit требуется положительный NOT_DISPATCHED: started_at отсутствует, нет результата и late evidence. Цикл допуска перестаёт брать новые строки при закрытых воротах. Резерв и исходное право сохраняются.
- RED: 2 failed для preflight; ещё 2 failed на реальном SafeAccount.permit; 1 failed для второго заказа цикла. GREEN: реальные UI/worker сценарии stock/text, один send после восстановления, резерв не освобождён; совмещённый профиль 44 passed.
- Безопасность: started/UNCERTAIN/late, настоящий STOP, изменённая личность/политика не получают право повтора. Денежные виды операций этим исключением не охвачены.

### RT-04 — P1: один товар выключал глобальную политику продвижения

- Код: `app/services/promotion_settings.py:90`.
- Причина: бюджетный отказ evaluate записывал enabled=false всей политики, в том числе при индивидуальном лимите одного товара.
- Исправление: бюджет остаётся ограничением допуска покупки, не уничтожает намерение владельца. Независимый товар продолжает покупать в своих пределах; общий дневной/месячный потолок запрещает расход до смены окна.
- RED/GREEN: `test_other_item_keeps_purchasing_with_exact_approved_tariff[item_limit]`; actual Outbox покупает только второй допустимый товар. Старые ожидания глобального выключения заменены документированным контрактом; исходные no-charge/budget проверки сохранены.
- Риск: max_operations_per_item остаётся настоящим лимитом, а не бесконечно сбрасываемым счётчиком.

### RT-05 — P1: несколько PREMIUM-тарифов делали подтверждённый тариф недоступным

- Код: `app/workers/promotions.py:115`.
- Причина: планировщик требовал ровно один тариф данного типа, игнорируя уже одобренный конкретный quote_id.
- Исправление: выбирается именно одобренный ID текущего типа. Отсутствующий/дублирующийся ID, изменённые цена/период не заменяются произвольным тарифом.
- RED/GREEN: `tests/test_runtime_promotion_isolation.py`: два товара, несколько тарифов, реальные charges; changed/missing/duplicate — ноль покупок.

### RT-06 — P2: смена интервала отменяла неизменённое финансовое разрешение

- Код: `app/services/promotion_settings.py:25`.
- Исправление: разрешение атомарно переносится только при тех же финансовых границах, выборе и включённой политике. Финансовые изменения, STOP/повторное включение, смена области не наследуют разрешение. Уже стоявшая очередь старой ревизии не перезаписывается и безопасно отвергается.
- RED/GREEN: interval change → old queued action rejected без списания → новые разрешённые действия по двум товарам; отдельные отрицательные случаи budget/STOP/selection.
- Остаток: изменение суммы разрешённых расходов остаётся новым финансовым решением владельца.

### RT-07 — P1: исчезновение UNKNOWN после точной сверки снимало ручной бюджетный cap

- Код: `app/services/paid_promotions.py:68`.
- Причина: проверка manual caps зависела от наличия ещё не сверенного released UNKNOWN. После поздней точной квитанции старый расход становился SUCCEEDED, множество UNKNOWN пустело и проверка пропускалась.
- Исправление: факт финансового разрешения сохраняется исторической записью review; его лимиты проверяются и после точной поздней сверки. Расход остаётся в бюджете.
- RED: 1 failed. GREEN: `test_review_caps_survive_exact_later_receipt_reconciliation`, вторая покупка отклонена дневным cap; прежнее списание ровно одно.
- Не изменено: старый UNKNOWN без доказательств не становится SUCCEEDED; автоматика после ручного финансового решения сама не включается.

### RT-08 — P2: readiness timeout терял источник

- Исправление: реальный stage и CHECK_TIMEOUT, прежний bounded deadline. Временная проверка описана как автоматическое ожидание; старый снимок не разрешает платежи.
- RED: 2 failed. GREEN: `tests/test_readiness_refresh.py`, item/Telegram timeout → восстановление → успешная фоновая проверка; профиль 39 passed.
- Остаток: это исправляет классификацию и доказанный recovery, а не обещает устранить произвольный внешний timeout.

### RT-10 — P1: direct Telegram мог выйти мимо Happ после отключения VPN

- Код: `app/telegram/system_tunnel.py`, `app/telegram/transport.py:26,59,212`, `app/gifts/mtproto.py:73,87,149,314`, `app/gifts/auth.py`, `app/__main__.py:127`.
- Причина: direct означает системный маршрут, без привязки к интерфейсу. Одной проверки «VPN сейчас Up» недостаточно: между ней и connect маршрут может измениться.
- Исправление на Windows с текущей установленной Happ: Bot API и личный Telethon используют сокеты с IP_UNICAST_IF/IPV6_UNICAST_IF на happ-xray. Исчезновение/нерабочее состояние интерфейса закрывает admission. Новый интерфейс закрывает старую Bot API session/Telethon connection; используется прежнее восстановление/backoff. Никаких альтернативных прокси и повторов paid RPC.
- Контракт Windows socket option: [Microsoft IP_UNICAST_IF](https://learn.microsoft.com/en-us/windows/win32/winsock/ipproto-ip-socket-options).
- Один общий helper нужен двум существующим транспортам; нового worker/client/схемы/настроек нет. Для обычного direct на хостах без установленной Happ поведение не меняется. Обнаруживается штатная установка Program Files/FlyFrogLLC/Happ; переносная установка/переименование интерфейса потребует проверки, это не универсальный VPN-detector.
- RED: 4 failed (запросы начинались при unavailable tunnel); login route — ещё 1 failed. GREEN: native socket-option отрицательные проверки, реальный Telethon codec/TCP/задачи на локальном peer, lifecycle, bootstrap: 277 passed. Тест с настоящим wait_for_telegram и виртуальными 10/60/300 сек + повторный обрыв: 8 passed.
- Реально на этой Windows без мутаций: happ-xray Up, index=52; unconnected socket getsockopt(IP_UNICAST_IF)=52; Bot API getMe через новый pinned session успешен, 0.265s. Это один read-only замер, не p95.
- НЕ ПРОВЕРЕНО: физическое выключение Happ во время живой сессии, пакетный захват, OS DNS resolver и исходящий IP, видимый Telegram. Interface pinning — доказанная настройка сокета; полного packet-level подтверждения отсутствия любых DNS/OS-утечек нет. Playerok socket/маршрут не менялся.

### RT-11 — P1: точный ACK Gift не использовался для фонового восстановления

- Код: `app/gifts/worker.py:22`, `app/gifts/service.py:900`.
- Воспроизведение: после оплаты сохранить точный ack_message_id, оборвать независимое чтение квитанции, восстановить сеть/перезапустить SQLite. Worker оставлял операцию UNKNOWN до ручного нажатия. Дополнительно старый reconcile подтверждал Gift, но оставлял Outbox UNKNOWN.
- RED: 3 failed на отсутствии фоновой сверки; отдельное воспроизведение старого reconcile из committed HEAD в изолированном pytest-процессе — 2 failed на несогласованности Outbox, без замены файлов проекта.
- Исправление: существующий GiftWorker читает максимум одну точно коррелированную квитанцию за цикл, 15 секунд на чтение, существующий retry_at ограничивает повтор чтения 60 секундами. После отмены чтения обязательно дожидаемся освобождения старого транспорта; 15 секунд не объявляются жёсткой гарантией завершения всего cleanup. MESSAGE_ID + сохранённый ACK + начатый исходный intent обязательны. Сам платёж не отправляется повторно и UNKNOWN не возвращается в очередь исполнения.
- GiftService.reconcile сверяет актуальное состояние, администратора, шаг и Outbox после чтения. Одна транзакция подтверждает Outbox/шаг/пакет, сохраняет предыдущую причину в receipt result. При concurrent close/отмене/refund/late evidence не выдаёт новое право. STOP и настройки расходов не меняются. Следующие позиции пакета и автозавершение используют прежний Outbox и исходное разрешение.
- GREEN: 14 новых тестов реального Dispatcher setup и production worker: restore/restart, ровно один платёж, отсутствие ACK/квитанции, другой получатель/подарок/плательщик, late conflict, STOP, rollback, частичный пакет, разрешённое завершение, отмена и concurrent close. Широкий профиль Gifts/bundles/safety/independent lanes — 75 passed; итоговый новый профиль — 14 passed / 18.13s.
- Граница: без сохранённого ID, при конфликте, неизвестном возврате или late evidence карантин сохраняется. Старые REFERENCE-операции не переводятся в этот автоматический путь; существующая явная сверка сохраняется. Новая логика не делает неизвестный платёж безопасным для повторения.

### RT-12 — P1: половинчатое TCP-соединение Telethon переживало timeout RPC

- Код: `app/gifts/mtproto.py`, `_read`, `_read_rpc`, `_retire`, `pay`.
- Причина: отмена ожидающего RPC не обязана сбрасывать Telethon.is_connected. После VPN-обрыва sender сохранял me/client и мог снова обращаться к старому TCP вместо нового подключения.
- RED: два теста оставили активные transport loops и cached client после отменённого balance RPC и после потерянного ответа возможного платежа (2 failed / 1.39s).
- Исправление: транспортный сбой/timeout/cancel чтения дожидается disconnect ровно того соединения, на котором начался запрос, под прежним sender.lock. Поздняя ошибка старого чтения не закрывает новый клиент. При сбое paid RPC старый транспорт также закрывается под существующей блокировкой; результат платежа остаётся UNKNOWN, RPC не повторяется. Cleanup не является разрешением на новый платёж.
- GREEN: совмещённый профиль актуальных ACK/Happ/Gift safety/bundles/lifecycle — 87 passed / 43.18s; финальные lifecycle-тесты — 7 passed / 1.12s, включая позднюю ошибку старого соединения после успешного нового подключения.
- Граница: реальный сетевой timeout остаётся возможным. Новый код восстанавливает владение и освобождение соединения; он не угадывает исход RPC, который мог дойти до Telegram.

Простой, восстановление соединения и новый баланс сами по себе не доказывают, что прежняя покупка не состоялась.
