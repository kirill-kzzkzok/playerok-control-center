# Playerok Control Center

Личные Telegram-подарки: [настройка, ограничения и контролируемая live-проверка](README_GIFTS.md).
Покупки Stars и автовозвраты по умолчанию выключены; авторизация личного аккаунта
выполняется только локально, отдельно от Telegram Bot API.

Локальная Telegram-панель магазина на Python 3.12 / aiogram 3.
Проект в разработке: полный набор критериев PROJECT_SPEC.md пока не принят.
Не включайте автоматическую выдачу или денежные действия, опираясь только на зелёные unit-тесты.

## Установка и запуск на Windows

1. Установить Python 3.12 и запустить `install.bat`.
2. Заполнить локальный `.env` по `.env.example`. В текущей рабочей папке секреты уже перенесены из приватной спецификации.
3. Запустить `start.bat` или `.venv\Scripts\python.exe -m app`.
4. Открыть бота и отправить `/start`. По прямому указанию владельца в текущем `.env` включён `FIRST_START_CLAIM=true`: первый `/start` **в личном чате** атомарно закрепляет владельца в БД. После этого остальные пользователи не получают доступ. Для новых установок безопасное значение шаблона — `false`; предпочтителен явный `OWNER_IDS`.

По умолчанию Telegram Bot API и личный MTProto используют отдельный localVPN SOCKS5
`127.0.0.1:1080`. `start.bat` поднимает и проверяет собственный Playerok-сервис;
Chrome/Codex и их туннели не требуются. [Настройка, сборка и диагностика](LOCALVPN_INTEGRATION.md).
При отказе SOCKS прямого fallback нет. Старый Bot API Worker доступен явным
`TELEGRAM_TRANSPORT=worker` с HTTPS `TELEGRAM_API_PROXY_URL` без `/botTOKEN`.
Polling, callback, фото и скачивание подтверждены отдельной owner-only живой проверкой.

Проверка подключений: `.venv\Scripts\python.exe -m app.diagnostics`.
Тесты: `.venv\Scripts\python.exe -m pytest -q`.
Офлайн-проверка установки: `.venv\Scripts\python.exe -m app.selfcheck` (без .env, сети и рабочей БД).
Статическая проверка: `.venv\Scripts\python.exe -m ruff check app tests`.

## Четыре пользовательских сценария перед первой складской выдачей

- **Склад:** «Мои товары» → лот → «Склад». Здесь четыре остатка и номера единиц без
  содержимого. «Загрузить запас» принимает строки и показывает новые/пустые/повторные
  значения перед локальным сохранением. Известные выданные/карантинные единицы не
  используются заново. Пополнение не снимает защитную остановку: возобновление отдельно.
- **Из мастера в склад:** в мастере выбрать «Уникальный запас» и ввести значения.
  Полное превью показывает количество, не секреты. После успешного создания из результата
  открыть склад и подтвердить однократный перенос. Новая политика stock сохраняется
  выключенной; существующая политика не перезаписывается. Исполнение включается отдельно.
- **Статус:** лот, заказ и политика показывают общий снимок «Работает / Не готово /
  Остановлено», режим, остатки, глобальные разрешения и синхронизацию. Экран не включает
  ни одного разрешения. Для stock после последней единицы требуется явное возобновление.
- **Результаты:** «Ещё → Инструменты → История и результаты». QUEUED не означает успеха;
  после завершения приходит отдельное сообщение владельцу с подтверждёнными полями
  ответа сервера и переходами к объекту. PENDING_APPROVAL не считается активной
  публикацией; актуальное состояние перечитывается при открытии карточки лота.
  Потерянный Telegram ACK не повторяется: результат остаётся доступным в списке.
- **После выдачи:** «Выдано — подтвердить» показывает PAID-заказы с подтверждённой
  отправкой (и DELIVERED для склада). Проверить результат → прежний Fulfillment с
  личным подтверждением владельца. Допустимость заранее разрешённого автозавершения определяется конкретной политикой и серверными требованиями; редизайн его не включает.
- **Превью:** игра, категория, способ передачи, характеристики, полный текст,
  фото с просмотром, цена/финансовые оценки и подготовленный запас. Изменение отдельного
  поля возвращает к превью, сохраняя независимые данные. Изменение категории/способа
  требует повторной проверки соответствующих полей/условий. Скидка устанавливается
  отдельным действием после создания серверного черновика; фиктивной базовой цены нет.

Новые экраны проверены локальными интеграциями, включая настоящий aiogram Dispatcher,
FSM restart и сбои. Реальная выдача/сообщения покупателям ещё не приняты. Подтверждённый
предыдущий live-цикл управления одним лотом сохранён в LIVE_ACCEPTANCE_20261030.json.
Миграции019/020 применяются при штатном запуске с существующим механизмом Store.

## Возможности текущей реализации

- Inline-меню, проверка владельца на message/callback, HTML-экранирование.
- Реальные профиль, товары, категории, способы получения, схема полей и сообщения через PlayerokAPI.
- Мастер локального черновика: выбор игры, категории, полей, описание, фотографии, цена, параметры выдачи, превью; FSM переживает перезапуск.
- Серверные операции создания, редактирования, удаления, бесплатной публикации и ответа через сохраняемую очередь. В штатном `.env` записи выключены. Mock-тесты не доказывают работу этих операций на реальном сервере.
- SQLite WAL, транзакции, уникальные ключи операций, leasing, UNCERTAIN, атомарный запас и резервирование.
- API-сверка истории с пагинацией, уведомления с дедупликацией и сохранением неизвестного результата отправки.
- Decimal-калькулятор с происхождением ставок, отдельными расходами; графики по локальной истории, карточка профиля с реальным рейтингом.
- Продвижение: расчёт cooldown, повторной проверки позиции и лимитов в dry-run. Реального списания модуль не выполняет.

## Ограничения, которые ещё предстоит закрыть

Полная приёмка мастера на Telegram, загрузка фотографий на Playerok, создание/редактирование/публикация тестового лота, установка реальной скидки, точные комиссии вывода, фильтры всех разделов, настройка реальной автоматизации и сверка успешности всех типов UNCERTAIN ещё не подтверждены/не завершены. Замена фотографий существующего лота реализована с повторной проверкой актуальных ID и подтверждением, проверена на mock API; live-записи в рабочие товары не выполнялись.
Контролируемый технический черновик был отклонён Playerok по правилам товара; обход этого ограничения не выполняется. Поиск по уникальному имени не нашёл созданного объекта. Бесплатная публикация не проверялась.
Автоподтверждение нельзя путать с SENT продавца. Автовывод не реализован. PREMIUM и платное автоподнятие требуют отдельных подтверждений тарифов и бюджета; платежи за Telegram Gifts имеют собственные разрешения.

Для будущего включения обычных записей существует `PLAYEROK_WRITES_ENABLED=true`; это не разрешает оплату PREMIUM или поднятий. До завершения live-приёмки оставляйте `false`.

Условия категории и инструкции продавцу показываются полностью, постранично. Принятие соглашений — отдельное действие с явным подтверждением владельца и сохраняемой очередью; оно не создаёт товар и не покупает продвижение. При выключенных записях соглашения на сервере не принимаются. Изменившиеся условия нужно прочитать повторно.

Атрибуты и приватные данные существующего товара редактируются через отдельный сохраняемый мастер: перед отправкой проверяются владелец, разрешение редактирования и исходный снимок полей. Параллельные изменения блокируются; приватные значения не выводятся в публичном превью.

Механизм настоящей скидки подтверждён публичным кодом редактора: цена продажи `price` меняется относительно имеющейся `rawPrice`; обычный продавец не задаёт произвольную старую цену. Есть отдельное превью/подтверждение скидки и её снятия, с проверкой минимум 5% и актуальных цен. Реальная запись скидки не выполнялась; проверка пока изолированная. Для нового товара скидка доступна после создания серверного черновика.

Мастер поддерживает постраничные варианты и множественный выбор, предпросмотр/замену/удаление отдельного фото, а для категорий без ITEM_DATA — приватные данные покупателю в поле `comment`. Название и описание проверяются по текущим ограничениям официальной формы (10–72 и 10–2048 символов); стандартная цена — 90–100000 ₽, для подтверждённой роли OFFICIAL_SELLER — от 10 ₽. Это проверка формы, а не гарантия принятия товара сервером.

Очистка `data/uploads` выполняется ежечасно: сохраняются файлы активных черновиков, FSM и незавершённых/UNCERTAIN операций. Успешно обработанные загрузки и старые бесхозные файлы удаляются; при повреждении списка ссылок очистка прекращается с диагностикой.

## Данные и эксплуатация

- Конфигурация: `.env` (приватная, вне Git).
- Приватная спецификация: `PROJECT_SPEC.md` (вне Git).
- База: `data/control_center.sqlite3`; содержит сообщения и данные запаса, хранить как секрет.
- Загрузки: `data/uploads/`.
- Резервные копии: `data/backups/` — SQLite backup API на запуске и по кнопке настроек.
- Логи с ротацией: `logs/control_center.log`.
- Локальные свидетельства live-проверок: `data/live_*.json`, `data/controlled_live_test.json`.

Остановка — Ctrl+C. Два экземпляра для одной БД блокируются OS-lock.
При неизвестном результате внешнего запроса операция получает UNCERTAIN и автоматически не повторяется. Сначала сверяйте реальное состояние сервера.

Восстановление вручную: остановить бот, сохранить текущую БД и её `-wal`/`-shm`, выбрать проверенную резервную копию и заменить файл основной БД при полностью остановленном процессе. Не восстанавливайте старый запас поверх новых выдач без сверки: это может повторно сделать выданные коды доступными. Автоматическое восстановление поверх рабочих данных не выполняется.

Для круглосуточной работы компьютер должен оставаться включённым с интернетом. Автозапуск можно настроить в Планировщике Windows с рабочей папкой проекта; бот не работает при выключенном компьютере.

Прогресс: `PROGRESS.md`; архитектура: `ARCHITECTURE.md`; исследование: `PLAYEROK_RESEARCH.md`; доказательства проверок: `TEST_REPORT.md`.
Переиспользованный PlayerokAPI распространяется по MIT; сохранён `LICENSE.PlayerokAPI`.


## Финансовый калькулятор

В настройках откройте «Условия вывода», выберите доступный метод и введите предполагаемую
сумму. Это калькулятор: реквизиты не запрашиваются, деньги не выводятся. Выбранный метод
сохранится для вашего Telegram ID и подставится в новые черновики. Условия можно обновить;
старый курс/тариф не считается актуальным.

В превью черновика кнопка «Вывод и себестоимость» позволяет выбрать метод для этого
товара и ввести стоимость одной единицы. Отдельная финансовая карточка есть у существующих
товаров. Для серверного черновика можно включить стоимость будущего размещения, включая
PREMIUM, полученную из API. Это только preview: платное действие не выполняется.

Комиссии продажи/вывода, размещение и себестоимость разделены. Прибыль появляется только
при наличии всех нужных составляющих и себестоимости; иначе показываются известные суммы
и причины, почему итог недоступен. Вывод суммы одной продажи может быть ниже минимального
лимита — в таком случае бот не обещает поступление. Минимальная комиссия при объединённом
выводе нескольких продаж распределяется иначе.

USDT включает доплату 1 USDT по полученному курсу; результат показан в рублёвом эквиваленте.
Фактическое округление settlement ещё не проверено, поэтому расчёты явно помечены оценками.
Время источников показывается по Москве. История оценок хранится в financial_quotes,
отдельно от подтверждённых расходов/поступлений. Это не история реальных выводов.


## Сверка и история сообщений

Каждому диалогу Playerok соответствует одна обновляемая карточка Telegram.
Новые входящие и подтверждённые ответы обновляют её; полная доступная история
остаётся в SQLite. В карточке только «Ответить» и «Закрыть». Ответ текстом поступает
в прежний Outbox без дополнительного подтверждения; /cancel отменяет ввод.
Закрытие сохраняет переписку и не отмечает сообщения прочитанными на Playerok.
Новое сообщение покупателя открывает карточку снова. Если исход отправки неизвестен,
повтор заблокирован до достоверной сверки. Платёжные квитанции и критические
уведомления сохраняются отдельно. Старые кнопки шаблонов больше не отправляют ответы.

Сверка загружает историю частями, сохраняет курсоры и продолжает после перезапуска.
BACKFILL означает продолжающуюся первую загрузку; ERROR — ошибку одного или нескольких
потоков. Один цикл ручной сверки не означает, что вся история уже загружена. Большое
число диалогов увеличивает задержку обнаружения. WebSocket ускоряет сверку, но не заменяет её.


Быстрые ответы доступны в настройках и при нажатии «Ответить»: можно сохранить
собственные шаблоны, изменить или удалить их. Перед отправкой всегда показывается
полный текст с отдельной кнопкой подтверждения. Введённый вручную текст работает так же.
Шаблоны принадлежат вашему Telegram ID и сохраняются после перезапуска.

Исходные уведомления не заменяются экраном ответа. Для ответа из уведомления бот
сохраняет связь и обновляет его результатом из очереди операций. UNCERTAIN означает,
что результат неизвестен: перед любым повтором нужна проверка на Playerok. При сбое
обновления Telegram повторяется только редактирование уведомления, не сообщение покупателю.
Эти сценарии пока проверены в тестовой среде; live-отправка покупателям не выполнялась.


Фото в диалоге открываются кнопкой «Открыть фотографии». Бот проверяет, что сообщение
ещё доступно, и загружает изображение с ограничением размера. Если страница сдвинулась,
обновите диалог. При открытии прочитанность автоматически не меняется.

Для ответа фото откройте «Ответить» и пришлите одну фотографию или файл JPEG/PNG/WEBP
с необязательной подписью. Бот покажет preview и отдельную кнопку подтверждения.
Альбомы пока не объединяются: одно фото соответствует одному подтверждаемому ответу.
В штатном read-only режиме реальная загрузка/отправка заблокирована. Контракт сверён
с текущим веб-клиентом и покрыт mock-тестами; live-фото покупателям не отправлялись.


## Неопределённые операции

В диагностике откройте «Неопределённые операции» или «История операций». При UNCERTAIN
бот не повторяет отправку автоматически. Для ответа/выдачи можно указать ID сообщения
из истории диалога: бот сопоставит отправителя, текст, время и число вложений. Фото
нужно лично сверить на Playerok. Проверка ограничена 480 сообщениями; отсутствие
совпадения не доказывает, что отправки не было. Для прочитанности проверяется текущее
состояние чата. Решение требует комментария и отдельного подтверждения.

Можно остановить операцию без повтора, оставив внешний результат неизвестным. Резерв
сохранится в карантине, фото — для сверки; новых отправок не будет. Ручное подтверждение
выдачи меняет только локальный учёт и не завершает сделку на Playerok. Для прочих типов
операций успешность этим интерфейсом не устанавливается; доступна остановка без повтора.
Ручное решение и исходная ошибка остаются в журнале. Не вводите секреты в комментарии.


WebSocket включён по умолчанию; PLAYEROK_REALTIME_ENABLED=false отключает его,
оставляя периодическую сверку API. В диагностике видны состояние подключения и очередь
адресных сверок. После обрыва бот переподключается с задержкой и перечитывает данные.
Завершённый catchup cycle не означает полной загрузки истории: проверяйте BACKFILL.
В реальной проверке подтверждены handshake и heartbeat; новые события покупателей
не создавались, поэтому полный live-поток событий ещё не принят.


## Заказы и локальный запас

В заказах доступны поиск по ID/товару/покупателю, фильтры, подробная карточка и история.
Локальная проблема и заметка видны только в панели: это не жалоба на Playerok.
При недоступном API карточка использует явно обозначенный кеш; выдача из него отключена.

У оплаченного заказа можно локально добавить уникальные коды по строкам и отдельно
подтвердить выдачу одной единицы. Записи Playerok в штатной конфигурации выключены.
Выдача перед отправкой проверяет актуальную продажу и чат; timeout оставляет карантин.
Код никогда не возвращается в доступный запас автоматически. Добавление кодов само
по себе не отправляет их покупателю и не включает автоматизацию.

Отправленный код не означает отметку SENT или подтверждение покупки. Кнопка «Я выполнил заказ» открывает checklist и, если требуется, форму отчёта.
Состояние сделки и требования проверяются повторно перед записью.
Реальные выдачи и изменения статуса этой контрольной точкой не проверены.


Отметка выполнения требует личного подтверждения передачи товара и отдельного подтверждения.
Для официального продавца могут понадобиться данные исполнителя и поставщика, номер
заказа и стоимость. Это отчёт, не оплата. При недоступном списке поставщиков нельзя
подставить произвольного поставщика. Timeout записи не вызывает автоматического повтора.
В штатном read-only режиме отправка заблокирована. Live-изменение статуса/отправка отчёта
не проверялись: данные ветки пока приняты только в изолированных тестах.


## Политики выдачи

В карточке товара откройте «Политика выдачи · dry-run». Можно сохранить режим,
постоянный текст, приветствие, сообщение после выдачи и запрос отметки SENT.
Переключатель задаёт желаемое включение; автоматическое исполнение пока выключено,
что явно показано на экране. Сохранение настройки не отправляет сообщения и не меняет лот.

После сохранения можно выбрать локально известный оплаченный заказ для dry-run: бот
перечитает его и чат через API, покажет причины запрета и предполагаемые шаги. Код
не резервируется, отправки не создаются. «Выключить все политики выдачи» доступно
в общем разделе автоматики; ранее подтверждённые ручные операции проверяйте отдельно.


Цепочки приветствие → выдача → сообщение после выдачи можно зарегистрировать для
отдельного заказа после dry-run и подтверждения. Для исполнения нужны оба локальных
флага PLAYEROK_WRITES_ENABLED и PLAYEROK_AUTOMATION_ENABLED; штатно они выключены.
Старые оплаченные заказы автоматически не включаются. Следующий шаг отправляется только
после подтверждения предыдущего; неизвестный результат останавливает продолжение.
Изменение политики останавливает её текущие цепочки. Отметка SENT остаётся отдельным
подтверждаемым действием; успешная отправка кода не означает подтверждение покупки.
Цепочки проверены изолированно, live-отправок покупателям не выполнялось.


## Продвижение: настройки и проверка без покупки

Откройте «Автоматизация → Продвижение · dry-run». Доступны интервалы и пороги,
ночное время МСК, cooldown, лимиты расходов и выбор всех подходящих/отдельных лотов.
Конкретный лот можно включить или исключить в его карточке продвижения. Изменения
нужно сохранить; параллельный старый редактор не перезапишет новую версию.

Проверка читает реальную цену размещения, сравнивает интервалы и лимиты. Для режима
позиции нужны два чтения с интервалом; быстрый повтор кнопки недостаточен. Позиция
приоритетного размещения не доказывает общее место товара в поиске. При превышении
лимита политика локально выключается. Dry-run ничего не покупает и не записывает
оценку как расход. Платное исполнение подключается отдельным подтверждением тарифа и расписания (см. раздел PREMIUM ниже); история показывает сохранённые
записи расходов, если они есть. Эти сценарии проверены изолированно, без реальных поднятий.


Планировщик продвижения периодически выполняет только dry-run для включённой политики.
Он сохраняет очередь и курсор каталога, учитывает ошибки и продолжает после перезапуска.
При выключенной политике запросов нет. Для каждого лота проверяется стоимость текущего
класса размещения; неоднозначная цена не означает автоматический выбор PREMIUM.
Состояние видно в диагностике. При выключении политики из-за лимита приходит локальное
уведомление с указанием, что списания не было. Реальные поднятия не выполняются.


В разделе автоматики доступны «Все политики выдачи» и «Цепочки выдачи»; в продвижении —
выбранные/исключённые лоты, очередь проверок, история dry-run и расходов. Списки имеют
страницы. Карточка цепочки содержит операции шагов без показа данных выдачи.

Остановить цепочку можно после отдельного подтверждения. Уже отправленное не отзывается;
запрос в полёте может завершиться и сохранит настоящий результат. Зарезервированный код
остаётся в карантине. Если цепочка изменилась после открытия подтверждения, проверьте
её снова. Неизвестные цепочки автоматически не возобновляются.

В очереди продвижения можно локально запланировать новую dry-run проверку. Это не
покупка и не включение политики; выполняющийся lease не сбрасывается. Исторический
результат dry-run не подтверждает сегодняшние условия или факт списания.


## Автовыдача будущим продажам

В политике товара есть отдельный переключатель «Будущие заказы автоматически».
Он выключен по умолчанию. Для enabled-политики сохранение такого выбора требует
дополнительного подтверждения; реальное исполнение требует также двух глобальных
флагов PLAYEROK_WRITES_ENABLED и PLAYEROK_AUTOMATION_ENABLED. Штатно они выключены.

Автоматически включаются только продажи с подтверждённым серверным временем создания
после сохранения текущей версии политики. Старые, неизвестные по времени и созданные
до новой версии заказы не получают код автоматически. После изменения политики
начинается новый отсчёт. Пропуски и блокировки видны в «Регистрация будущих заказов».
Сетевые ошибки чтения имеют задержку; неопределённые отправки не повторяются.

При окончании запаса новые автоматические регистрации блокируются. После пополнения
проверьте и сохраните включённую политику заново. Отметка SENT остаётся отдельным
подтверждаемым workflow; получение кода не означает buyer confirmation. Весь сценарий
пока проверен изолированно, реальным покупателям тестовые выдачи не выполнялись.

## Профиль и аналитика

Профиль показывает доступный баланс и сумму к выводу раздельно, статистику объявлений,
продаж и покупок из текущего API-ответа. В статистике доступны пять периодов, несколько
графиков, лучшие товары и категории. Временные графики — плавные линии: точки показывают
исходные значения, линия между ними — визуальное сглаживание, не прогноз.

Статусы заказов текущие, период определяется серверной датой создания. Отсутствующие
даты догружаются ограниченными read-only запросами деталей с сохранением очереди.
Счётчики неполноты/покрытия доступны в «Подробности». Выручка до комиссий не является
поступлениями или прибылью. Расходы продвижения и другие расходы показаны отдельно;
разделение всех комиссий и полная финансовая приёмка ещё не завершены. После обновления
локального header 30.10 viewer/user/transactions вернули HTTP 200. Загружены 462 транзакции
и серверные даты всех 217 сохранённых заказов; полнота относительно всей истории API
этим не гарантируется.

В статистике кнопка «Поступления и расходы по транзакциям» показывает отдельную
историю подтверждённых движений баланса по дате завершения транзакции. Продажи,
пополнения, списания выплат, PREMIUM и прочие приоритеты разделены. Загрузка выполняется
частями и продолжается после перезапуска; ошибки/покрытие видны в панели. Суммы без
серверной даты завершения или в другой валюте не подставляются в рублёвый итог.
Сумма списания выплаты и явное поле API «к получению» показаны отдельно; деньги в банке
этим не подтверждаются. Комиссии с неясными единицами и историческая прибыль не выдумываются.

В карточке заказа кнопка «Себестоимость и прибыль» ведёт в исторический учёт. Себестоимость
всего заказа и остальные расходы вводятся явно (в том числе 0), отдельно от текущих
расчётов товара. Подтверждённый PREMIUM/удержания выплаты можно распределить между заказами:
доли не превысят источник. Для выплаты используется только разница списания и явной суммы
к получению из API. Это не повторное вычитание всей выплаты.

После заполнения проверьте полноту расходов. При одном однозначном подтверждённом SELL-
зачислении бот покажет прибыль по вашему учёту; неизвестные данные блокируют итог. Смена
исходных сумм требует повторной проверки. Не включайте распределённые расходы повторно в
прочие расходы. Раздел статистики показывает результат только по проверенным заказам и
число исключённых; это не заявление о полной прибыли магазина или банковской выписке.

Диагностика Playerok без записей: `.venv/Scripts/python -m app.auth_diagnostics`.
Она один раз читает viewer/user и страницу транзакций, сохраняет точный HTTP-статус,
endpoint, операцию, тип ответа и обезличенную причину ошибки в
`data/playerok_auth_diagnostics.json`. Успешные тела профиля/транзакций не сохраняются;
cookies и токены скрываются. Challenge не решается и не повторяется автоматически.

Если операция получила поздний ответ после истечения lease, его ID виден в карточке
операции. Это свидетельство для сверки: основной статус и карантин не меняются, повтор
не разрешается. Остановка автоматики проверяется перед HTTP-отправкой, включая ожидание
API-lock и rate limit; она не может отозвать уже переданный серверу запрос.
Карта проверок и оставшихся ограничений: `ACCEPTANCE.md`.

В «Настройки → Уведомления» можно отдельно включить сообщения, изменения заказов,
проблемы, пустой запас, остановку продвижения и блокировку выдачи. Настройка сохраняется
для вашего Telegram ID. Пропущенные при отключении события не отправляются задним числом
после включения. Уже отправленные карточки продолжают показывать результат операций.
Предупреждение о неопределённом результате обязательно и не отключается. Эти настройки
не включают и не выключают саму выдачу/продвижение. Подключения показывают сохранённые
состояния; для текущего сетевого диагноза используйте локальную auth_diagnostics команду.

«Черновики» показывает всю локальную историю по страницам, с поиском названия/ID и
фильтрами состояний. Старые записи больше не скрыты лимитом 30. Поиск не включает
данные выдачи и описание. Статус записи — локальный; актуальный статус объявления
проверяется отдельно в его серверной карточке. Кнопка «Черновики» сбрасывает поиск.

Заказы сортируются по серверной дате создания, с приведением часового пояса к UTC.
Время первого локального импорта не считается датой продажи. Заказы без подтверждённой
серверной даты остаются доступными в конце списка и не попадают в периоды статистики.

«Настройки → Очистка интерфейса» показывает превью до 20 старых карточек панели. Удаление
требует отдельного подтверждения и необратимо. Сохраняются текущая карточка, уведомления,
ваши сообщения и вся локальная история/запас/Playerok-данные. Учитываются только сообщения,
отправленные после включения новой системы учёта; старые ID бот не угадывает.
Сообщения должны быть без изменений 5 минут и не старше 47 часов (с запасом к
[ограничению Telegram 48 часов](https://core.telegram.org/bots/api#deletemessage)).
При неизвестном результате автоматического повтора нет; журнал итогов виден в панели.
Live-удаление ещё не проверялось, тесты выполнены на mock Telegram API.

В «Настройки → Правила автоответов» можно задать точную фразу и готовый текст. Правило
создаётся выключенным; включение для будущих сообщений подтверждается отдельно после
просмотра полного ответа. Регистр/пробелы нормализуются; вложения и служебные сообщения
не вызывают автоответ. Нужны оба локальных флага writes и automation и завершённая
сверка; сохранение/включение правила не меняет эти флаги.

Ответы ограничены паузой в чате и суточным лимитом попыток по Москве. История до включения
не обрабатывается; сообщение должно быть свежим. Если диалог уже продолжился, есть другая
очередь ответа/выдачи или источник изменился, автоответ блокируется. Неизвестный результат
отправки не повторяется. Журнал доступен в панели. Не используйте автоответ для уникальных
кодов: запас выдаётся отдельным механизмом. Live-автоответы ещё не проверялись.

## Проверка установленного пакета

`python -m app.selfcheck --output data/installation_check.json` импортирует модули,
проверяет упакованные SQL-миграции и сертификат, создаёт временную SQLite БД, проверяет
backup/reopen и PNG профиля/графика. Рабочие данные и секреты не читаются. Ненулевой код
выхода означает ошибку установки; это не проверка авторизации и не live-приёмка магазина.
После установки пакета также доступны команды `pcc-check` и `pcc`.

Сборка wheel: `python -m pip wheel --no-deps --wheel-dir data/dist .`.
Не отключайте build isolation без отдельно установленных build dependencies. Зависимости
для запуска фиксированы в requirements.lock.txt. Успешная проверка wheel с текущими
зависимостями не гарантирует работу на всех версиях Python/Windows/Linux.

Приватный удалённый репозиторий:
[GitHub — Playerok Control Center](https://github.com/kirill-kzzkzok/playerok-control-center).
Приватные .env/PROJECT_SPEC.md, рабочая БД, коды, логи и build output не публикуются.

В статистике «Сверенные комиссии продажи» показываются только однозначно связанные
CONFIRMED продажи, где цена заказа − transaction.fee точно равна зачислению в RUB.
Несогласованные/неизвестные суммы исключаются с видимым счётчиком. Комиссия уже находится
в разнице цены и зачисления и не вычитается повторно из прибыли. Период этого раздела
определяется завершением зачисления, а не созданием заказа.

Для выплат показывается удержание лишь при явной пригодной сумме «к получению» в API.
Нулевое/отсутствующее поле при положительном списании не считается доказанной нулевой
комиссией или полной потерей суммы. Отсутствующие исторические комиссии не заменяются
современным тарифом. Эти цифры сами по себе не подтверждают поступление денег в банк.


Фоновые циклы контролируются Supervisor: неожиданный выход вызывает перезапуск с
задержкой 5–300 секунд и обязательное уведомление владельцу. В диагностике видны
последнее сохранённое состояние и число сбоев. RUNNING не подтверждает исправность API;
это не watchdog зависших запросов. Неопределённые отправки не повторяются: проверяйте
их отдельно в истории операций. Отмена и штатное завершение не запускают новый цикл.


Каждая база привязывается к одному аккаунту Playerok после успешной авторизации.
Cookies другого магазина не переназначают старые заказы, запас, финансы и очередь.
Для другого аккаунта укажите отдельный `DATABASE_PATH` в локальном `.env`.
При конфликте принадлежности записи и синхронизация блокируются; не удаляйте привязку
для обхода проверки. Старые данные без установленного аккаунта требуют отдельной проверки.
При старте выполняется свежая проверка аккаунта; сохранённый успешный статус её не заменяет.
При ошибке доступны безопасные локальные экраны и диагностика, но записи, покупки
подарков и автовыдача заблокированы независимо от настроенных разрешений.
В «👤 Профиль» есть статус, аккаунт последней успешной проверки, время успеха/попытки
и кнопка «🔄 Проверить соединение». Сеть/timeout показываются жёлтым, подтверждённая
ошибка авторизации или конфликт аккаунтов — красным. Проверки сериализованы, между
завершением проверки и следующим запросом требуется5 секунд. Успешная проверка
снимает блокировку соединения только в пределах ранее настроенных разрешений.


При штатной остановке бот ждёт завершения активных синхронных API-вызовов перед
закрытием клиента и БД. Отмена ещё не начатой отправки проверяется также перед HTTP.
Запрос в полёте может завершиться после отмены: операция остаётся UNCERTAIN, а поздний
ID ответа сохраняется для сверки без автоматического повтора или признания успехом.
HTTPX использует таймауты сетевой активности; время штатной остановки зависит от
завершения исполняющегося вызова и не имеет нового жёсткого общего лимита.


С начала штатной остановки новые обращения к Playerok отклоняются кодом `API_CLOSING`.
Очередь ожидания API также проверяется перед входом в метод, а отправки — ещё раз после
rate limit перед HTTP. Это защищает от позднего обработчика Telegram, который иначе
мог бы обратиться к уже закрытому клиенту. Для новой сессии запускается новый процесс.


Старый технический live-test снят с исполнения после отклонения объявления Playerok.
Команда `.venv/Scripts/python -m app.live_test` теперь **только локально читает**
`data/controlled_live_test.json` и печатает краткие исторические признаки без секретов.
`--journal ПУТЬ` позволяет проверить другой локальный файл. Файл не меняется; отсутствие
или повреждение журнала не включает создание или удаление лота. Код возврата0 — журнал
прочитан либо отсутствует,2 — ошибка чтения/формата/размера. Это не подтверждение
текущего состояния лота на сервере. Для live-приёмки нужен отдельно разрешённый сценарий
с реальным допустимым товаром; старое техническое объявление не создаётся повторно.


В статистике «Топ по заказам» ранжирует товары по числу оплаченных заказов, а «Топ по
выручке» — по известной сумме до комиссий. Неизвестная цена не исключает заказ из
количественного топа: число таких сумм видно отдельно. Если известных сумм нет, экран
не показывает выдуманный ноль. Группировка товаров идёт по серверному ID лота;
одинаковые названия не объединяются в SKU автоматически. Для категорий доступны оба
вида, с явной группировкой по сохранённому названию. Периоды и текущие статусы те же,
что у общей статистики; возвраты в оплаченный топ не входят, полнота истории не обещается.


Списки товаров и диалогов сохраняют продолжение в SQLite FSM. Кнопка «Далее» относится
к конкретной странице; после смены фильтра, перехода или завершения списка старая
кнопка просит открыть список заново. Неполный ответ сервера не стирает курсор для
повторной read-only загрузки; зацикленный курсор отклоняется. Пустая страница с
продолжением не считается концом истории. Один обход ограничен1000 страницами.


В «Моих товарах → Фильтры» можно сочетать статус, подстроку названия, диапазон цены,
категорию по ID и PREMIUM/обычный приоритет. Диапазон вводится как `100 500`;
`- 500` оставляет нижнюю границу открытой, `- -` снимает диапазон. Для названия и
категории `-` очищает значение. Категория запрашивается на сервере в вашем аккаунте;
цена, название и приоритет проверяются на каждой полученной странице. Экран показывает
число совпадений на странице и сохраняет «Далее» даже при нуле совпадений: это не
глобальный поиск по ещё не загруженным лотам. Неизвестные цена/приоритет не подходят под
соответствующее ограничение. Категория пока вводится ID, выбора по названию ещё нет.


Кнопка «Категория» в фильтрах теперь позволяет ввести название игры и выбрать её
категорию из списка Playerok. Страницы и выбор сохраняются при перезапуске; перед
применением принадлежность категории игре проверяется повторно. Другие фильтры
сохраняются. Ручной ввод ID или снятие категории остаётся отдельной кнопкой.
Предыдущее ограничение «только ввод ID» этим этапом снято; остальные фильтры всё ещё
проверяются на каждой странице лотов, а не через неподтверждённый глобальный поиск.


В карточке лота «Просмотреть фото» открывает галерею. Перед каждым фото заново проверяются
владение, запрет показа и ID вложения; скрытые/удалённые фото не скачиваются. Счётчики
просмотров и сделок показываются только при наличии пригодных полей API; число сделок
не считается доказанным числом завершённых продаж. Позиция относится к приоритету лота.


Результат публикации подтверждается только явным статусом размещения/модерации и ID
лота. HTTP200 без статуса не считается успехом. Удаление требует ответ с ID и датой
удаления; boolean/пустой ответ также не считается доказательством. Неподтверждённый
исход сохраняется как UNCERTAIN без автоматического повтора — проверьте лот на Playerok.
Ожидание модерации не означает, что объявление уже активно.


Сохранение названия, описания и цены подтверждается по возвращённым полям API, а не
одному ID. Замена фото проверяет число и уникальные новые ID вложений. Неполный ответ
оставляет UNCERTAIN без повторной записи; локальные фото сохраняются для сверки.
Эта проверка набора вложений не доказывает совпадение байтов изображения без хеша API.


## Автоматическое принятие условий продавца

`PLAYEROK_AUTO_ACCEPT_AGREEMENTS=true` — отдельное постоянное разрешение принять
соглашения продавца выбранной категории и способа передачи, включая новые версии.
Для новых установок значение `false`. Для текущего локального магазина включено
по распоряжению владельца; `PLAYEROK_WRITES_ENABLED` и денежные флаги остаются `false`.
После изменения настройки перезапустите бот.

Выберите категорию и способ передачи: мастер прочитает актуальные требования,
поставит необходимые соглашения в существующий Outbox, выполнит штатный
`acceptGameCategoryAgreement` и повторно проверит отсутствие непринятых условий.
При подтверждении сразу откроется следующий шаг — листать страницы и подтверждать
каждую версию не требуется. Уже принятые соглашения повторно не отправляются.
Тот же механизм применяется в мастере редактирования и подготовке публикации.

Исключение действует **только** для этой GraphQL-мутации: создание, редактирование,
удаление, публикация, сообщения, возвраты и выдача требуют прежних разрешений.
При выключенных общих записях worker выбирает только операции `agreements`;
другие ожидающие операции заодно не исполняются. При неподтверждённом или другом
аккаунте принятие блокируется, база не перепривязывается.

Перед каждым POST повторно проверяются свежие ID/содержимое/применимость через
тот же SafeAccount; устаревшая версия не отправляется. Playerok принимает только
agreementId/userId, отдельного version-CAS API не предоставляет: абсолютную
атомарность изменения текста на сервере после последнего чтения приложение не обещает.
Текущая подтверждённая версия фиксируется по ID и хешу документов. Инструкции продавцу
учитываются политикой и журналом; отдельная мутация для текста без server agreement ID
не выдумывается. Серверные соглашения подтверждаются только серверным readback.

Журнал в SQLite хранит аккаунт, категорию, способ, версию-хеш, хеши документов,
операцию, статус и время. Полные тексты не выводятся в логи. При потерянном ответе
сохраняется `UNCERTAIN`; приложение только перечитывает серверное состояние.
Если сервер подтверждает отсутствие непринятых условий, открытый мастер продолжится
автоматически, в том числе после рестарта. До такого подтверждения повторной мутации нет.
Если пользователь ушёл в другой раздел, фон не заменяет его экран; черновик сохранён.
Ошибки уведомления не повторяют принятие — откройте сохранённый черновик.

Регулярная смена условий ограничена: максимум6 новых операций на аккаунт/категорию/
способ за10 минут, максимум20 отправок и3 версии одного ID в операции. Счётчик
сохраняется после рестарта. Конфликтующие условия, неизвестный тип, неверный scope
или неподдерживаемый API останавливают процесс с коротким статусом.

Необязательный просмотр: «Диагностика» → «Условия продавца · просмотр» либо
«Условия» в превью. Этот просмотр только читает документы и не принимает их.
Реальные серверные принятия в тестировании этой реализации не выполнялись.


## Telegram-интерфейс магазина

После обновления отправьте боту `/start`. На главном экране пять разделов: **Товары, Заказы, Сообщения, Подарки, Ещё**. Кнопка «Требует внимания» появляется только по существующим проблемам.

- В карточке товара: **Редактировать**, **Настроить выдачу**, **Другие действия**. Склад находится внутри настройки выдачи; публикация и удаление — в других действиях, с прежними проверками и подтверждением.
- В заказе основные действия видны сразу; история, заметки, учёт и сверка находятся в **Подробнее**.
- В подарках: товары, история и настройки. При включённых настройках остановка выдачи доступна на первом экране. Неизвестный результат платежа не разрешает повтор.
- В **Ещё** доступны статистика, автовыдача, автопродвижение, профиль, настройки и инструменты. Баланс профиля открывается отдельной кнопкой; проверка соединения остаётся явной.

Старая навигация остаётся совместимой. Для устаревшего подтверждения откройте объект заново; после неизвестного результата сначала выполните сверку. Редизайн не включает платежи, автовозвраты, Auto-SENT или автоматизацию и не меняет `.env`.

Полная карта переноса и ограничения: [UX_REDESIGN.md](UX_REDESIGN.md).


## Разрешения операций и совместимость конфигурации

`PAID_OPERATIONS_ENABLED` **выведен из эксплуатации и игнорируется**. Старый `.env` совместим как с `true`, так и с `false`: ни один вариант не мешает запуску и не разрешает операции. Параметр раньше только вызывал безусловный отказ запуска при `true`; рабочего исполнителя, управляемого этим флагом, не было. Удалять его из старого файла необязательно.

| Флаг | Что разрешает | Чего сам по себе не включает |
|---|---|---|
| `PLAYEROK_WRITES_ENABLED` | Поддерживаемые записи Playerok через защищённый клиент и Outbox: товары, сообщения, выдача, выполнение и допустимые возвраты | Подарочные платежи, фоновые политики, платное продвижение |
| `PLAYEROK_AUTOMATION_ENABLED` | Вместе с записями позволяет workers автоответов, складских цепочек и обнаружения подарочных заказов | Без включённой политики/привязки заказы не начинают исполняться; прошлые заказы не переоформляются |
| `TG_GIFT_PAYMENTS_ENABLED` | Покупку Telegram Gifts через авторизованный личный MTProto при включённых записях, автоматизации и подтверждённой привязке | Другие платные функции и возвраты; начальная цена каталога не заменяет свежую проверку |
| `TG_GIFT_REFUNDS_ENABLED` | Отдельно разрешает возврат подарочного заказа по окончательной ошибке username до начала платежа, если Playerok допускает возврат | Не включает подарочные покупки; сценарий работает в действующей подарочной автоматизации и подтверждает ROLLED_BACK чтением API |
| `PLAYEROK_AUTO_ACCEPT_AGREEMENTS` | Только применимые условия продавца от подтверждённого аккаунта, в том числе при выключенных общих записях | Другие ожидающие операции Outbox, объявления, сообщения, платежи и выдачу |

Все разрешения по умолчанию выключены. Флаги не заменяют подключение нужного аккаунта, владение, PAID, явное включение товара/политики, emergency stop, сверку истории, остаток, бюджет, цену, получателя и подтверждение доставки. После смены `.env` необходим штатный перезапуск. Ошибка сети или неизвестный исход не разрешают повторную покупку.

**Реально поддерживаются:** управление лотами с бесплатной публикацией, сообщения и складская выдача, политики/цепочки/автоответы, платежи за обычные Telegram Gifts и последовательные пакеты, ограниченный возврат подарочной сделки, существующий Fulfillment с требованиями Playerok. Работоспособность на локальных транспортах не является live-приёмкой.

**Поддерживаются с явным подтверждением:** PREMIUM-публикация/повышение и платное автоподнятие с LOCAL-баланса Playerok через Outbox. Автоматический вывод денег не реализован. Устаревший общий флаг не разрешает эти операции сам по себе; инструкция ниже.

При выключенной общей записи, но включённом автопринятии условий запускается только узко разрешённый сценарий соглашений. Фоновые автоматические workers требуют одновременно записей и автоматизации; GiftService дополнительно проверяет собственные флаги и состояние. Неизвестные платежи и возвраты остаются заблокированными до достоверной сверки. Эта правка не меняет существующие значения локального `.env`.


## PREMIUM-публикация и платное автоподнятие

Реализованы через существующий PlayerokAPI, SafeAccount, Outbox, журнал promotion_expenses и планировщик. Расходы только с **баланса Playerok (LOCAL)**; банковские платежи, пополнения и автовывод не добавлены. Рабочая `.env` этим обновлением не меняется; PAID_OPERATIONS_ENABLED остаётся игнорируемым.

1. **Ещё → Продвижение → Настройки расчёта**: сохраните лимит одной операции, суток, месяца и число операций на товар. Нулевые значения не разрешают расход. Дневная/месячная границы — Москва; число операций на товар считается по всему журналу.
2. **Товары → товар → Другие действия → PREMIUM / платное поднятие**: выберите текущий тариф API, проверьте сумму и подтвердите расход. Для серверного DRAFT выполняется публикация PREMIUM; для APPROVED — повышение/поднятие. Создание товара остаётся отдельным действием; готовый серверный черновик можно опубликовать этим путём. Очередь не означает успех.
3. Для автоподнятия товар должен быть APPROVED/PREMIUM. На экране выбранного тарифа отдельно нажмите **Разрешить этот тариф для автоподнятия** — товар добавится в выбранные. Затем в продвижении отдельно подтвердите **Разрешить платное расписание** с текущими лимитами. Нужны writes + automation и включённая сохранённая политика.
4. Старые dry-run-настройки не разрешают расходы автоматически. Изменение политики/лимитов делает прежний платный допуск недействительным; изменение тарифа требует нового подтверждения. Интервалы, ночное расписание и две проверки позиции работают по существующей политике. Планировщик ставит операции только в Outbox.
5. **Остановить продвижение** блокирует новые/ещё не отправленные операции. Уже ушедший запрос отменить нельзя; его реальный ответ сохраняется. Неизвестный исход остаётся неизвестным, бюджет удерживается, слепого повтора нет.

Успех требует нового ID платёжной транзакции из ответа мутации и независимого чтения того же платежа у того же товара: CONFIRMED, OUT, LOCAL, ITEM_PREMIUM_PRIORITY и точная согласованная сумма. Ожидание модерации не объявляется активным объявлением. Результат приходит через существующие квитанции; сверка доступна в истории операций. Если ACK потерян целиком и ID платежа не сохранён, автоматическое подтверждение не выдумывается: операция требует ручного решения, новые расходы блокируются.

Технические границы и локальные/live проверки: [PAID_PROMOTIONS.md](PAID_PROMOTIONS.md). Ни одна платная live-операция в рамках разработки не выполнена.

Статистика теперь группирует графики, лучшие товары, финансы и подробный отчёт. Полные технические данные сохранены в подробностях/инструментах. Для первой настройки Gifts после глобальной остановки: «Подарки → Настроить → Разрешить новые покупки» с явным подтверждением; включение отдельного товара не снимает остановку магазина. Все текущие значения .env сохраняются.
Подробности текущей приёмки и ограничения: FINAL_ACCEPTANCE_REPORT.md, FINAL_UX_ACCEPTANCE.md. Offline CI запускает тесты без рабочих секретов, live-orchestrator не входит в CI.

### Интерфейс магазина и прогноз выручки

Обычные переходы используют одну текущую панель Telegram. При потерянном подтверждении её отправки автоматического повтора нет: нажмите кнопку фактически полученного экрана или явно восстановите только меню командой `/panel_reset`. Эта команда сбрасывает старые UI-подтверждения, но не повторяет операции Playerok/Gifts.

Общий способ получения денег: **Ещё → Профиль → Способ получения денег**. Прогноз: **Товары → товар → Сколько получу чистыми**. Себестоимость и распределение разовых расходов — внутри параметров расчёта. Известная сумма после комиссий не зависит от наличия старой стоимости PREMIUM; неизвестные расходы не считаются нулём.

Объединение связанных объявлений в рейтинге: **Статистика → Лучшие товары → Объединить предложения**. Требуются подтверждённые магазин, категория и явный выбор владельца; исходные заказы сохраняются. Подробнее: [приёмка UX и финансов](UX_FINANCE_ACCEPTANCE.md), [карта кнопок](UX_BUTTON_MAP.md).

### Восстановление и быстрые предложения

После неизвестного результата отправки панели используйте `/start` → **Восстановить меню**. Подтверждение восстанавливает только интерфейс, сбрасывает старые UI-подтверждения и не повторяет действий магазина. В рейтинге автоматически предлагается объединение подходящих объявлений — без ввода номеров; требуется одно подтверждение владельца. Автопродвижение имеет отдельный выбор товаров, а индивидуальный экран расписания — один переключатель участия и дополнительные параметры. См. [отчёт follow-up](UX_FOLLOWUP_REPORT.md).

## Постоянный код товара и перевыставления

**Товары → товар → Настроить выдачу → Постоянный код и выдача товара.** Настройте Gifts/склад/текст, проверьте превью и подтвердите добавление `[AB6]` в конец названия. Дождитесь подтверждения Playerok, затем отдельно включите выдачу и при необходимости наследование перевыставлений. Конфигурация Gifts хранится внутри бота; неперенесённые старые привязки требуют безопасного переноса перед новой выдачей. Платёжные флаги не включаются автоматически.

Сценарии и точные ограничения: [универсальная выдача — приёмка](UNIVERSAL_AUTODELIVERY_ACCEPTANCE.md). Новые реальные записи и платежи в рамках разработки не выполнялись.

Старые попытки без такого доказательства считаются неопределёнными консервативно.

Подробный offline-отчёт: [FIX_PROGRESS.md](FIX_PROGRESS.md),
[матрица дефектов и тестов](FIX_TRACEABILITY.md),
[безопасная ручная проверка](MANUAL_SMOKE_TEST.md).

### Перенос старой привязки и краткий расчёт

В карточке настройки выдачи для старой подарочной привязки нажмите
«Обновить описание на Playerok». Бот покажет замену последней метки `gift:` на уже
выделенный короткий код в конце названия. Подтверждение ставит необходимые изменения в Outbox;
после повторного чтения привязка подтверждается, выдача остаётся выключенной.
При неизвестном исходе доступна сверка без повторной записи. Если старая выдача
работает или есть незавершённая операция, сначала безопасно остановите/разрешите её.

«Сколько получу чистыми» показывает короткий прогноз одной продажи. Ниже порога
СБП отображается лишь процентная оценка с предупреждением о минимуме. Новый тариф
PREMIUM конкретного объявления и ранее подтверждённые разовые расходы показаны
отдельно; автоматического повторного вычитания нет. Полный расчёт и распределение
расходов сохранены в «Подробности»/«Параметры расчёта».

### Единый запуск и управление магазином

Создание: **Товары → Создать товар**. Описание пишется обычным текстом.
Для подарочной выдачи выберите подарки кнопками: повторное нажатие добавляет
ещё один подарок. Для текста или склада введите данные, которые остаются скрытыми
в карточках. При подготовке автоматической выдачи бот сам добавляет постоянный код
и создаёт закрытый черновик Playerok. До публикации доступны сообщения, лимиты,
завершение заказа, бесплатный/PREMIUM-тариф и отдельное разрешение наследовать
настройки штатных перевыставлений. Финальная кнопка — **Опубликовать и запустить**.

Для опубликованного настроенного товара **Запустить продажи** собирает известные
препятствия перед подтверждением. Старые кнопки подарков/обычной выдачи открывают
единую настройку. Общая остановка и остановка товара сохраняют историю и результаты
запросов. После возобновления общих разрешений товары сами не включаются.

**Фотографии**: можно добавить изображение, выбрать одно для замены или удаления.
Остальные сохраняются. Замена всего набора названа отдельно и подтверждается.
Описание сохраняет постоянный код автоматически; параллельное изменение на сайте
останавливает устаревшую запись. Server-side CAS описания Playerok не гарантирует:
редактируйте товар в одном месте, а неизвестный исход сверяйте без повтора.

**Продвижение → тариф → подтвердить расход** — разовая покупка PREMIUM с актуальной
ценой и балансом, без обязательного включения расписания и его бюджетов. Автопродвижение
остаётся отдельным разрешением с прежними лимитами. Такая же разовая покупка доступна
при выборе PREMIUM в мастере. При неизвестном результате второй платёж блокируется.

**Поиск** проверяет доступный каталог всех статусов, а не одну страницу. Поддерживаются
название, постоянный код и фильтры настроенной выдачи/проблем. Неполная загрузка явно
отмечается и продолжается кнопкой; снимок хранится 60 секунд и обновляется по запросу.
Обычный вход в товары по-прежнему показывает активные объявления.

Служебный ввод в активном сценарии удаляется из личного чата владельца, если Telegram
разрешает. Ошибка удаления не отменяет сохранение. Уведомления, квитанции и сообщения
вне сценария сохраняются. **Статистика → Скорость выдачи** показывает фактические
локальные замеры и отдельно отсутствие достоверного серверного времени оплаты.

Результаты, покрытие и ограничения: [SELLER_UX_ACCEPTANCE.md](SELLER_UX_ACCEPTANCE.md).


### Товары со встроенной выдачей Playerok

**Товары → карточка → Настроить выдачу → 📦 Выдаёт Playerok**. Независимо включите
автоответ после оплаты и автоматическую отметку выполнения продавцом, при желании
измените текст, затем нажмите **Сохранить**. Это явное разрешение выбранных действий
по будущим покупкам. По умолчанию оба переключателя выключены.

Бот не передаёт товар, не требует локального склада, gift-метки, постоянного кода
или изменения объявления. Свежая сделка должна подтверждать вашего продавца,
оплаченный статус и встроенную автоматическую выдачу (`is_automated=true`). Данные
выданного товара не анализируются. Сохранение исключает уже известные заказы;
отдельно проверяется серверное время создания будущей покупки.

Ответ и отметка имеют отдельные подтверждения. Уже отмеченный или завершённый
новый заказ получает только ещё не отправленный ответ. Отмена блокирует новые
действия; неизвестный результат не повторяется. Ответ с неизвестным исходом
останавливает последующие шаги до решения владельца.

Автоматическая отметка использует существующий `updateDeal(SENT)` только без
обязательного отчёта и при подтверждённой роли продавца. Это не подтверждение
получения за покупателя. Системные товары, неизвестная роль и обязательный отчёт
требуют действий в Playerok: причина и переход доступны из карточки заказа.

Настройки наследуются при штатном перевыставлении только через уже подтверждённую
логическую привязку с ранее разрешённым наследованием; по похожему названию ничего
не включается. Без такой связи новый ID настраивается отдельно. Общая остановка
автовыдачи выключает и этот режим; возвращение глобального разрешения не включает
остановленные настройки. Подробный контракт: [PLAYEROK_NATIVE_DELIVERY_SPEC.md](PLAYEROK_NATIVE_DELIVERY_SPEC.md).

Если Playerok возвращает приватный снимок покупки с другим ID, автоматическая связь
допускается только через существующую проверенную логическую привязку: полный
снимок точной сделки, постоянный код, критичные параметры, разрешение наследования
и привязка снимка к одному заказу. При отсутствии такого доказательства новый ID
не получает чужие настройки по названию; требуется проверить его связь вручную.


### Telegram: краткая консоль и DEBUG
Обычные успешные HTTP-запросы не печатаются. Причины Telegram ошибок классифицируются; повторяющиеся сетевые отказы группируются, подтверждённое восстановление видно отдельно. `PCC_LOG_LEVEL=DEBUG` в окружении запуска или `python -m app --telegram-network-diagnostics` включает подробный безопасный файловый журнал `logs/control_center.log` (2MB,5резервныхкопий); консоль остаётся краткой. Секреты и текст сообщений не записываются. Подробности исправлений/границы offline-проверки: TELEGRAM_STABILITY_REPORT.md.


### Короткие коды товаров и автоматическая миграция
Новые логические товары получают постоянный трёхсимвольный код в конце названия:
`Название [AB6]`. Машинный код подарка (`zombie_bear`) и точный gift_id не меняются.
Старая служебная строка `#1234567` больше не используется для новых покупок.
Разрешённый владельцем перенос запускается из папки магазина командой
`python -m app.migrate_codes`: без Telegram-подтверждений, под эксклюзивным lock,
с предварительным backup, через существующий edit Outbox и точное чтение результата.
Обычные очереди сообщений и платежей этот запуск не исполняет. Неизвестная операция
не повторяется; конфликт одного логического товара не мешает независимым товарам.
Сначала остановите бот через Ctrl+C. Глобальное разрешение записи не обходится.
Реальный результат текущего магазина: [TITLE_CODE_MIGRATION_RESULT.md](TITLE_CODE_MIGRATION_RESULT.md).


### Единая подготовка товара и безопасная диагностика

`Товары → Создать` предлагает ручную выдачу, постоянный текст, уникальный
склад, Telegram Gifts и «Выдаёт Playerok». Сначала создаётся серверный
черновик. Затем **«Продолжить настройку и запуск» → «Проверить готовность» →
«Опубликовать и запустить»** сохраняет разрешённую выдачу до публикации.
Для PREMIUM требуется актуальный тариф и итоговое подтверждение расхода.
Новая подарочная привязка использует каталог и постоянный код `[XXX]`
в названии; добавлять `gift:` в описание не требуется.

Сообщения для будущих покупателей можно менять без STOP. Уже учтённые
заказы и поставленные в очередь сообщения сохраняют прежний текст.
Смена способа выдачи, критичных параметров и финансовых разрешений
по-прежнему требует предусмотренных проверок и подтверждений.

В карточке товара есть **«Проверить готовность»**, конкретные причины
блокировки и переходы к настройкам соответствующего товара. Возраст
последней проверки аккаунта показывается отдельно от действительной
потери авторизации. Локальная история доступна даже после удаления
публичной карточки Playerok; она не доказывает текущий статус объявления.

Массовая остановка показывает область действия и требует одного актуального
подтверждения. История и результаты начатых запросов сохраняются.
Возобновление после пополнения склада проверяет постоянную привязку,
не отменяет резервы и не снимает явный STOP владельца.

Ожидание Telegram Gift не занимает независимую очередь Playerok:
используется тот же Durable Outbox с двумя последовательными направлениями
исполнения. Покупки Stars остаются строго последовательными; неизвестные
результаты не повторяются. Telegram RetryAfter откладывает только доказанно
неотправленное уведомление. Сетевой таймаут остаётся неопределённым результатом.

Автоматические startup-копии SQLite хранятся ограниченно: последние десять
проверенных старых копий, текущая копия и до трёх месячных контрольных точек.
Ручные, неизвестные, повреждённые файлы и ссылки не удаляются. Результат
виден в диагностике. Проверки разработки выполняются на временных базах;
они не подтверждают реальные платные отправки или публикации на Playerok.

## Восстановление после простоя и финальная диагностика

Подтверждённые новые продажи с современной привязкой [XXX] могут быть обработаны после длительного простоя: исходный период разрешения сохраняется, возраст заказа сам по себе не включает и не отменяет выдачу. Неизвестная дата, противоречивые серверные сведения, STOP и UNCERTAIN требуют проверки; права не восстанавливаются автоматически.

Старые подарочные привязки, требующие перехода, показывают действие подтверждения [XXX]; новая оплаченная продажа такого товара остаётся в разделе внимания. Переход не повторяет неизвестную покупку и не меняет старые квитанции. Новые ручные товары также получают [XXX], без включения автоматики.

Автопродвижение показывает повторяющиеся ошибки отдельных товаров и следующий повтор. Здоровый dry-run не подтверждает оплату. notifications:timing содержит фактические длительности обработки событий/фоновых обновлений и возраст критических событий; это диагностика, не обещание доставки Telegram за фиксированное время.

Сквозная карта проверки и границы live-приёмки: [docs/FINAL_OPERATION_READINESS_ACCEPTANCE.md](docs/FINAL_OPERATION_READINESS_ACCEPTANCE.md).
