1. АРХИТЕКТУРА ПОСТОЯННЫХ ИДЕНТИФИКАТОРОВ

- публичный постоянный код;
- owner_id;
- тип автовыдачи;
- конфигурацию выдачи;
- версию конфигурации;
- состояние и разрешение автоматической выдачи;
- историю связанных Playerok item_id;
- метаданные исходного объявления;
- подтверждённую категорию и способ получения;
- даты создания, обновления и последней успешной проверки;
- ссылки на аудит и историю изменений.

Примеры:
#3848148
#1234567
#8372914

Формат для пользователя: # + 7 цифр.

Используй криптографически стойкий генератор, уникальный индекс SQLite и безопасную повторную генерацию при коллизиях.

Семизначный код является публичным идентификатором, а НЕ секретом и НЕ разрешением на выдачу или списание денег.

Один и тот же код всегда обозначает один логический товар внутри аккаунта.

Нельзя автоматически объединять разные логические товары только по одинаковым названиям, ценам, изображениям или категориям.

2. ПРИВЯЗКА ТОВАРА ЧЕРЕЗ TELEGRAM

Доступные варианты:

- фиксированный текст;
- ручная выдача.

Для подарков пользователь вводит, например:
gift: heart
gift: bear, heart
gift: heart, heart

Для Steam-аккаунтов выбирает существующий склад или создаёт новый и загружает уникальные единицы товара.

Конфигурация хранится в базе, а не в описании Playerok.

После проверки конфигурации:
- генерируется публичный код;
- отображается превью изменений;
- пользователь подтверждает привязку;
- бот добавляет код в конец описания Playerok;
- выполняется повторное чтение лота;
- проверяется, что именно нужный код сохранился;
- только после успешного подтверждения привязка становится пригодной для включения автовыдачи.

Внешние изменения должны быть явными. Подтверждение настройки не означает разрешение на платную выдачу Stars.

Сохраняй исходное описание и версию наблюдавшегося состояния.

Не перезаписывай чужие изменения описания, сделанные после чтения.

Если описание изменилось между подготовкой и записью, останови операцию, обнови данные и предложи повторить подтверждение.

Редактируй только необходимую часть описания, сохраняя остальные пользовательские данные.

Не допускай:
- нескольких различных PCC-кодов в одном описании;
- случайной замены чужого кода;
- появления кода посреди пользовательского текста;
- порчи форматирования;
- потери текущего описания;
- создания дублирующих лотов;
- повторного добавления одинакового маркера.

Управление должно быть идемпотентным.

Если Playerok не разрешает редактировать описание определённого статуса, покажи понятное сообщение и безопасный способ продолжить. Не обходи ограничения площадки скрытыми действиями.

3. ПЕРЕВЫСТАВЛЕНИЕ ЛОТОВ

Это критическая часть.

После покупки Playerok может автоматически перевыставить объявление.

Нельзя рассчитывать, что item_id всегда сохраняется.

Поддержи оба сценария.

Сценарий А:
Playerok восстанавливает лот с прежним item_id.

Бот проверяет статус, описание, конфигурацию и продолжает использовать существующую привязку.

Сценарий Б:
Playerok создаёт новый item_id с тем же постоянным кодом.

Бот обнаруживает новый лот, проверяет принадлежность аккаунту, код, категорию, способ получения, неизменность критичных параметров и возможную подтверждённую связь с исходным объявлением.

После успешной проверки новый item_id связывается с прежним логическим товаром.

Необходимо поддерживать историю:
Логический товар #3848148
  item_id=A
  item_id=B
  item_id=C

Заказы по A, B и C должны использовать согласованную конфигурацию выдачи, с учётом действовавших разрешений и версии конфигурации.

Не полагайся исключительно на поиск по описанию оплаченной сделки.

Реализуй отдельное обнаружение новых лотов через существующий API, периодическую сверку и доступные события.

Плановый скан не должен приводить к чрезмерному количеству API-запросов.

Используй ограниченную пагинацию, контроль ошибок, backoff и сохранение прогресса.

Если подтверждено, что Playerok передаёт надёжную связь перевыставления с исходным объявлением, используй её. Если нет, не выдумывай такую связь.

Одинаковый публичный код сам по себе недостаточен для безусловного включения платной автоматизации.

Если появился неизвестный item_id с кодом:
- проверь владельца;
- проверь категорию;
- проверь способ получения;
- проверь сохранённую конфигурацию;
- проверь отсутствие конфликтующих привязок;
- установи допустимость автоматического наследования;
- при недостаточности доказательств отправь на подтверждение владельцу.

Неизвестный или неоднозначный новый лот должен переходить в безопасное состояние без автовыдачи.

Если пользователь одновременно создал две активные копии с одним кодом и нет доказанной допустимости такого состояния, блокируй автоматическое наследование до разрешения конфликта.

Проверь отдельный сценарий: после покупки прежний лот становится неактивным до перевыставления. Это не должно само по себе отменять уже полученный подтверждённый оплаченный заказ. Но отсутствие доказательств допустимости выдачи также нельзя обходить.

4. ОБРАБОТКА НОВЫХ ЗАКАЗОВ

Сохрани существующую логику WebSocket, API reconciliation, polling, durable inbox и SQLite.

При поступлении заказа:

1. Получить уникальный order_id.
2. Проверить направление сделки — продажа текущего владельца.
3. Проверить подтверждённый статус оплаты.
4. Проверить владельца и item_id.
5. Найти привязанный логический товар.
6. Проверить согласованность постоянного кода и истории item_id.
7. Проверить активность и разрешения соответствующей конфигурации.
8. Проверить, что заказ подходит для автоматической выдачи.
9. Проверить, что такой заказ не обрабатывается повторно.
10. Создать долговечное намерение выдачи и продолжить через существующую систему операций.

При необходимости догружать достоверные данные через API Playerok.

Не считать один лишь текст gift: или совпадение названия достаточным основанием для расходования Stars.

Не разрешать выдачу старых заказов после первоначального подключения.

Не разрешать автоматическое повторное выполнение старых заказов после изменения конфигурации.

Сохранить проверенный порядок обработки состояний заказа, защиту от устаревших событий и повторных уведомлений.

Ни один повторный WebSocket event, API polling, рестарт или повторное нажатие кнопки не должен приводить к повторной выдаче.

9. МИГРАЦИЯ СТАРОЙ СИСТЕМЫ

Существующая система Gifts использует gift: в описании.

Новая система должна хранить конфигурацию внутри бота.

Нельзя просто удалить старую логику и сломать уже настроенные товары.

Реализуй безопасную миграцию:

- определить существующие gift_listings;
- создать логические товары и постоянные идентификаторы;
- перенести конфигурацию без потери gift ID, порядка подарков, лимитов и настроек;
- сохранить историю заказов;
- сохранить прежние gift_jobs, gift_steps и receipt;
- не переписывать выполненные операции;
- не повторять исторические покупки;
- не включать автоматически ранее выключенные товары;
- не разрешать старым pending или UNCERTAIN операциям повторную отправку.

Замена gift: на #ID в реальном описании должна быть явной управляемой операцией с подтверждением.

Пока описание не мигрировано и не проверено, прежнее состояние должно оставаться безопасным, а пользователь должен видеть необходимость миграции.

Сделай миграции SQLite транзакционными и повторяемыми.

Существующие функции и отчёты по историческим продажам должны продолжать работать.
