## Предварительные условия настоящей проверки

1. Реальный разрешённый товар, поставляемый передачей одной уникальной текстовой
   единицы (действительный код/ключ/другой допустимый цифровой товар).
   Владелец должен подтвердить право продажи и работоспособность этой единицы.
   Не выбирать выдуманный код или Stars: складское сообщение не переводит Stars.
2. Exact item ID, категория, способ передачи, цена и описание фактического товара.
   Если нужен новый лот, его создание/публикация — отдельный согласованный объём.
   Другие объявления не редактировать. Индивидуальный DEFAULT quote=0 обязателен.
3. Согласованный независимый покупатель/получатель, который действительно получит
   товар. Платёж выполняет покупатель по отдельно согласованным условиям Playerok.
   Не создавать фиктивную/самостоятельную покупку; агент не проводит платежи.
4. Один реальный секрет в inventory, связанный только с этим item_id. Не писать
   значение в отчёты/Git/логи. Нужен безопасный локальный ввод владельцем.
5. Явное разрешение на автоматическую отправку этой единицы в чат одного нового
   PAID-заказа и (отдельно) на seller fulfillment после фактической проверки.
   Заранее согласовать исполнение runtime writes/automation и возврат flags вfalse.
   Не запускать с неизвестными старыми policies/outbox jobs; текущая read-only
   проверка рабочей БД показала0 policies/stock/chains/delivery jobs и1 owner.

## Порядок одного live-прогона существующей архитектуры

A. Без записи: авторизация текущего seller, actual item/owner/category/obtaining,
   отсутствие проблемы/серверной автораздачи, свежие поля заказа/чата. Сделать
   SQLite backup, проверить историю outbox/UNCERTAIN/reservations и baseline заказов.
   До завершения baseline EnrollmentWorker должен оставаться выключенным.

B. После точного согласования: одна policy на указанный item, stock/auto_enroll=true,
   greeting/after пустые (ровно одно товарное сообщение), mark_sent=true только как
   NEEDS_FULFILLMENT. Явно подтвердить future-order cutoff. Загрузить одну единицу;
   проверить AVAILABLE1/RESERVED0/DELIVERED0/QUARANTINED0 без раскрытия содержимого.
   В существующих workers нет per-order scope допуска до появления заказа: согласованная
   policy охватывает будущие продажи выбранного item, пока включена. Поэтому сначала
   закрыть/проверить все остальные policies, согласовать окно с покупателем и наблюдать.
   Запас1 ограничивает выдачу одной единицей; конкурирующая продажа не должна получить
   второй товар. Это не гарантирует, что первым придёт именно согласованный покупатель.
   Если тест требует строгого допуска только конкретного order ID, существующий
   автоматический enrollment пока такого фильтра не имеет; не заявлять обратное.

C. После согласованной настоящей оплаты Synchronizer получает get_deals/get_deal,
   Orders сохраняет PAID, EnrollmentWorker регистрирует одну цепочку и атомарно
   резервирует1. Повторный polling/WS hint не создаёт второй резерв/цепочку.
   Не подменять created_at локальным временем и не подавать исторический PAID как новый.

D. ChainWorker создаёт единственную delivery outbox operation. Executor ещё раз
   читает сделку и чат, сверяет owner/status/problem/stock/policy/lease, затем делает
   одну send_message. Зафиксировать message_id, не содержимое товарного секрета.
   Outbox SUCCEEDED и inventory DELIVERED фиксируются одной локальной транзакцией.

E. Независимо прочитать get_chat_messages: тот же message_id, seller, точный товарный
   текст, допустимое время, не удалён. Сохранить только результаты сравнения/ID/hash,
   без секрета. Отсутствие в одной странице не доказывает отсутствие отправки.
   SUCCEEDED означает серверную квитанцию, не прочтение покупателем и не активацию кода.
   Реальный покупатель отдельно подтверждает, что товар получен/пригоден.

F. Chain заканчивается NEEDS_FULFILLMENT. Текущий Fulfillment требует личное owner
   attestation. После отдельного согласования проверить actual requirement/role,
   выполнить один updateDeal(SENT) либо требуемый report, затем fresh get_deal.
   Локальный статус обновляется только из реального ответа; SENT не равен buyer
   CONFIRMED. CONFIRMED ожидается отдельно от покупателя, не имитировать его.
   Полностью автоматического SENT текущая реализация не делает.

G. Остановить согласованное окно исполнения/политику, вернуть flagsfalse по
   согласованному плану, сверить остатки/резерв/outbox/статус сделки. Автоматика
   последнего остатка уже ставит delivery:item:enabled=false; пополнение само по себе
   не является разрешением возобновить выдачу. Не удалять купленный товар автоматически.

## Сбой и восстановление

- До отправки restart продолжает PENDING из БД с тем же operation key.
- PROCESSING с истёкшим lease, timeout/потеря ACK, отсутствие message ID: UNCERTAIN,
  товар QUARANTINED, chain BLOCKED; последующие сообщения/fulfillment блокируются.
- Не повторять send/updateDeal и не возвращать секрет в AVAILABLE автоматически.
- Reconciliation: read-only поиск exact message ID/seller/text/time + явное решение
  владельца через существующий интерфейс. Одно совпадение текста без ID недостаточно.
- Даже после положительной сверки BLOCKED цепочка не перезапускается автоматически;
  дальнейшие действия только после осмотра владельцем, без повторной выдачи.
- Реальные аварии не инъецировать покупателю без дополнительного согласования:
  сценарии с kill/timeout проверены локально, live сначала один обычный безопасный проход.

## Открытые критерии

Live обнаружение новой PAID продажи → reserve → actual send/readback → stock update
→ seller fulfillment не выполнены. Нет выделенного реального товара/секрета,
согласованного покупателя/заказа и разрешения на live send/исполняющие flags.
Строгий allowlist конкретного order/buyer для auto enrollment отсутствует.
Независимый readback сообщения используется в плане проверки, а не встроен как
автоматический обязательный шаг до DELIVERED. Полностью автоматический SENT отсутствует.
Эти ограничения не закрываются числом локальных тестов.
