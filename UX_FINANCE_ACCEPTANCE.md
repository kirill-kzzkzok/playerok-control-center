## Что было причиной и что исправлено

| Проблема | Причина | Исправление |
|---|---|---|
| Новое сообщение при навигации | Панели напрямую вызывали answer/answer_photo, обходя display | Navigation/PanelMessage оборачивает существующие production-панели; известная текстовая панель редактируется, фото меняется через editMessageMedia |
| Неверный возврат | context_back угадывал раздел из callback | История фактических read-only экранов и безопасного контекста; встроенные шаги Wizard/FSM сохраняют свои возвраты, nonce не сохраняется в истории |
| Закрытый профиль не открывается | Указатель оставался на подтверждённо удалённом сообщении | После подтверждённого delete указатель очищается; закрытие блокирует старые изменяющие callbacks |
| Timeout панели | Нельзя узнать, был ли send принят Telegram | Durable sending; автоматический повтор запрещён. Callback с точной ожидаемой клавиатурой подтверждает существование панели. `/panel_reset` — отдельное явное восстановление только UI с очисткой старого FSM |
| Остановка Gifts после потерянного ACK | Общая проверка старого message ID блокировала кнопку stop | Авторизованная остановка новых расходов допускается независимо от старого/неподтверждённого экрана; RED → GREEN через Dispatcher |
| Неактивные товары на главном списке | statuses=None и отсутствие проверки статуса строки | APPROVED по умолчанию, серверная и локальная проверка, отдельные черновики/архив; gift picker сохраняет доступ к DRAFT |
| Сохранённый фильтр сам менялся | Временные просмотры автоматически перезаписывали preference | Предпочтение товаров меняется только явным «Запомнить фильтр» |
| Три одинаковых предложения в рейтинге | Агрегация только item_id | Отдельная проекция подтверждённых владельцем групп, с account/category/normalized title и исходными ID; оригинальные заказы не меняются |
| Выбор вывода требовал ввод суммы | Старый calculator FSM запускался сразу после выбора | Сохраняется общий preference; следующие расчёты перечитывают ставки, ввод суммы из обычного выбора убран |
| Расчёт спрятан и повторно вычитает размещение | Несколько входов и отсутствие per-sale allocation | Прямой вход из товара; разовое новое размещение отдельно, распределение задаётся явно, неизвестная прибыль остаётся неизвестной |
| Прогноз и сохранённая quote расходились | UI применял allocation после save_quote | Один result с allocation используется для отображения и сохранения; fee_basis сохраняется |
| Дубли PREMIUM | Разные входы quote/promo/payp и старый текст «не реализована» | Основной вход payp:item; старый quote перенаправляется туда, расписание и расчёт без оплаты остаются вложенными |
| Фото ответа исчезало до подтверждения | Фото и подтверждение рендерились последовательно как разные панели | Фото с коротким текстом и подтверждением в одном экране; длинный текст имеет безопасный переключатель текст/фото с тем же nonce |
| Полный автоответ терялся при редактировании | Ранее отправлялись несколько отдельных preview-сообщений | Постраничный полный preview в одной панели, подтверждение в последней странице |

## Финансовые границы

- Общий вывод хранится в прежнем `finance:{owner}:withdrawal`; нового конфликтующего хранилища нет.
- Ставка берётся из текущего товара/его способа передачи. При необходимости читается схема с `auto_agreements=False`: просмотр калькулятора не принимает условия и не меняет Playerok.
- Минимумы, лимиты и USDT остаются в существующем withdrawals. Ни одна неизвестная комиссия не превращается в ноль.
- Placement allocation — явный локальный прогноз на продажу. Он не меняет историю расходов, заказы и реальные списания. Новая стоимость PREMIUM не вычитается повторно автоматически.
- Stars показаны в исходной валюте; неизвестный RUB-эквивалент не подставляется.
- Аналитические группы сохраняются в owner/account-scoped settings. Изменение владельца, категории или нормализованного названия не позволяет применить старое объединение. Без достаточной provenance автоматическое объединение не производится.
- Outbox, paid approvals, guards, бюджеты, started_at, UNKNOWN/UNCERTAIN, receipt, запреты повторов и refund не изменены.

## Проверки и доказательства

- Production Dispatcher, SQLite FSM и контролируемые Telegram/Playerok транспорты. Новые targeted tests: `tests/test_global_ux_finance.py`; существующие регрессии сохраняют проверку финансовых guards и реальных worker-решений.
- RED воспроизведены: активный список; запрос суммы после выбора вывода; quote/allocation; ошибка свежей obtaining-комиссии; перезапись явно сохранённого фильтра; emergency stop и Back при неизвестной отправке панели. Затем GREEN теми же тестами.
- Независимый reviewer искал unknown/stale/duplicate/budget/isolation/restart нарушения; обнаруженные проблемы закрытия, остановки и callback adoption исправлены.
- Старые тесты рендеринга адаптированы к настоящим editMessageMedia/deleteMessage вместо требования нового send при каждом переходе. Проверка неподвижности receipt заменяет устаревшее требование всегда отправлять новую панель. Финансовые ожидания отражают явное распределение разового расхода, а не повторное вычитание всей суммы.
- Самопроверка и миграции выполняются только на временной SQLite. Новых SQL-миграций для UI/settings не требуется.
- Итоговые exit codes и CI записаны в PROGRESS.md после завершения проверок.

## Проверка владельцем в Telegram

1. Перезапустить через штатный start.bat, отправить `/start`.
2. Открыть Товары: обычный список должен содержать только APPROVED; DRAFT и архив доступны отдельно.
3. Профиль → Способ получения денег → выбрать метод. Сумма не запрашивается.
4. Товар → Сколько получу чистыми. Проверить расчёт и при необходимости задать себестоимость/распределение в параметрах.
5. Открыть статистику, выбрать период и подраздел, вернуться Назад. Проверить тот же период.
6. В рейтинге явно выбрать и подтвердить связанные предложения. Одно название не объединяет товары автоматически.
7. Товар → Продвижение: только просмотр. Не подтверждать расход для UX-проверки.
8. Профиль → Закрыть → `/start`. Не должно исчезнуть уведомлений и квитанций.
9. Если после сетевой ошибки панель действительно пришла, нажать её навигационную кнопку. Если нет — явный `/panel_reset` восстанавливает только меню; он не повторяет операций магазина.

Все изображения галереи — offline-рендеры настоящих production-сообщений на безопасных фикстурах, **не скриншоты живого Telegram**. В этой задаче нет реальных покупок, публикаций, возвратов, сообщений покупателям и live-проверки тарифов. Рабочие .env, база и MTProto-сессия не изменялись.

Финальная локальная приёмка: 1401 pytest passed; новые целевые инварианты 19 passed; галерея 1 passed. Ruff check/format, compileall, pip check и selfcheck — exit 0. GitHub workflow проверяется для опубликованного commit перед сдачей; источник статуса — GitHub Actions, а не mock. Точные checkpoints и локальные артефакты — PROGRESS.md.

Текст → фото через editMessageMedia сверён с [официальным Bot API](https://core.telegram.org/bots/api#editmessagemedia). Обратный переход использует подтверждаемую замену панели; это не основание удалять уведомления или квитанции.
