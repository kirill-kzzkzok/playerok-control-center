# Подтверждение редактирования и независимые Telegram-карточки

## Контракт

`update_item` вызывается один раз через прежний Outbox, после `started_at` и guard.
Полный ответ подтверждается прежним сравнением квитанции. Неполный или
несовпадающий ответ проверяется тремя чтениями `get_item` (паузы 0, 100, 300 мс).
Повторной mutation нет. Проверяются ID, владелец, все запрошенные поля и
неизменность известных полей идентичности. Цена сравнивается как Decimal;
название и описание — точно, после существующей нормализации входной формы.
Фотографии проверяются по сохранённым/удалённым ID, уникальности и числу новых
вложений. API не подтверждает побайтовое содержимое фотографии.

Причины воспроизведённых отказов:

- частичный ответ mutation немедленно приводил к EDIT_NOT_CONFIRMED без чтения;
- защищённая правка названия вместе с ценой сравнивала цену с предыдущим
  снимком даже после подтверждения запрошенной новой цены;
- после смены подарка готовность выключенного товара могла проверять старую
  неактивную gift_listings-проекцию вместо нового подтверждённого пакета.

Это доказанные причины в коде, а не утверждение о содержимом ответа реальной
операции bf5e0e70226d491cad0153f175133292: её рабочая база не открывалась.

Перед записью сохраняется ожидаемый контракт, после подтверждения — квитанция,
привязанная к payload, аккаунту и действующему lease. Если процесс упал между
квитанцией и завершением Outbox, повторная сверка читает сервер и использует
эту квитанцию. Чужой аккаунт, потерянный lease, последующая локальная mutation
или конфликт текущих полей запрещают такое завершение.

У старой обычной операции без квитанции совпадение полей означает только
«сейчас совпадает». API не предоставляет пригодную ревизию редактирования,
поэтому такое совпадение не превращается в успех старой операции.
logical_binding и code_migration проверяют свои сохранённые журналы/guards и
завершают связанные записи в той же транзакции, что и Outbox.

## Неопределённый результат

Основная кнопка — «🔍 Проверить результат на Playerok». Это только чтение.
Закрытие — отдельное действие с объяснением, причиной и финальным
подтверждением. «⛔ Закрыть без повторной отправки» не отменяет серверное
изменение, не подтверждает успех и не запускает запрос повторно. Начатые
денежные резервы и карантин выдачи сохраняются. Только доказанно неиспользованный
резерв обрабатывается прежним специальным guard. Для обычного edit снимается
ожидание этой записи; перед новой правкой нужно прочитать актуальный товар.
После закрытия edit остаётся доступна сверка, но не повторная mutation.

## Навигация

Главное меню сохраняет свой прежний ключ. Остальные карточки получают ключ
по исходному chat/message; замена недоступного сообщения сохраняет этот
контекст и не меняет соседние карточки. История «Назад» независима.

FSM каждой карточки хранится канонически в существующей таблице fsm через
StorageKey.destiny. Это не копии подтверждений: consume и enqueue остаются
одной SQLite-транзакцией. Первая миграция старого общего FSM атомарна. Обычный
текст относится к последней выбранной карточке; команды /start и /status — к
главной. Существующая изоляция владельца сериализует callback, а ACK выполняется
до долгой работы. Старые токены/закрытые сообщения не получают новые полномочия.

Обновления квитанций, старых уведомлений и ChatCards проверяют конкретный
message_id и текущий маршрут под тем же UI-lock. Они не перезаписывают форму,
открытую владельцем. Если уведомление перепрофилировано в другой экран, новое
входящее сообщение создаёт одну новую карточку; историю Playerok это не меняет.
Важные квитанции не удаляются при обычной замене/закрытии экрана.

## Покрытие реальных Dispatcher/FSM-маршрутов

| Маршрут | Проверка |
|---|---|
| Товар / выдача / LogicalProducts / Gifts | исходная карточка B; A неизменна |
| Склад / заказ / операции / результаты / настройки / главное меню | исходная B; нет Outbox-операций от просмотра |
| Назад из настроек к истории | независимая история B |
| Подтверждение A после открытия B и рестарта Dispatcher | nonce сохраняется только в A; повтор не создаёт edit |
| Одновременные callback A/B | каждый результат в своей карточке |
| Недоступная B и старые кнопки | замена только B; старые кнопки не меняют A/новую B |
| Фоновое уведомление после открытия истории в B | история B не перезаписана |
| Открытие переписки в B | B редактируется, новая карточка не отправляется |
| UNCERTAIN → проверка → причина → закрытие | только исходная квитанция; одна операция, ноль повторных mutation |
| Старый Gift → edit → новый пакет → явное включение | код/UUID/старый заказ сохранены, покупок при настройке нет |

Тесты используют настоящие сервисы и временную SQLite, заменены только внешние
транспорты. Это не live-приёмка Playerok или Telegram. Полный результат проверок
и оставшиеся ограничения фиксируются в PROGRESS.md.

Изменение старого latency-теста — документированная смена UI-контракта: форма
ответа больше не создаёт независимую notification-карточку. Прежние проверки
сохранённого ожидания ответа и отсутствия Outbox сохранены; добавлены проверки
исходного message_id, текста инструкции и отсутствия новых сообщений.

Прежний запрет *любого* редактирования уведомления заменён более точным
контрактом текущего задания: явный callback владельца может изменить его
отображение, но не удалить сообщение/квитанцию/историю, не изменить соседнюю
панель и не запустить повторную бизнес-операцию. Автоматические фоновые
обновления такого права на чужой экран не получают. Обычная карточка чата
сохраняет две основные кнопки «Ответить»/«Закрыть», без добавления общей «Назад».
