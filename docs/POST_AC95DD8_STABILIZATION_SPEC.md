Проведи финальный целевой аудит и исправление оставшихся проблем после коммита ac95dd8 в проекте Playerok Control Center.

Работай с текущим HEAD репозитория. Сначала прочитай AGENTS.md, PROJECT_SPEC.md, PROGRESS.md и документацию последних изменений. Не откатывай исправления из ac95dd8.

Приоритет: надёжность внешних операций, корректность Telegram UI, отсутствие ложных подтверждений и сохранение всех защит от двойной выдачи.

1. Исправить ложное подтверждение фоновых обновлений Telegram

В app/workers/notifications.py обнаружен потенциальный дефект.

Метод edit_notice() может пропустить редактирование Telegram-сообщения, когда владелец уже открыл в нём другой экран.

Однако вызывающие методы refresh_messages() и refresh_actions() после такого пропуска могут продолжить выполнение и сохранить rendered_payload или rendered_status так, будто сообщение действительно обновлено.

Проверь и воспроизведи это поведение.

Требования:

- Явно различать успешное редактирование, MESSAGE_NOT_MODIFIED, намеренно пропущенное обновление и ошибку.
- Не фиксировать успешный рендер, если сообщение фактически не обновлялось.
- Не перезаписывать экран, который владелец открыл через inline-кнопку.
- Не создавать бесконечные фоновые повторные попытки.
- Сохранять корректное состояние уведомлений после рестарта.
- Проверить аналогичные ошибки в operation_results.py, chat_cards.py и других фоновых обновлениях.
- Не терять историю операций и квитанции.
- Добавить тесты на переход из уведомления в другой экран, последующий результат операции и конкурирующие фоновые обновления.

2. Исправить обработку полностью потерянного ответа update_item

В ac95dd8 добавлена проверка get_item, если mutation вернула неполный или несовпадающий ответ.

Но если update_item выбрасывает исключение после потенциально выполненного запроса, обычный путь проверки ответа может вообще не выполниться.

Проверь это отдельно.

Нужная логика:

- Если mutation потенциально была отправлена, а ответ потерян, разрешить только безопасную read-only сверку.
- Проверять сохранённые ожидаемые значения, владельца, исходное состояние, связанные идентификаторы и действующий lease.
- Если есть достаточно доказательств успешной записи, корректно завершить операцию.
- Если доказательств недостаточно, оставить UNCERTAIN.
- Не выполнять update_item второй раз.
- Не переводить в успех операции с неизвестным происхождением изменений.
- Не обходить существующие guards для logical_binding и code_migration.
- Учитывать потерю соединения, исключение транспорта, отмену задачи, истечение lease и перезапуск процесса.

Особенно внимательно проверь ситуации, когда mutation уже выполнена, но подтверждение либо пришло слишком поздно, либо не дошло до приложения.

Добавь регрессионные тесты, доказывающие, что количество внешних write-запросов не превышает одного.

3. Проверить замену и порядок изображений

В последнем исправлении фотографии сверяются преимущественно по ID и количеству.

Необходимо отдельно проверить:

- Добавление изображения.
- Удаление изображения.
- Замену всех изображений.
- Замену только первого изображения.
- Сохранение остальных изображений.
- Порядок изображений после операции.
- Случай, когда сервер возвращает изображения в другом порядке.
- Случай, когда новая фотография появляется, но не становится главной.

Если API Playerok позволяет достоверно подтвердить порядок, добавь соответствующую проверку.

Если API не предоставляет такой гарантии, не выдумывай подтверждение. Явно зафиксируй ограничение и не показывай владельцу ложную успешную проверку порядка.

Не меняй существующие защитные правила работы с файлами.

4. Проверить жизненный цикл сохранённых квитанций edit

В app/services/edit_confirmation.py используется сохранение доказательств редактирования через настройки с ключами edit:confirmation:<operation_id>.

Проверь:

- Накапливаются ли эти данные бесконечно.
- Насколько увеличивается SQLite при тысячах операций.
- Не сохраняются ли ненужные большие объекты.
- Можно ли безопасно очищать завершённые временные данные.
- Что требуется сохранять для аудита и восстановления.
- Что происходит при повреждённой, старой или неполной квитанции.
- Что происходит после миграции БД и восстановления резервной копии.

При необходимости реализуй ограниченную безопасную очистку.

Категорически запрещено удалять доказательства для UNCERTAIN и незавершённых операций, если это ухудшает восстановление или безопасность.

Не ломай совместимость со старой SQLite.

5. Проверить безопасность новой message-scoped навигации

Проведи отдельный аудит нового MessageNavigation и StorageKey.destiny.

Особенно проверь:

- Два открытых сообщения одного владельца.
- Независимые состояния редактирования товара.
- Независимые формы ответа покупателям.
- Нажатие старой кнопки после изменения экрана.
- Рестарт между показом подтверждения и нажатием кнопки.
- Два быстрых нажатия одной кнопки.
- Одновременную обработку callback и обычного текстового сообщения.
- Отправку текста в момент, когда открыты две формы ввода.
- Неверное связывание введённого текста с последней активной карточкой.
- Использование чужого или устаревшего confirm_token.
- Восстановление старого FSM без дублирования полномочий.
- Фоновые обновления после закрытия карточки.

Не допускай, чтобы текст, предназначенный одной форме, случайно стал ответом покупателю из другой формы.

Если назначение обычного текстового сообщения неоднозначно, лучше попросить владельца выбрать нужный сценарий, чем отправить данные не туда.

Проверь, что бизнес-операции выполняются только при действительном подтверждении владельца и что повторное нажатие не создаёт новую отправку.

6. Проверить единообразие UNCERTAIN для остальных операций

Проведи обзор путей подтверждения:

- create;
- publish;
- discount;
- edit_fields;
- delete;
- mark_read;
- reply;
- delivery;
- fulfill;
- premium_publish и premium_bump;
- gift_send и gift_refund.

Найди случаи, аналогичные старому EDIT_NOT_CONFIRMED, когда операция выполнена, но приложение игнорирует доступные доказательства результата.

Не объединяй все операции под один универсальный механизм, если для них различаются условия безопасности.

Для сообщений, выдачи, платежей и подарков требуются строгие идентификаторы и однозначная связь с исходной операцией.

Нельзя подтверждать отправку товара только по совпадению текста, покупку подарка — только по уменьшению баланса Stars, а платное продвижение — только по изменению статуса лота.

Если невозможно подтвердить конкретную операцию, сохраняй UNCERTAIN и блокируй опасный повтор.

Все обнаруженные проблемы сначала воспроизведи тестами. Исправляй только подтверждённые дефекты, а не гипотетические сценарии без обоснования.
