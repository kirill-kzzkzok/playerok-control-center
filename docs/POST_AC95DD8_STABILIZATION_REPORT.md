# Адресная стабилизация после ac95dd8

База: ac95dd8f5324823b72f91bbb4d4178611239efe5. На ней локально прошли
2066 тестов и CI 41683280684. Это исходное доказательство, не результат новых правок.
Полное ТЗ: POST_AC95DD8_STABILIZATION_SPEC.md. Счётчики итоговой проверки — в PROGRESS.md.

## Подтверждённые дефекты и исправления

1. `Notifications.edit_notice()` возвращал None при занятом владельцем экране,
   а вызывающие функции сохраняли rendered_payload/rendered_status. RED: два
   падения. Теперь результат явно UPDATED/UNCHANGED/SKIPPED; ошибки остаются
   исключениями с прежним backoff. SKIPPED не меняет доказательство рендера,
   выключает только обслуживание этой устаревшей UI-проекции через существующий
   terminal-маркер failures=-1. История, Outbox и operation_receipts сохраняются.
   Параллельные обновления не перехватывают экран. Закрытый или заменённый
   operation-results view теряет только указатель фонового редактирования,
   без записи ложного rendered_status. ChatCards уже проверяет маршрут до
   изменения fingerprint и сохраняет CAS/busy-token; подтверждения успеха при
   пропуске там не найдено.
2. Потерянный ответ `update_item` обходил readback. RED: два падения, один
   безопасный expired-lease сценарий уже проходил. Теперь uncertain APIError
   разрешает ограниченное чтение только при действующем lease/аккаунте.
   Совпадение сохраняется как `readback_only`, confirmed=False. Оно не доказывает
   происхождение изменения и не завершает старую операцию успешной. Отмена задачи
   и запоздалый ответ сохраняют прежний UNCERTAIN; рестарт не повторяет mutation.
   Имеющаяся настоящая квитанция до сбоя по-прежнему допускает штатную сверку.
3. Две открытые формы позволяли тексту для названия товара стать ответом
   последнему покупателю. RED: реальная запись reply в Outbox через Dispatcher.
   Теперь неоднозначный ввод ничего не потребляет/не ставит в очередь. Бот
   просит использовать Telegram «Ответить» на сообщение нужной формы. Проверяются
   владелец, автор исходного сообщения, message_id, открытый канонический FSM.
   Два контекста сохраняются после перезапуска. Явно адресованный ответ использует
   прежние Replies/Outbox/consume, не новый механизм отправки. /cancel отменяет
   текущий сценарий, /start и /status сохраняют прежнюю командную навигацию.
4. Edit-доказательства хранили полный item, включая ненужные объекты и приватные
   data_fields, без очистки; повреждённые/неполные proof вызывали AttributeError/
   KeyError. RED воспроизведён. Теперь сохраняются только поля сравнения, ID
   фотографий и SHA256 критических значений вместо их содержимого. Старый полный
   формат остаётся читаемым; неполная/повреждённая квитанция даёт только актуальное
   состояние, без успеха и без повторной отправки.
   Дополнительный RED воспроизвёл пустой result при confirmed=True: теперь
   обязательны literal true и согласованные target ID в before/observed/result.
   Существующий hourly UploadCleanup удаляет максимум 500 временных proof за цикл
   только для SUCCEEDED edit старше семи дней. UNCERTAIN, PROCESSING, PENDING,
   PERMANENT_FAILED (включая ручное закрытие unknown) не очищаются. Outbox payload,
   result, audit и квитанция операции не удаляются. Новых таблиц/миграций нет.
   SQLite освобождает страницы для повторного использования; это не VACUUM и не
   обещание уменьшения физического файла. Изолированный замер 1000 подготовок:
   суммарно 395890 байт proof JSON (~395 байт/операцию), рост всех страниц SQLite
   823296 байт, включая Outbox. Тестовый item содержал 2 МБ лишних metadata и
   большие секретные поля: они в proof не попали. Размер реального proof зависит
   от названия/описания/пакета изменений.
5. При подтверждённом частичном ACK `create`, бесплатной публикации, скидки и
   редактирования полей отбрасывались доступные серверные доказательства.
   RED: четыре падения. Добавлены отдельные проверки в существующих ветках:
   известный ID создания и полный серверный DRAFT; известный ID публикации,
   допустимый опубликованный статус и цена; скидка с точной ценой продажи и
   raw_price; поля с field_receipt_matches и точным ID. Нет второго запроса записи.
   Без ID создания нет поиска по названию. Противоречивый explicit-статус
   публикации не заменяется предположением. Потерянный ответ по этим путям не
   превращается в успех от одного текущего совпадения.

## Фотографии: подтверждение и ограничение API

Используемый Playerok `updateItem` принимает addedAttachments/removedAttachments.
В существующем контракте приложения нет поддержанного параметра перестановки
или подтверждения главного изображения. PartialFile содержит id/url, не позицию.
Нельзя сделать вывод о гарантированном порядке только по порядку массива ответа.
Поэтому сохраняются строгие проверки состава/количества/уникальности ID и удаления
старых фото, но перед подтверждением и в успешном результате есть предупреждение:
«API не подтверждает порядок и главное фото; проверьте их на Playerok».
Не выполняется дополнительная запись ради перестановки.

Тестируются добавление, удаление, полная замена, замена первого фото, сохранение
остальных и противоположные порядки ответов. Замена первого изображения может
добавить новое в конец — это подтверждённое ограничение используемого пути,
не обещание замены обложки. Защита корня файлов/размеров/форматов сохранена.

## Gift-discovery: безопасное поведение без изменения кода

Курсор не является постоянной нижней границей: пустая страница сбрасывает его,
следующий цикл начинает обход заново. Новый оплаченный заказ с меньшим ID
обнаруживается после wrap. Это доказано новым тестом с повторной синхронизацией,
созданием нового worker, старым историческим заказом и фактическими тестовыми
Stars-вызовами: два новых заказа — два успешных job/платежа, повтор не добавляет
третий. Исторический заказ до armed_at не исполняется. Существующий тест 100
исторических строк также сохраняется. Безопасного дефекта потери из-за меньшего
ID в этом сценарии не воспроизведено; runtime не переписывался. Нет жёсткого
обещания задержки при бесконечно растущем потоке/продолжительном сетевом отказе.

## Остальные receipt-пути: сохранённые границы

| Путь | Что считается доказательством / что остаётся неизвестным |
|---|---|
| create | возвращённый ID + точный owned DRAFT/поля; без ID нет безопасной атрибуции |
| publish | ack известного ID + статус и цена; потерянный RPC-ответ не повторяется |
| discount | ack ID + согласованная sale/raw-price пара, без выдуманного raw_price |
| edit_fields | fresh owned target + все поля; действующий исходный draft/guards |
| delete | точный ID и aware deletedAt в transport receipt; 404 не доказывает свой delete |
| mark_read | отдельный нулевой счётчик чата, не доказательство отправки товара |
| reply/delivery/chain_message | уникальный server message_id, отправитель, чат, текст/вложения, время, no reuse; одного текста недостаточно |
| fulfill | отдельный статус и требуемый отчёт, сохранённые разрешения |
| premium_publish/bump | подтверждённая транзакция, тариф, сумма, бюджет, intent; одного PREMIUM-статуса недостаточно |
| gift_send | однозначная Telegram-квитанция sender/recipient/gift/time/ID; падение баланса ничего не подтверждает |
| gift_refund | отдельная проверка сделки/операции, запрет полного возврата после начала/частичной выдачи |

Для денег, Stars, отправки товара и сообщений общий postcondition edit не
используется. Неопределённость без подходящего server receipt принципиально
сохраняется. Старые настройки/резервы/карантин не сбрасываются. В этом этапе
не выполнялись live-платежи, изменения Playerok, сообщения покупателям,
реальные отправки подарков или обращения к рабочей SQLite/.env/сессиям.
