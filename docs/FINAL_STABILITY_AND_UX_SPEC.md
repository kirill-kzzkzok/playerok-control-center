A1. УСТРАНИТЬ ПУБЛИКАЦИЮ В ОБХОД ЕДИНОГО ЗАПУСКА

Сейчас из карточки серверного черновика доступны два пути:

- «Настроить и запустить».
- «Опубликовать бесплатно · проверка».

Первый проходит через ListingLaunch.

Второй использует старый publish: и Outbox. Если отсутствует launch_id и нет подготовленного запуска, некоторые проверки ListingLaunch.guard() обходятся по существующему контракту.

В результате владелец может создать товар с предполагаемой автовыдачей и случайно опубликовать его раньше окончательной настройки склада, подарков, текста или соответствующих разрешений.

Требуемое поведение:

1. Для новых товаров используй один основной процесс публикации.
2. Проверка бесплатного DEFAULT 0 ₽ должна быть частью этого процесса, а не отдельной конкурирующей публикацией.
3. Перед запуском показывай фактический способ выдачи.
4. Перед публикацией проверяй, завершена ли настройка выбранного способа.
5. Если выбран автоматический способ, публикация не должна обходить проверку готовности.
6. Если пользователь намеренно выбрал ручную продажу, допускай отдельный корректно подтверждённый ручной режим.
7. Не требуй от ручного товара наличия склада или Telegram Gifts.
8. При уже созданном автоматическом черновике не предлагай неочевидный способ обойти его настройку.
9. Сохраняй существующие серверные черновики и результаты операций.
10. Не выполняй публикацию повторно, если результат предыдущей операции неизвестен.

Нужно проверить также прямые старые callback publish:, а не только убрать кнопку.

Обычный пользователь не должен иметь второго скрытого пути, обходящего обязательную настройку.

A2. РЕДАКТИРОВАНИЕ НЕ ДОЛЖНО НЕЗАМЕТНО ЛОМАТЬ АВТОВЫДАЧУ

Сейчас обычное редактирование описания и характеристик допускается через общий Outbox.

При этом LogicalProducts.verify_listing() сравнивает:

- description_sha256.
- field_baseline.
- Критические параметры.
- Подтверждённое название и код.
- Конфигурационную ревизию.

Если описание или характеристики изменились, ранее сохранённый снимок может перестать соответствовать серверному товару.

В результате нормально работающий товар может перестать проходить проверки после обычного редактирования.

Исправь это как единую задачу согласованного изменения товара.

Раздели параметры на две категории.

Безопасные пользовательские изменения:

- Текст после выдачи.
- Текст благодарности.
- Допустимые сопроводительные сообщения.
- Другие параметры, не влияющие на идентичность и обязательства покупателя.

Критические изменения:

- Характеристики товара.
- Способ получения.
- Категория.
- Поля, определяющие предмет покупки.
- Данные, от которых зависит автовыдача.
- Изменения описания, для которых требуется обновление подтверждённого снимка.
- Изменения идентичности постоянного товара.

Для безопасных изменений:

- Не останавливай продажи без необходимости.
- Применяй изменения только к будущим операциям.
- Не изменяй снимки уже зарегистрированных заказов.
- Сохраняй ревизии и историю.
- Если сообщение уже поставлено в Outbox, не меняй его содержимое задним числом.

Для критических изменений:

- Показывай пользователю последствия.
- Требуй соответствующего подтверждения.
- Не допускай изменения, которое оставит логический товар формально включённым, но фактически недействительным.
- Согласованно обновляй подтверждённый снимок только после свежей серверной проверки.
- Если безопасное обновление невозможно без остановки, явно требуй STOP и повторное подтверждение.
- Не используй автоматически обновлённый снимок как способ узаконить произвольную внешнюю подмену.

Особенно проверь editdesc:, editname:, editfields: и непосредственные операции edit/updateItem.

Для названия уже имеется механизм сохранения [XXX] и обновления title_snapshot. Не ломай его.

A3. ЗАЩИТИТЬ УДАЛЕНИЕ ТОВАРА С НЕЗАВЕРШЁННЫМИ ЗАКАЗАМИ

Сейчас в карточке товара кнопка «Удалить» доступна без явной локальной проверки незавершённых оплаченных заказов.

Удаление выполняется через remove_item.

Исследуй, может ли локальная система допустить удаление при:

- PAID.
- RESERVED.
- ACTIVE.
- BLOCKED.
- NEEDS_FULFILLMENT.
- PROCESSING.
- UNCERTAIN.
- Незавершённом Gift RPC.
- Незавершённой отправке складского секрета.
- Уже поставленном в Outbox исполнении.

Требования:

1. Перед предложением удаления проверяй незавершённые операции данного товара.
2. Повтори проверку непосредственно перед внешним удалением.
3. Не полагайся исключительно на отказ Playerok.
4. Не удаляй автоматически резервы или историю вместе с объявлением.
5. Не допускай потери доступа к уже оплаченным обязательствам.
6. При наличии опасных операций объясняй причину блокировки.
7. Давай прямой переход к проблемным заказам.
8. Разрешай безопасное удаление черновиков и товаров без обязательств.
9. Не обещай откат удаления, если API Playerok его не поддерживает.
10. Если результат внешнего удаления неизвестен, сохраняй соответствующее безопасное состояние.

Необходимо отдельно проверить, какие удаления разрешены самим Playerok. Не придумывай возможности платформы.

B1. ОДИН СТАРЫЙ ЧАТ НЕ ДОЛЖЕН ОСТАНАВЛИВАТЬ НЕЗАВИСИМЫЕ ПРОДАЖИ

Предыдущий этап исправил часть зависимости Telegram Gifts от sync:health.

Но остальные подсистемы всё ещё могут требовать строго sync:health.status == OK.

Проверь конкретно:

- ListingLaunch.check().
- AutoReplyWorker.
- AutoReplies.dispatchable().
- Notifications.once().
- Первоначальную инициализацию уведомлений.
- Synchronizer.run().
- Backoff полного опроса заказов.
- Проверки готовности новых товаров.
- Другие места чтения sync:health.

Сейчас ошибка одного исторического чата может записать общий sync:health = ERROR.

При этом синхронизация оплаченных заказов может оставаться полностью исправной.

Нужна согласованная модель состояния:

- Авторизация аккаунта Playerok.
- Полнота и свежесть данных оплаченных заказов.
- Синхронизация отдельных чатов.
- Первичная загрузка исторических сообщений.
- Текущее состояние WebSocket.
- Состояние резервного polling.
- Технические ошибки конкретных операций.

Не обязательно вводить новые таблицы. Можно использовать существующие структурированные health-поля.

Важен единый контракт принятия решений.

Сбой нерелевантной старой переписки не должен:

- Выключать готовый магазин.
- Запрещать публикацию независимого товара.
- Останавливать обнаружение новых продаж.
- Увеличивать интервал опроса оплаченных заказов.
- Блокировать независимые Telegram Gifts.
- Бесконечно удерживать новые уведомления.
- Отменять автоответы в других исправных чатах.

Но соответствующее действие должно оставаться заблокированным, если невозможно достоверно проверить именно его заказ, чат, продавца или покупателя.

B2. ИСПРАВИТЬ BACKOFF РЕЗЕРВНОЙ СИНХРОНИЗАЦИИ ЗАКАЗОВ

Сейчас общая ошибка может увеличивать интервал полного опроса вплоть до 900 секунд.

Если WebSocket пропустит новое событие, это приведёт к большой задержке обнаружения покупки.

Требуемое поведение:

- Независимая ошибка исторического чата не замедляет проверку новых заказов.
- Настоящий сбой синхронизации заказов обрабатывается безопасно.
- Соблюдаются rate limits Playerok.
- RetryAfter учитывается там, где применим.
- Нет бесконечных агрессивных запросов при недоступном API.
- После восстановления нормальная частота опроса возвращается автоматически.
- Очередь новых оплаченных заказов не блокируется старой историей сообщений.

Цель проекта — обнаруживать оплаты и приступать к допустимой выдаче максимально быстро, желательно в пределах установленной цели 60 секунд при нормально работающих внешних сервисах.

Это цель производительности, не гарантия при любой сетевой ситуации.

B3. РАЗОБРАТЬ HTTP 403 ОТ НЕДОСТУПНОГО СТАРОГО ЧАТА

Обнаружена потенциально опасная последовательность:

1. Синхронизатор запрашивает исторический чат.
2. API возвращает HTTP 403.
3. Adapter преобразует ответ в UNAUTHORIZED_OR_CHALLENGE.
4. Playerok.call() вызывает connection.invalidate().
5. PlayerokConnection.disable() отключает права на записи и автоматизацию.

То есть даже после исправления sync:health сбой может остановить магазин через более низкий уровень адаптера.

Проведи интеграционный тест именно для HTTP 403 на get_chat/get_chat_messages.

Различай:

- Реальную потерю сессии.
- Challenge или блокировку аккаунта.
- Доказанный отказ в доступе к конкретному чату.
- Неоднозначный HTTP 403.
- HTTP 401.
- Временный HTTP 503.

Очень важно:

НЕ игнорируй все HTTP 403.

НЕ сохраняй денежные разрешения, если авторизация действительно сомнительна.

НЕ возвращай возможность тратить Stars или деньги Playerok по кэшированному успеху.

Если природа HTTP 403 неоднозначна, консервативно ограничь опасные операции и проведи отдельную свежую проверку viewer/account.

После подтверждения аккаунта можно восстановить только те разрешения, которые ранее действительно были выданы владельцем.

Локальный отказ старого чата должен оставаться локальной ошибкой, когда это достоверно установлено.

Обязательные тесты:

- get_chat_messages → HTTP 403, viewer → успешный ответ.
- get_chat_messages → HTTP 403, viewer → HTTP 401.
- get_chat_messages → HTTP 503.
- Непосредственный viewer → HTTP 403/challenge.
- Смена подтверждённого аккаунта.
- Восстановление после успешной проверки.
- Отсутствие платных операций при сомнительной идентичности.

B4. ПРАВИЛЬНАЯ ПЕРВИЧНАЯ ИНИЦИАЛИЗАЦИЯ УВЕДОМЛЕНИЙ

Особо опасен сценарий notifications:initialized = False.

Сейчас часть старых событий переводится в BASELINE после первоначальной успешной синхронизации.

Но если старый недоступный чат мешает завершению начальной синхронизации, новые события могут оказаться в неопределённой границе между историей и текущей работой.

Необходимо:

- Не засыпать владельца всеми историческими сообщениями.
- Не считать новую покупку исторической только потому, что одна старая переписка недоступна.
- Не терять новые сообщения, появившиеся после запуска.
- Корректно фиксировать момент или границу первоначальной инициализации.
- Сохранять данные после рестарта.
- Не переносить новые события в BASELINE при последующем восстановлении старого чата.
- Отдельно обрабатывать критические события, которым недопустимо исчезать из видимости.
- Не делать вывод о свежести только по локальному времени получения, если требуется серверное доказательство.

Обязательный тест:

1. Новый магазин, notifications:initialized=False.
2. Исторический чат возвращает HTTP 403 или 503.
3. Появляется новое сообщение.
4. Появляется новая оплаченная продажа.
5. Старая синхронизация остаётся неполной.
6. Старый чат позднее восстанавливается.
7. Выполняется переход к нормальному состоянию.

Проверь, что новая покупка и новое сообщение не были ошибочно записаны в исторический BASELINE и не потерялись.

B5. ВОССТАНОВЛЕНИЕ АВТООТВЕТОВ ПОСЛЕ ВРЕМЕННОЙ ОШИБКИ

- Реальное изменение сообщения.
- Удаление сообщения.
- Изменение правила.
- Истечение актуальности.
- Уже начатую внешнюю отправку.
- Неизвестный результат отправки.

Безопасно повторяй только бесплатные проверки при доказанном отсутствии внешней отправки.

Используй ограниченные попытки и backoff.

Перед постановкой автоответа снова проверь актуальность исходного сообщения и правила.

Не отвечай на старое сообщение, если диалог уже продолжился и такой ответ стал неуместен.

Не отправляй дубликат при неизвестном результате исходящей операции.

C1. НЕ ДОПУСКАТЬ БЛОКИРОВКИ СКЛАДСКОЙ ВЫДАЧИ МЕДЛЕННЫМ TELEGRAM GIFT

Сейчас основной Outbox исполняется последовательно.

Одна операция gift_send может занимать до 90 секунд.

Пока она выполняется, независимая выдача складского товара или текста может ждать своей очереди.

Нужно разработать безопасное планирование операций.

Требования:

- Медленный Gift RPC не должен без необходимости останавливать независимую складскую выдачу.
- Не создавать второй независимый Outbox.
- Не создавать конкурирующие платёжные движки.

- Не допускать повторной отправки одного сообщения или секрета.
- Не допускать обхода глобального STOP.
- Не нарушать lease fencing.
- Соблюдать ограничения Playerok на запись.
- Не увеличивать параллельность просто ради формального улучшения времени.

Сначала измерь задержки текущего исполнения.

Затем выбери минимальный безопасный способ изоляции независимых операций — например, ограниченные классы исполнителей или диспетчеризацию с сериализацией по опасным ресурсам.

Архитектурное решение обоснуй тестами.

Обязательные сценарии:

- Один Gift RPC задержан на 90 секунд.
- Новый складской заказ оплачен во время ожидания.
- Новый заказ с постоянным текстом оплачен во время ожидания.
- Два Gift RPC одновременно.
- Два заказа на одну складскую единицу.
- Перезапуск во время выполнения.
- STOP при активных задачах.
- Потерянный ответ внешнего API.
- Lease истёк до ответа.
- Поздний ответ старого исполнителя.

Для каждой операции сохраняй только допустимые состояния и подтверждённые результаты.

C3. ДОЛГОВРЕМЕННЫЕ ОШИБКИ WORKER НЕ ДОЛЖНЫ БЫТЬ НЕВИДИМЫМИ

Нужны:

- Количество последовательных ошибок.
- Текущая причина деградации.
- Время следующей попытки.
- Признак того, выполняет ли Worker полезную работу.
- Отдельное представление состояния от реального падения задачи.

Не обязательно вводить новые таблицы. Можно использовать существующие health-записи.

Не создавай уведомление на каждую единичную временную ошибку.

Добавь сигнал при:

- Превышении допустимого числа последовательных ошибок.
- Слишком долгом отсутствии успешного цикла.
- Накоплении непройденных оплаченных заказов.
- Зависании критического Worker.
- Повторяющемся отказе соединения, требующем владельца.

Устрани ложные тревоги во время предусмотренного backoff и штатных длительных операций.

C4. НЕ ТЕРЯТЬ ВАЖНЫЕ УВЕДОМЛЕНИЯ ПРИ ОШИБКАХ TELEGRAM

- Telegram явно запретил отправку.
- Ответ потерян, результат неизвестен.
- Отправка подтверждена.

- Изменение не должно отменять активные резервы.
- Не вызывай массовый STOP ради обычного текста.

D5. ПРАВИЛЬНЫЕ КНОПКИ ИСПРАВЛЕНИЯ ПРОБЛЕМ

Проверь все диагностические коды.

Известные ошибки:

WRITES_OFF:
Сейчас может предлагаться профиль, хотя разрешение задаётся через .env.

PROJECTION_MISMATCH:
Может открываться lp:ready, хотя для platform_only нужен другой механизм восстановления.

STARS_LIMIT:
Может открываться глобальный лимит, когда ограничение индивидуальное.

Устаревшие инструкции:
Местами всё ещё говорится, что постоянный код находится в описании.

GiftsPanel:
Кнопка остановки может показываться даже когда выдача уже остановлена.

Требования:

- Каждая проблема имеет понятную причину.
- Кнопка ведёт к реально доступному исправлению.
- После исправления возвращает к исходному товару.
- Если требуется .env, прямо укажи, что менять в Telegram невозможно.
- Если требуется перезапуск, сообщи это.
- Если ограничение индивидуальное, открывай индивидуальную настройку.
- Если товар выдаёт Playerok, используй соответствующие настройки.
- Не выводи кнопку, которая гарантированно приведёт к тому же конфликту.
- После исправления обновляй проверку готовности.
- Исправь все пользовательские упоминания старой системы кодов.

D6. УБРАТЬ ЛОЖНОЕ ПРЕДУПРЕЖДЕНИЕ О ПОДКЛЮЧЕНИИ ЧЕРЕЗ ПЯТЬ МИНУТ

connection_summary() может менять отображение после 300 секунд с момента последней успешной проверки.

При этом PlayerokConnection.run() не обязательно обновляет это время, пока подключение считается CONNECTED.

В результате интерфейс создаёт ложную тревогу, хотя нет доказательств потери соединения.

Раздели:

- Последнюю подтверждённую идентичность аккаунта.
- Текущий runtime-статус.
- Давность последней проверки.
- Необходимость повторного подтверждения.
- Действительное отключение разрешений.

Не показывай ложное «подключение потеряно».

Но и не представляй старую проверку как свежую.

Обычное открытие профиля не должно снова сбрасывать автоматику.

D7. ПРАВИЛЬНАЯ ДЛИНА НАЗВАНИЯ С УЧЁТОМ [XXX]

Мастер допускает название до 72 UTF-16 единиц.

При создании логического товара дополнительно добавляется суффикс " [XXX]".

Он занимает шесть UTF-16 единиц.

Нужно проверять окончательное название до принятия ввода.

Если серверный лимит действительно 72 UTF-16 единицы, доступная длина исходного имени уменьшается на длину суффикса.

Показывай понятное предупреждение до финального шага.

Не допускай двойного добавления [XXX].

Не теряй код при редактировании.

Явно объясняй эффект.

Не активируй платные или денежные разрешения незаметно.

Не меняй стандартный выбор на опасный автоматический режим только ради удобства.

При наследовании проверяй подтверждённую идентичность и действующие разрешения.

D11. ИСТОРИЯ ТОВАРА ДОЛЖНА ОТКРЫВАТЬСЯ БЕЗ ПУБЛИЧНОГО GET_ITEM

Редактирование, включение выдачи и внешние отправки должны по-прежнему использовать свежие проверки API.

Не выдавай локальную историю за текущий серверный статус.

D12. УБРАТЬ ДУБЛИРОВАНИЕ ТОВАРОВ В ОСНОВНОМ МЕНЮ

Сейчас AutomationPanel и AutomationQueue строят списки по delivery_policies.item_id.

Требования:

- Его текущий активный item_id определяется из подтверждённых связей.
- Исторические item_id доступны отдельно.
- История не удаляется.
- Нельзя автоматически считать неподтверждённое объявление активным.
- Для legacy-товаров без постоянной идентичности оставь безопасное понятное отображение.
- Список подарков не должен повторять тот же товар через несколько независимых проекций.
- Не теряй доступ к операциям исторических объявлений.

Разделы «Автовыдача», «Товары с подарками», «Мои товары» и «Проблемы» должны иметь согласованную идентичность товара.

D13. МАССОВЫЕ ОСТАНОВКИ ТОЛЬКО С ПОНЯТНЫМ ПОДТВЕРЖДЕНИЕМ

- gft:stop.
- auto:stop.
- promo:stop.
- ar:stop.
- Другие глобальные STOP.
- Callback, реально изменяющие состояние.

Требования:

2. Старый callback не должен незаметно применить изменение к текущей конфигурации.
3. Перед массовой остановкой показывай количество затрагиваемых товаров или правил.
4. Объясняй, что произойдёт с новыми продажами и уже начатыми заказами.
5. Подтверждение привязывай к владельцу, действию, nonce и актуальной ревизии.
6. Повторное нажатие не должно выполнять действие второй раз.
7. Не стирай историю.
8. Не уничтожай настройки временной паузой.
9. Не восстанавливай платные разрешения после экстренного STOP автоматически.
10. Не превращай экстренное отключение в сложную недоступную процедуру.

Экстренный STOP должен оставаться быстро доступным через актуальный интерфейс с надёжной авторизацией и подтверждением.

Для кнопки «Выключить все» автоответы также требуй осмысленное подтверждение.
