# Карточка товара и проверка готовности

## Один маршрут

`Товары → товар → карточка → настройка/проблема → карточка`

`/status` показывает до пяти опубликованных товаров, причины и нумерованные кнопки
проверки/открытия. Полные данные страницы используются сразу; недостающие карточки
догружаются параллельно. Каталог, Stars и MTProto при открытии `/status` не запрашиваются.

Карточка содержит способ выдачи, постоянный код, сохранённое разрешение, причины,
баланс/пакет/резервы для Gifts, момент отправки сообщения и способ отметки выполнения.
«Проверить готовность» выполняет только чтения. «Обновить баланс» использует тот же
полный read-only путь: проверка одного баланса не доказывает готовности выдачи.

Основные настройки:

- Telegram Gifts: существующий LogicalProducts — состав, сообщение после доставки,
  завершение, лимиты, подтверждение привязки и включения. Gifts остаётся обзором
  аккаунта, каталога, выдач, сверок и общих лимитов.
- Склад/текст: тот же LogicalProducts; склад показывается только складскому товару.
  Сохранена отдельная проверка конкретного заказа без отправки.
- Playerok: существующий PlatformPanel; независимые ответ после оплаты и отметка
  выполнения. Сам товар бот повторно не передаёт.
- Ручная выдача: отсутствие автоматики не считается неисправностью.
- Глобальные ответы на фразы покупателей — отдельная функция, не сообщение лота
  после оплаты/доставки.

Изменение действующей конфигурации Gifts/склада/текста требует остановки новых выдач.
Остановка — явная кнопка; чтение диагностики ничего не выключает и не включает.
Смена на Playerok проходит существующее подтверждение и guards PlatformOrders.

## Источники и границы

`ProductReadiness.snapshot()` собирает структурированные признаки из тех же SQLite
таблиц и настроек, которыми пользуются исполнители. `check()` дополняет их свежими
чтениями объявления и, для Gifts, MTProto-каталога/баланса и схемы получения.
Он не заменяет авторизацию бюджета или preflight конкретного заказа в workers.

Состояния: READY, BLOCKED, UNKNOWN, OFF, STOPPED. Причины имеют отдельные коды,
русский текст и существующий маршрут исправления. Необязательные выключенные
сообщения/отметки не создают проблему. Неизвестная операция никогда не становится
разрешением на повтор. Временная ошибка замера сохраняет время прежнего успеха,
но блокирует зелёную готовность текущей проверки. Программное исключение не
превращается в сообщение о недоступности сети.

Частые проверки объединяются коротким cooldown и lock на товар. Память процесса
хранит только последнюю прочитанную карточку для повторного отображения; после
рестарта выполняется новое чтение. Настройки и права берутся из текущей SQLite,
а не из сохранённого текста или старой FSM. Схема БД, исполнители, разрешения,
Outbox, платежные intents и receipt не менялись.

Готовность относится к известным условиям будущей покупки. Username конкретного
покупателя, окончательная стоимость и допустимость отметки выполнения проверяются
существующими workers для каждого оплаченного заказа. Отчёт Playerok не подделывается.
Недоступное редактирование, авторизация личного аккаунта и пополнение Stars требуют
действий владельца; диагностическая кнопка их не обходит.

## Карта переходов и проверок

Все проверки ниже выполняются в production Dispatcher/FSM, на временной SQLite,
с транспортами только на внешней границе. Это не live-приёмка Telegram/Playerok.

| Экран → действие | Callback / следующий экран | Возврат | Автоматическая проверка |
|---|---|---|---|
| /status → проверить/открыть | rd:check:ID / item:ID | Тот же товар | test_product_readiness, test_quick_relist_status |
| Карточка → готовность / Stars | rd:check:ID / rd:balance:ID | item:ID | test_product_readiness |
| Карточка → выдача | iv:delivery:ID → lp:item:ID или platform:item:ID | item:ID | test_product_readiness, test_playerok_delivery |
| Смена способа | lp:method:ID → прежние guarded callbacks | item:ID | test_playerok_delivery, test_unified_delivery_controls |
| Сообщения / завершение | iv:messages:ID / iv:completion:ID → lp или platform | item:ID | test_product_readiness; подтверждение настроек — test_platform_binding |
| История товара | iv:history:ID → order / ops / details | item:ID | test_product_readiness |
| Склад / проверка конкретного заказа | stock:view:ID / auto:check:ID | Карточка/выдача | test_unified_delivery_controls, test_logical_faults |
| Старые Gifts/Automation | gft:item / enable / auto:item → текущая привязка | Товар | test_unified_delivery_controls |
| Привязка, неизвестное редактирование | lp → reconcile, без повторной записи | Товар | test_logical_navigation, test_platform_binding |
| Операция → проверка товара | result:show → rd:check | Товар | test_operation_results_ui, test_product_readiness |

Диагностические случаи: актуальные/устаревшие Stars, нехватка, MTProto, цена/
доступность/лимиты, синхронизация, неподтверждённый код, изменённое описание,
пустой/непустой склад, выключенные необязательные действия, несколько причин,
незавершённый запрос и неизвестный исход — test_product_readiness.

Выдача ровно один раз, потерянный платёжный ответ, закрытые/старые заказы,
перевыставление и приватный ID дополнительно проверяются существующими
test_logical_faults, test_universal_delivery_e2e, test_playerok_delivery,
test_platform_binding и тестами Gifts/Outbox. Таблица описывает фактически
исполняемые группы сценариев, а не доказывает выполнение каждой динамической
ветки всех старых инструментов.

Живой Telegram в этой работе не использовался. Проверка владельцем: открыть
`/status`, нажать проверку возле товара, вернуться в карточку, открыть выдачу,
сообщения и завершение. Проверка не покупает подарки и не пишет покупателям.
