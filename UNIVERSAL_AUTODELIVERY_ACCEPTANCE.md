# Универсальная автовыдача: приёмка и границы доказательства

## Как пользоваться

Товары → товар → Настроить выдачу → **Постоянный код и выдача товара**.
Выберите Telegram-подарки, склад, постоянный текст или ручной режим. Заполните настройки, проверьте превью описания и подтвердите запись. Очередь не считается выполненной записью: откройте «Проверить результат» и дождитесь подтверждения Playerok. После этого отдельно включите выдачу только этого объявления либо разрешите наследование проверенных перевыставлений. Включение не меняет глобальные разрешения.

Для Gifts пакет `gift: heart, heart, bear` хранится внутри SQLite. В публичном описании — только постоянный `#1234567`. Старое `gift:` удаляется только в явно подтверждённом превью. По умолчанию возвраты нового логического товара выключены; их отдельное разрешение всё равно требует глобального флага, окончательного отказа Telegram, допустимого состояния Playerok и отсутствия начатой оплаты. Приветствие поддержано текущими цепочками текста/склада; подарок отправляется без подписи. После доставки доступно отдельное сообщение покупателю.

## Реализация

Миграция **024** добавляет:

- `logical_products`: неизменяемый PK, уникальный публичный код, owner/account, handler/config/revision, отдельный STOP fence `control_revision`, состояние подтверждения, разрешение наследования, cutoff, канонический склад и baseline.
- `logical_listings`: история item IDs, версия конфигурации, точный хеш описания, время подтверждения, операция записи.
- `logical_order_scopes`: неизменяемый order→product/version/item/config/stock scope.
- `logical_scan_items`: приватный durable checkpoint чтения каталога. Пароли/сессии/платёжные формы сюда не копируются; секретный запас остаётся в прежнем Inventory.

Применённые миграции 001–023 не изменены. `migrate_legacy()` создаёт только локальные LEGACY-проекции старых gift bindings с прежними пакетами, ID, ценами, сообщением и options. Она не изменяет старые gift_jobs/steps/receipts, не создаёт внешних операций и не включает выключенные товары. Повторный запуск не меняет результат. Замена описания — отдельное подтверждение владельца.

Реестр находится в `app/services/logical_products.py`. Набор handler IDs проверяется отдельно от Gifts; существующие GiftService, Inventory, Orders, DeliveryChains, EnrollmentWorker, ChainWorker, Outbox и Fulfillment исполняют выдачу. Нет второго двигателя заказов или очереди. `stock_item_id` — постоянный bucket существующего склада; единицы не копируются между объявлениями. Резервы по-прежнему защищены SQLite-транзакцией и уникальными ограничениями.

## Привязка и перевыставление

PREPARE читает свежий лот, проверяет владельца/категорию/получение/цену/данные; для Gifts получает реальный каталог/баланс и согласовывает каждую цену. Криптографический код генерируется до превью. COMMIT проверяет CAS текущей привязки, права и версию, атомарно сохраняет конфигурацию и существующую Outbox-операцию `edit`. Worker ещё раз проверяет baseline/lease/аккаунт, выполняет настоящий поддерживаемый `updateItem`, перечитывает результат. Только точный ответ подтверждает VERIFIED. UNIQUE collision требует нового превью, а не незаметной смены кода.

Потерянный ACK записи → UNCERTAIN. Доступна read-only сверка точного описания/ID/аккаунта/версии; отсутствие кода не разрешает повтор. Подтверждение результата и binding коммитятся одной транзакцией. Никакой локальный флажок не заменяет подтверждение API.

`LogicalProductWorker` использует существующий PageScanner: максимум две страницы списка за проход, до 20 hydration GET, сохранение прогресса, backoff, запрет наследования по неполному/просроченному снимку. Обычно проверка раз в 120 секунд, при незавершённом проходе продолжение через 5 секунд. Одновременные ручной и фоновой проходы одного процесса сериализованы.

Связь нового item ID допускается по заранее разрешённой политике этого логического товара: подтверждённый тот же аккаунт, единственный корректный код, точное описание и критичные параметры, действующая версия и отсутствие конфликта активных копий. `parent_id` не выдумывается. Новый ID получает существующую исполняемую проекцию с первоначальным cutoff, поэтому заказ сразу после перевыставления не теряется. Если новый лот уже продан до сканирования активных объявлений, кандидат догружается из свежего подтверждённого PAID заказа; SOLD сам по себе не разрешает выдачу. Старый item ID также поддерживается.

До резервирования и отправки проверяются свежий лот и закреплённый scope; неподтверждённый код, чужой аккаунт, другой товар/получатель/конфигурация останавливают действие. Изменение настроек при незавершённом намерении блокируется; уже выполненные шаги/receipts не переписываются. STOP инвалидирует незавершённый ARM отдельным fence. Commit логического разрешения выполняется внутри той же транзакции, что включение существующей политики.

## Денежные и товарные инварианты

- Реальные внешние записи только через существующий SafeAccount/Outbox. .env, рабочая SQLite и MTProto-сессия в разработке не изменялись.
- Код публичен, не секрет и не разрешение на расход. Account binding, PAID, точное obtaining field username, повторный resolve, gift ID/цена/количество/лимиты/баланс/receipt сохраняются.
- UNKNOWN/UNCERTAIN не даёт новую форму, повторную покупку или новый складской товар. Нет receipt — нет успеха.
- Точный Telegram ACK и независимый receipt каждого подарка остаются прежними. Внутренний reference не отправляется покупателю.
- Полный возврат запрещён после начала любой оплаты. Для нового логического заказа требуется согласие и в неизменяемом snapshot, и в текущих options; старый экран не может расширить это право.
- Доставка, благодарность и подтверждение Playerok независимы. Ошибка благодарности не отменяет доставку. Неподдерживаемое автоматическое завершение не останавливает выдачу; остаётся ручное действие без фиктивного SENT.
- Исчерпание общего склада останавливает новые выдачи всех связанных объявлений. Последний закреплённый резерв продолжает исполнение; пополнение не снимает защитную остановку автоматически.
- Конфликты вызывают owner-уведомление и появляются в «Требует внимания». Приватные данные выдачи не выводятся в карточках/уведомлениях.

Все новые тесты используют production-сервисы/SQLite/Outbox. Только внешние API заменены транспортами внутри `tests/`. Рабочий runtime не содержит симулятора или fake fallback.

## Найденные и исправленные дефекты

RED перед исправлением: неверный item ID из GET проходил к записи; commit устаревшего второго preview повреждал link; STOP проигрывал ARM; быстрая продажа нового ID терялась; изменяемое сообщение подменяло благодарность старого заказа; старые refund options расширяли snapshot-разрешение; перенос терял прежний after; active legacy выдачу можно было перенастроить без STOP; смена stock bucket после превью сохраняла данные не в тот bucket; owner-уведомление конфликта пропускалось. Дополнительные локальные RED: inline marker и неправильный парсер внутреннего пакета. Независимый reviewer проверил исправления трёх рисков STOP/stale-preview/fast-sale, конкурентные workers/restart и paid cursor после сетевого сбоя.

## Конкретные внешние ограничения и live-приёмка

1. Используемый API и локальные имеющиеся доказательства не подтверждают, сохраняет ли штатное перевыставление ID и описание. Реализованы оба варианта ID; если Playerok удаляет маркер/меняет критичные параметры, автоматическое наследование останавливается. Проверить на контролируемой реальной продаже.
2. У updateItem нет подтверждённого server-side CAS описания. GET→POST оставляет внешнюю гонку с одновременным редактированием другим клиентом. Код не затирает уже обнаруженное изменение, но абсолютную атомарность между клиентами заявлять нельзя.
3. Каталог Playerok не даёт подтверждённого атомарного snapshot всех страниц. Полный ограниченный проход и свежая проверка выбранного лота уменьшают риск, но конкурентная внешняя копия после прохода обнаружится следующим сканом. Это не криптографическое доказательство происхождения relist; доверие задаёт владелец для своего аккаунта/кода/точных параметров.
4. Поле username может быть необязательным на стороне Playerok. Для приложения оно обязательно; без точного значения выдачи нет. Владение покупателя выбранным Telegram username не доказывается.
5. Без точного ACK потерянного платежа и однозначного Telegram receipt повтор запрещён, даже если нужный подарок виден в истории. Нужна безопасная ручная сверка; отсутствие квитанции не даёт новую покупку.
6. Автозавершение применяется только к существующему подтверждённому контракту Fulfillment. Где площадка требует отчёт/данные исполнителя, они не выдумываются. Доставка и благодарность могут завершиться независимо.

Новые реальные изменения описаний/платежи/возвраты/сообщения покупателям на этом этапе не выполнялись. Перед эксплуатацией нужны отдельные разрешённые проверки: сохранение #кода реальным updateItem; реальное перевыставление; первый будущий PAID; точное поле username; receipt без подписи; реальная доставка/благодарность/поддерживаемое завершение. Финальный набор локальных тестов и CI фиксируется в PROGRESS.md.
