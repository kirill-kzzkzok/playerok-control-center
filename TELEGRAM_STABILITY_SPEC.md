1.1. ПЕРЕРАБОТКА КОНСОЛЬНОГО ЛОГИРОВАНИЯ

Сейчас консоль бота засоряется техническими строками вроде:

Telegram editMessageText: SOCKS5 127.0.0.1:1080 — TelegramBadRequest host=api.telegram.org elapsed=1.875s http=400 connection=reused chunked=False bytes=649 cause=--

Telegram getUpdates: SOCKS5 ... TelegramNetworkError

Failed to fetch updates — TelegramNetworkError: ClientConnectionError: Playerok SOCKS service is not ready

При этом многочисленные HTTP 400 не содержат понятной причины, а длинные технические строки мешают увидеть действительно важные события.

Исправь систему логирования.

В обычной консоли должны отображаться короткие человекочитаемые сообщения на русском.

Примеры желаемого формата:

18:15:56 [SUCCESS] Сообщение покупателю отправлено · заказ подтверждён сервером

18:16:54 [WARNING] Не удалось обновить Telegram-панель · MESSAGE_NOT_EDITABLE

18:20:00 [ERROR] Telegram-прокси недоступен · переподключение

18:20:21 [INFO] Telegram-соединение восстановлено

18:25:14 [WARNING] Медленный отклик кнопки · 4.2 с · ожидание Playerok API

18:26:00 [ERROR] Результат отправки неизвестен · требуется сверка

Эти строки являются примерами формата, а не захардкоженными событиями.

Обязательные принципы:

- Один лог — одна короткая строка в обычных случаях.
- Разумная длина сообщения.
- Понятное название операции.
- Понятная причина ошибки, если она установлена.
- Минимум технического шума.
- Безопасный идентификатор операции, если он необходим для диагностики.
- Не выводить каждое успешное обращение к Telegram API.
- Не выводить каждый успешный HTTP 200.
- Не показывать подробности SOCKS5 при каждом запросе.
- Не выводить все поля сетевого транспорта в обычную консоль.

Значимые бизнес-события продолжай логировать.

3.1. СЛУЖЕБНЫЕ ЧЕРНОВИКИ ЗАПУСКА

Приоритет HIGH.

Аудит GLM описал конфликт:

ListingLaunch.open создаёт служебный draft с launch_target.

Этот draft может появляться среди обычных черновиков.

Router может направлять его в обычный Wizard.

Обычный Wizard не рассчитан на такой payload.

Отмена служебного draft может оставлять устаревший указатель launch:config на запись CANCELLED.

Перепроверь поведение на текущем HEAD.

Если проблема сохраняется:

- Раздели обычные черновики и служебные конфигурации запуска.
- Запрети открытие служебной конфигурации в обычном Wizard.
- Предотврати случайное создание второго товара.
- Обеспечь возможность повторно открыть настройку запуска после отмены.
- Сохрани существующие нормальные черновики.
- Корректно обработай старые записи.
- Не выполняй массовую очистку данных.

3.2. УСТОЙЧИВОСТЬ FSM

Проверь раздельные set_state и set_data.

Найди сценарии, когда ошибка между вызовами оставляет неконсистентное состояние.

Обеспечь атомарность только там, где она необходима.

Не меняй глобальную семантику FSM без доказанной необходимости.

Повреждённые или неполные черновики не должны оставлять пользователя в бесконечном KeyError.

Должен существовать безопасный выход или восстановление сценария.

Проверь также новые состояния, появившиеся после UX-переработки.

3.3. СОГЛАСОВАНИЕ UNCERTAIN

Проверь AutoAgreements и переход UNCERTAIN → SUCCEEDED.

Если такой переход обходит обязательные аудит, историю или уведомления, исправь его.

Не повторяй принятие условий Playerok.

Положительное серверное чтение подтверждает уже выполненную операцию, а не разрешает новую мутацию.

Сохрани общий контракт согласования.

3.4. ОТЛОЖЕННОЕ ВКЛЮЧЕНИЕ ЗАКАЗОВ

Проверь EnrollmentWorker.

Установи, могут ли временные ошибки оставлять заказ в PENDING настолько долго, что автоматическая выдача неожиданно начнётся через несколько часов.

Если риск подтверждён:

- Введи ограничение актуальности.
- Используй OWNER_REVIEW_REQUIRED или аналогичное состояние.
- Не выполняй старые заказы неожиданно.
- Не теряй заказ.
- Не скрывай проблему от владельца.
- Не отменяй уже отправленные операции.
- Не нарушай UNCERTAIN.

3.5. ДОПОЛНИТЕЛЬНАЯ ЗАЩИТА OUTBOX

Проверь классификацию APIError.uncertain и защиту Store.finish.

Это потенциальная проблема, не подтверждённый активный баг.

Добавляй defense-in-depth только при сохранении корректного поведения.

После возможного POST система не должна автоматически повторять:

- Выдачу товара.
- Сообщение покупателю.
- Покупку Telegram-подарка.
- PREMIUM.
- Отметку выполнения.
- Другие внешние мутации.

Добавь тесты на ошибки до POST и после возможного POST.

Не смешивай неизвестный результат Telegram UI-редактирования с неизвестным результатом денежной операции.
