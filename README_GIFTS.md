# Telegram-подарки с личного аккаунта

Интеграция работает внутри Playerok Control Center: существующие Dispatcher,
Orders, OutboxWorker, уведомления, SQLite WAL и Fulfillment. Отдельного бота нет.
Реальные покупки и возвраты этой интеграцией пока **не проверялись** и выключены.

## Настройка

1. Установить зависимости из `requirements.lock.txt`. Используется Telethon 1.45.0
   (у установленного пакета TL layer 229).
2. Получить собственные `api_id` / `api_hash` в https://my.telegram.org.
   Заполнить **локальный** `.env`: `TG_USER_API_ID`, `TG_USER_API_HASH`.
   Не присылать коды входа, пароль 2FA, API hash или session-файл в чат.
3. Остановить экземпляр приложения, использующий эту MTProto-сессию. В локальном
   интерактивном терминале выполнить `.venv/Scripts/python -m app.gifts.auth`.
   Авторизовать личный аккаунт; Bot API token для покупки подарков не используется.
   Сессия — `data/telegram_personal.session`; каталог data и session-файлы исключены
   из Git. Авторизация и runtime используют один файловый lock сессии.
4. Оставить `TG_GIFT_PAYMENTS_ENABLED=false`, `TG_GIFT_REFUNDS_ENABLED=false`.
   Просмотр состояния, каталога и баланса не требует включения платежей.
5. В панели открыть **🎁 Telegram-подарки → Подключение / баланс / каталог**.
   Проверить текущий каталог именно личного аккаунта. Значения из JSON — снимок,
   а не доказательство текущей доступности/цены.
6. У лота выбрать способ «Подарок». Последняя непустая строка описания должна быть,
   например, `gift: heart` или `gift: bear, bear, rose`. Каждая позиция — один
   подарок, включая повторяющиеся коды. Неизвестные/пустые элементы и несколько
   строк gift: запрещены. Мастер проверяет метку, но не разрешает расходы автоматически.
7. В карточке лота открыть **🎁 Telegram-подарок → Подтвердить код**.
   Проверить код, Telegram gift ID и актуальную стоимость. Привязка выключена.
   Изменение цены между превью и подтверждением отклоняется.
8. Только после отдельного разрешения на live-проверку включить необходимые
   глобальные допуски и подтвердить конкретный лот для **будущих** заказов.
   По умолчанию всё остаётся выключено. Первое включение не подхватывает старые
   оплаченные заказы. Смена настроек не повторяет старую выдачу.

Свежая read-only проверка 2026-10-30 подтвердила:

|---|---|
| Telegram → Звезды | `1ef2da4b-1ffc-62f0-b165-b07be0dc1444` |
| Получение «Подарок» | `1effb589-89db-61a0-5e74-3e27df00c994` |
| Username, OBTAINING_DATA / INPUT | `1effb589-d13f-6780-15ec-fe00995e7539` |

Эти публичные ID добавлены в `.env.example` и локальный `.env`. Схема повторно
проверяется при привязке и выдаче. **Playerok возвращает `required=false`**:
приложение не может превратить это поле в обязательное на сайте. Поэтому значение
обязательно для приложения: при его отсутствии покупка запрещена и нужен продавец.
Это ограничение площадки, а не выполненный критерий обязательности checkout.

Получатель берётся только из `obtaining_fields` с точным ID. Нет выбора по label,
нет fallback на `automation_obtaining_fields`, комментарий, переписку, Playerok
username или аккаунт владельца. Проверяются нормализация и формат; затем настоящий
`contacts.resolveUsername`, User ID, access hash/InputPeerUser, тип User, отсутствие
bot/deleted/min и совпадение активного username. ID фиксируется для сделки.
Перед покупкой username разрешается повторно: смена ID останавливает выдачу.
Покупатель сам выбирает адресата; доказать владение им Playerok-аккаунтом нельзя.

## Жизненный цикл и деньги

`PAID → пакет → gift_send каждой позиции → CHECKING → SPENDING → SUCCEEDED / UNCERTAIN`.

## Несколько подарков в одном заказе

Формат последней непустой строки, без изменения старого одиночного формата:

```text
gift: bear
gift: bear, bear
gift: bear, rose
gift: heart, bear, rose
```

Регистр и пробелы нормализуются, порядок и повторы сохраняются. `bear, bear, rose`
означает два Bear и одну Rose. Если текущие цены 15/25 Stars, сумма равна55 Stars;
это пример, при привязке и покупке используются только реальные текущие цены.
По умолчанию максимум5 позиций. Настройка `TG_GIFT_MAX_COUNT` в локальном `.env`
позволяет изменить предел; абсолютный защитный потолок20. Пустые элементы,
`;` вместо запятой, неизвестные коды, несколько меток и превышение предела запрещены.

**🎁 Telegram-подарки → лот → Подтвердить пакет** показывает количество каждого
вида, стоимость, общее число и итоговую цену. Подтверждение не включает отправку.
Смена любой согласованной цены требует повторной привязки. Список уже начатого
заказа не меняется вместе с последующим редактированием объявления.

SQLite22 хранит неизменяемый snapshot пакета и отдельную строку gift_steps для
каждой позиции: порядок, код, gift ID, цена, reference намерения, операция Outbox,
получатель, статус, форма, время dispatch и независимый receipt. До первой покупки
проверяется весь оставшийся пакет, суммарный баланс, индивидуальные ограничения
количества, лимит заказа/суток; остаток суммы резервируется транзакционно.
Параллельный заказ учитывает чужие резервы. Если между чтением баланса и intent
была другая отправка, наблюдение баланса отклоняется как устаревшее.

Следующая позиция получает свою Outbox-операцию только после подтверждения текущей.
Ключ включает order ID и позицию; два Bear имеют разные reference/operation/form ID.
Успешные шаги не отправляются заново после рестарта. Не начатая следующая операция
продолжается при действующих разрешениях и повторной проверке условий. UNKNOWN
блокирует пакет и новые покупки; нет повторной формы/покупки по timeout или по
отсутствию сообщения. Достоверная read-only сверка может подтвердить ровно этот
шаг; затем очередь продолжает оставшиеся позиции при действующих допусках.

При частичной выдаче карточка показывает **PARTIALLY_DELIVERED / BLOCKED**, прогресс,
каждый шаг, причину, подтверждённый и неизвестный расход Stars, серверное message ID
и переход к истории операции. Общий журнал скрывает получателя. Полный возврат и
SENT запрещены, пока не подтверждены все предусмотренные подарки. Владелец получает
обычное durable уведомление с отправленными/оставшимися позициями. Покупателю не
отправляется успешное итоговое уведомление о частично доставленном заказе.

Для BLOCKED позиции без платёжного intent есть **«Повторить только безопасную
проверку»** с отдельным подтверждением: продолжение с первой неотправленной позиции,
без повтора доставленных. Snapshot должен совпадать с привязкой. Если изменились
цены/состав/описание или есть неизвестный платёж, безопасное автоматическое
продолжение недоступно: требуется отдельное ручное решение, а не редактирование БД.
Возврат из-за username допускается только до **первой попытки оплаты всего пакета**.
Ошибки/смена username после начала выдачи не создают полный автовозврат.

Одно итоговое buyer notice и допустимый существующий Fulfillment запускаются только
после всех receipt. Журнал Stars хранит фактические суммы каждой подтверждённой
позиции отдельно от неизвестного расхода/резерва. Автоматического пересчёта Stars
в рублёвую себестоимость без подтверждённого курса нет.

Миграция21→22 переносит старые одиночные привязки/заказы в одну позицию. Сохраняются
настройки, form/reference/receipt, исходные статусы и существующая очередь.
Миграция не создаёт новых операций и не переоткрывает завершённые/UNKNOWN заказы.

## Живая Windows-консоль

Двойной щелчок по `start.bat` запускает один foreground Python-процесс. Консоль
работает всё время запуска, UTF-8 и unbuffered включены. Ctrl+C проходит через
существующее корректное завершение; после выхода/ошибки `pause` сохраняет окно.
`start`/pythonw, второй экземпляр ради логов и открытие новых окон не используются.

События имеют московское время, категории INFO/ORDER/CHECK/GIFT/SUCCESS/WARNING,
уровни DEBUG/INFO/WARNING/ERROR/CRITICAL и контекст заказа/операции/позиции.
ANSI включается только при поддержке терминала; иначе обычный текст. Для цветов
и emoji нужен поддерживающий их Windows-терминал/шрифт. Фактический двойной клик и
внешний вид терминала в текущей проверке не выполнялись; проверены launcher contract,
настоящий stdout/subprocess, форматирование/flush/файлы/ротация.

По умолчанию INFO. Локально можно задать `PCC_LOG_LEVEL=DEBUG`; `NO_COLOR=1`
выключает цвета. Одинаковые polling-события не засоряют INFO, неизменные циклы
синхронизации видны в DEBUG. Дубли handlers исключены при повторной настройке.
Файлы `logs/control_center.log` ротируются:2 MB,5 архивов. Событие «доставка
подтверждена» выводится только после сохранённого receipt, а не после постановки
в очередь. Ошибки содержат безопасный код/тип и контекст без сырых RPC payload.
Username всегда маскируется; owner-only режим его раскрытия не добавлялся.
API hash, access hash, session, cookies, токены, JWT и складской запас запрещены
в логах даже в DEBUG. Логи и резервные копии исключены из Git.

- Свежая продажа должна принадлежать магазину, иметь правильный item ID, чат,
  PAID, отсутствие проблемы и серверной автоматической выдачи.
- Перед расходом читаются актуальные каталог, доступность, Premium/лимиты подарка,
  `users.getFullUser.disallowed_gifts`, `checkCanSendGift`, баланс Stars и форма XTR.
  Цена обязана совпасть с отдельно согласованной ценой привязки и суммой формы.
- В BEGIN IMMEDIATE проверяются lease/CAS, политика, глобальные допуски, проблема
  заказа, лимиты и отсутствие другого SPENDING/UNCERTAIN платежа.
  Получатель, payer ID, gift ID, стоимость, уникальный form ID, opaque reference и
  намерение сохраняются **до** единственного `sendStarsForm`.
- У Telethon выключены RPC-повторы, автоматическое переподключение и FloodWait sleep.
  Неизвестный исход не приводит к новой форме или повторной покупке.
- `PaymentResult` недостаточен: отдельное чтение исходящего MessageActionStarGift
  проверяет получателя, gift ID, точный сохранённый Telegram message ID, дату и отсутствие refunded. Reference новых отправок остаётся только локальным; для старых отправок сохранена отдельная сверка по подписи.
  Только после этого общий Store.finish атомарно сохраняет подтверждение.
- Ограничены расход за заказ и за календарные сутки UTC; неопределённые расходы
  учитываются консервативно. Любая неразрешённая оплата/возврат блокирует новые покупки.
- При рестарте истёкший lease после SPENDING становится UNCERTAIN. Сбой до intent
  оставляет BLOCKED; никакой автоматической повторной оплаты. Для доказанного отказа
  до платежа есть отдельное подтверждение безопасной проверки в карточке заказа.
  Оно создаёт новый Outbox receipt, сохраняя прежнюю историю.
- В UNCERTAIN доступна только read-only сверка доставки. Поиск ограничен 100
  последними сообщениями адресата, либо точным message ID из PaymentResult.
  Отсутствие квитанции не доказывает отсутствие платежа; блокировка сохраняется. Для новых отправок без подписи поиск истории не используется, если точный message ID из платёжного ответа не сохранён.
- Содержимое складских единиц, username/access hash и session не попадают в общие
  списки, Outbox receipts и уведомления. SQLite/backup содержат приватные данные;
  обращаться с ними как с секретами. Telethon logger изолирован от общих логов.

Каталог и привязки сохраняются в SQLite. Смена описания/характеристик или удаление
лота через приложение сразу останавливают подарочную политику. Изменения на сайте
выявляет свежая проверка перед покупкой. Изменение цены Stars/недоступность подарка
тоже останавливают лот до повторной привязки. Пополнение баланса не включает его.
Один заказ не может одновременно попасть в склад/цепочку и в подарочную выдачу.

## Уведомления и завершение

После доказанной доставки отдельная операция gift_notice сообщает покупателю
результат через чат Playerok. Её сбой/UNCERTAIN не повторяет подарок. Владелец
получает стандартный durable OperationResults receipt; результаты доступны также
в разделе подарков и карточке заказа. Есть успешные/ошибочные/возвратные/UNKNOWN
списки, пагинация, безопасная сверка и **экстренная остановка новых покупок**.
Остановка не может отозвать запрос, уже отправленный Telegram.

При включении лота можно отдельно разрешить авто-SENT после подтверждённого подарка.
Автоматически используется только существующий **legacy** Fulfillment с повторной
проверкой заказа и серверным подтверждением SENT. Для требования draft/fields,
неизвестной роли, изменившихся требований или остановленной политики сохраняется
ручное решение через существующую форму. Провайдер/отчёт не выдумываются.
Складская выдача автоматически SENT не включает. Подтверждение покупателя отдельно.

## Возвраты

Подтверждены код библиотеки и официальный веб-клиент Playerok: кнопка продавца
«Сделать возврат» использует updateDeal с ROLLED_BACK для активной OUT сделки
обычного, не системного товара. Публичные скрипты повторно получены HTTP200,
их hash совпал с изученной версией; свидетельство — `data/gifts_refund_contract.json`.
Консервативный адаптер допускает только собственную PAID продажу, известные
seller_type USER / role USER, без проблемы и серверной автоматики.
Это подтверждение контракта, **не live-приёмка возврата**.

Отдельный `TG_GIFT_REFUNDS_ENABLED=false` по умолчанию. При разрешении возврата
только окончательные `USERNAME_INVALID` / `USERNAME_NOT_OCCUPIED` от resolveUsername
могут зарегистрировать единственную gift_refund через общий Outbox. Сначала новый
get_deal, затем защищённый updateDeal и независимый get_deal с ROLLED_BACK.
Только подтверждённый сервером возврат меняет refund_state на CONFIRMED и разрешает
сообщение «возврат подтверждён». Локальный статус заказа не подделывается.

Локально неверный формат, канал, смена username, FloodWait, timeout, отсутствие
авторизации и ошибки сети не являются доказательством отсутствия пользователя.
Они не запускают автовозврат. При выключенном допуске, неподдерживаемой сделке или
отказе сервера — ручная очередь. Потерянный ответ возврата → UNCERTAIN и только
сверка чтением; повторного refund нет. После SPENDING подарка возврат запрещён.
Покупатель в ручном случае получает честное уведомление без обещания возврата.

## Один контролируемый live-тест

Нужны локально авторизованная личная сессия, проверенный баланс, реальный разрешённый
лот с gift: heart, известный получатель и отдельное разрешение на **одну** платную
отправку (согласовать также сообщение в Playerok, допустимый SENT и отдельно refund,
если он входит в тест). До разрешения допуски остаются false, лоты выключены.
Для первого теста установить лимиты 15 Stars за заказ / сутки после свежего
подтверждения цены. Все прочие подарочные лоты остановлены. Покупатель оформляет
настоящий PAID заказ и вводит username в указанное поле. Проверить фактическое
получение, Stars, receipt и серверную сделку независимо; mock не закрывает live gate.

## Сеть localVPN

По умолчанию личный Telethon и Bot API используют один отдельный SOCKS5 на1080;
подробности: [LOCALVPN_INTEGRATION.md](LOCALVPN_INTEGRATION.md). Перед локальной
авторизацией `.venv/Scripts/python -m app.gifts.auth` остановите бот: авторизация
поднимает тот же управляемый сервис, занимает session lock и сохраняет действующую
сессию. Новый телефон/код не запрашивается, если Telethon подтверждает сохранённую сессию.
Сетевая интеграция не разрешает оплату. При потере/смене туннеля покупки блокируются;
неопределённый платёж требует receipt-сверки, не повтора. В этой задаче выполнен
только unauthenticated MTProto MemorySession help.getConfig, не личная Gifts-приёмка.

## Финальные изменения takeover (2026-11-01)
Подготовка запуска больше не меняет управляющие настройки до общей транзакции: расписание, автовыдача, резерв расходов, разрешение продвижения конкретного лота, маркер и Outbox фиксируются вместе. Наблюдения каталога, баланса и подтверждённого плательщика могут обновляться во время PREPARE; они не разрешают расходы.

Глобальная остановка подарков не отменяется включением отдельного товара. После установки или STOP: «Подарки → Настроить → Разрешить новые покупки» → явное подтверждение. Это только общий допуск; товары включаются отдельно. Более новая остановка во время сетевой проверки отменяет старое подтверждение.

Схема Playerok может возвращать точное поле Telegram username как необязательное. Это не блокирует настройку, но перед оплатой обязательно требуется одно корректное значение именно этого поля свежей оплаченной сделки. Комментарий, профиль и чат не заменяют его.

Первый запуск созданного приложением черновика сохраняет серверную дату создания как границу новых заказов только при подтверждённой привязке аккаунта, совпадающей квитанции создания и отсутствии предыдущих попыток публикации/известных заказов. Это устраняет сравнение секунд сервера с микросекундами локального включения. Импортированные/старые черновики без таких доказательств сохраняют строгую временную границу. Распределённая атомарность сайта и локального приложения не гарантируется; внешние изменения на сайте между проверками остаются риском.

Отчёты текущего прохода: FINAL_ACCEPTANCE_REPORT.md, TAKEOVER_FINANCIAL_REVIEW.md, FINAL_UX_ACCEPTANCE.md. Изолированный mock E2E: tests/test_final_acceptance_e2e.py. Контролируемый live-orchestrator tools/controlled_heart_acceptance.py по умолчанию выполняет только read-only preflight; отдельный явно указанный ключ допускает строго один Heart/15 Stars в отдельном постоянном журнале, с поддельным Playerok. Его нельзя использовать как обычную команду магазина; повтор существующего журнала запрещён.

## Подарки без подписи — обязательное исправление 2026-11-01
Новые Gifts отправляются вообще без InputInvoiceStarGift.message: нет PCC-reference, благодарности или другого комментария. Внутренний reference остаётся в SQLite, в публичный платёжный payload не попадает.

Миграция023 добавляет gift_steps.receipt_mode и ack_message_id. Для старых записей сохраняется REFERENCE, их receipt/цены/состояния не переписываются. Новая попытка атомарно фиксирует MESSAGE_ID вместе со SPENDING-intent доRPC. Из результата именно этого SendStarsForm выбирается ровно один подходящий исходящий Gift; ID сохраняется до независимого чтения истории. По точному ID повторно проверяются аккаунт-отправитель, получатель, gift ID, время и отсутствие refund/посторонней подписи. Уникальный индекс и проверка уже подтверждённых квитанций запрещают присвоить одно сообщение двум заказам.

Если ответ RPC потерян, ACK не содержит Gift либо неоднозначен, новый пустой Gift остаётся UNCERTAIN. Даже один похожий Gift в истории не разрешает подтвердить его или повторить покупку. Сохранённый ACK при timeout чтения позволяет безопасную read-only сверку после рестарта. Старые подписанные отправки продолжают проверяться по своему прежнему reference; новых подписей не создаётся.

Источник схем: https://core.telegram.org/constructor/inputInvoiceStarGift (message optional), https://core.telegram.org/constructor/payments.paymentResult (updates), https://core.telegram.org/constructor/messageActionStarGift. Привязка использует message ID из непосредственного ответа платёжного RPC; это корреляция, не замена независимому receipt.
Реальная Heart-квитанция16998 относится к прежней версии с видимым reference. Исправленная пустая подпись проверяется только mock/fault/restart тестами: новых расходов и реальных отправок не было. Рабочая SQLite и сессия для миграционных тестов не открывались.

## Логические товары с постоянным кодом

Новый путь: **Товары → товар → Настроить выдачу → Постоянный код и выдача товара**. Пакет (`gift: heart, heart, bear`) настраивается в Telegram и хранится в SQLite, а постоянный код размещается в конце названия: `Название [AB6]`. Запись названия подтверждается отдельно через настоящий Outbox и повторное чтение API. Включение платежей/автовыдачи — отдельное разрешение.

Перевыставления наследуют настройки лишь после заранее разрешённой проверки аккаунта, кода, точного описания, цены, категории/способа получения и отсутствия конфликтующих активных копий. Старые gift:-привязки, незавершённые шаги и receipt не переигрываются. Перенос не удаляет старую историю; сначала безопасно разрешите незавершённые операции; автоматический перенос старого #кода использует прежний Outbox без повторной покупки подарка. Возврат для нового логического товара по умолчанию выключен.

[Приёмка и внешние ограничения](UNIVERSAL_AUTODELIVERY_ACCEPTANCE.md). В этой интеграции новые live-покупки и записи не выполнялись; тестовые транспорты существуют только в tests.

### Купленный товар с отдельным ID в сделке

Playerok может вернуть в заказе снимок товара с ID, недоступным через публичный `get_item` (HTTP 404). Для Telegram Gifts сверка читает полный товар через эту же сделку. Наследование требует заранее включённого постоянного кода и разрешения на перевыставления, совпадения владельца, описания и всех критичных параметров, а также проверки публичных копий кода. Снимок разрешает выдачу только одному исходному заказу; он не становится общей привязкой для других продаж.

Перед каждым подарком заново проверяются оплаченный статус сделки, её товар и поле получения. Старые частичные данные не заменяют свежий ответ. Закрытые сделки не переисполняются, а неизвестный результат платежа блокирует повтор и следующие подарки. Все прежние разрешения, лимиты и подтверждения сохраняются.

Миграция 027 добавляет происхождение снимка, не меняя старые привязки и платежи. При запуске обновлённого бота она применяется штатным механизмом миграций. Разработческие проверки используют временную SQLite. Реальный read-only ответ Playerok подтвердил контракт полного товара сделки; успешная отправка по этому новому пути пока проверена только изолированными транспортами.

### Единое управление настроенным товаром

Для товара с постоянным кодом используйте **Товар → Настроить выдачу → Настроить выдачу товара**. Старые входы из раздела подарков и настроек обычной автовыдачи открывают эту же панель. Старые подтверждения включения и обновления отдельной подарочной привязки больше не действуют: откройте товар и подтвердите настройку заново. Остановка такого товара отключает его выдачу во всех связанных объявлениях, сохраняя историю и результаты отправленных запросов.

У текстовой и складской выдачи сохранена отдельная **Проверка без отправки** по оплаченному заказу. Она читает действующие настройки и API, не меняет запас и не отправляет товар. Возможный ручной запуск заказа по-прежнему требует отдельного подтверждения. Товары без постоянной привязки сохраняют прежние совместимые настройки. Новый мастер автоматической выдачи создаёт постоянную привязку сам; старые объявления не мигрируются и не включаются без разрешения владельца.

Приватные снимки купленных товаров не отображаются как отдельные объявления в списке настройки подарков. Их результаты остаются в истории заказов и выдач.

### Подарочный товар в едином мастере

Обычное описание → фото/цена → **Telegram Gifts** → кнопки актуального каталога.
Техническую `gift:`-метку вводить не требуется. Постоянный код выделяется вместе
с очередью создания в одной транзакции; серверный DRAFT независимо перечитывается,
после чего подтверждается его привязка, пока выключенная. В экране запуска задаются
сообщение после выдачи, Stars-лимиты, допустимое завершение/возврат и наследование.
**Опубликовать и запустить** сохраняет согласованную конфигурацию и включает
её проекцию до отправки публикации. Заказ, появившийся сразу после публикации,
не теряется из-за поздней временной границы включения.

Это не распределённая транзакция с Playerok: при неизвестном исходе публикации
повтор блокируется. Если потеряно лишь последующее чтение создания, сохранённый
ID ответа позволяет выполнить сверку в истории операций. Если потерян сам ответ
создания и надёжного ID нет, система не угадывает его и не создаёт копию.

Каталог, стоимость и наличие проверяются заново; одинаковые emoji не заменяют
gift ID. После редактирования состава/описания может понадобиться новое подтверждение.
Подарки продолжают отправляться без подписи; внутренний reference не виден покупателю.
Receipt, UNKNOWN/UNCERTAIN, дневные резервы, STOP и запрет полного возврата после
начала оплаты сохраняются. Реальная отправка по новому мастеру пока не выполнялась.
